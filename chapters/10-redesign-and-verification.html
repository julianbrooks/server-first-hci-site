10  Redesign and verification

By the end you have made the top-ranked change, run the twenty regression checks on it, re-piloted with two new participants, and written the chain from finding to verification with a file behind each link.

Before you start, you need the ranking from Chapter 9, a branch made from the week-10 tag, and two participants booked who were not among the first four. Have the parity table from Chapter 6 to hand.

10.1 Smaller than the bug report

The change is one change, and it is small. The finding named a task, a mode and a cause; the change removes the cause and nothing else. A few files and thirty lines is the shape of most fixes to this application, and a fix that touches ten files is either two fixes or a redesign the evidence did not ask for.

For a validation finding, three layers are available, and they catch different people. A browser attribute such as minlength stops the submission before it leaves the page, for anyone whose browser honours it. A CSS rule on :user-invalid shows the field in its error state as soon as the person leaves it, for anyone who can see it. The server, which already marks the field with aria-invalid and links the message with aria-describedby, catches what the other two miss, a script, an old browser, a form posted from elsewhere, and is the layer a screen reader hears. Chapter 6 left required and minlength off on purpose so that the server's path was the one you measured; this is the point where you decide, from your own data, whether to add them.

If you do, know what it does to your instrument. A submission the browser blocks never reaches the server, so after the change the validation_error rows for that task fall to zero whether or not people stopped making the mistake. The log has gone blind to the attempt, and a zero in the after table is the fix and the blind spot together. The note-taker counts browser-blocked submissions in the re-pilot, and the write-up gives that count beside the zero.

10.2 Activity 1: write the change down first

Under the top finding in research/findings.md, add a section headed Change, written before you open an editor. It names the files that will change; what a participant will see differently in each mode, one sentence each; which number in the before table should move and in which direction; which numbers should not move, always including the median server time and the parity rows for the routes you touch; and the WCAG criterion to check against, if the finding named one. This is the acceptance criterion, written now so that the result cannot rewrite it.

10.3 Activity 2: make it

Make the smallest change that removes the cause, in both modes, on your branch. Run ./gradlew test: the template smoke test loads every template and the route tests exercise every route in both modes, so a change that breaks either fails here and not in front of a participant. Then start the server and do the changed task yourself in both modes, switching as Chapter 7 showed, and read the footer to know which mode you are in.

Three things catch people here. A changed stylesheet is cached and a changed template is not, so a CSS change that does not appear needs a reload with the cache bypassed (Ctrl-Shift-R). HTMX does not swap a 4xx response by default, so a change that sends 400 on a validation error makes the error vanish with JavaScript on; Chapter 7 said why the routes answer 200 and 303. And a fragment given autofocus moves focus to that control every time it is swapped in, which is what you want for an error and not for a status message.

Commit on the branch with a message that names the finding's heading and the criterion. The commit hash is the third link in the chain.

10.4 Activity 3: the regression checks

Run every row of the table against your branch, in both modes where the test allows, and record each in research/regression.csv with the columns id, pass, notes. A row that fails on your branch and passed at the tag is a regression, fixed before the re-pilot. A row that fails at the tag too is a finding, and goes on the backlog with its criterion in the evidence column.

Row 9 fails at the week-10 tag for five actions. With JavaScript on, the add field and the filter field keep focus, because they are outside the element that is swapped, but Save, Cancel, Mark done, Delete and the pager's Next are inside the element they replace, and after the swap nothing is focused; a person using the keyboard starts again from the top of the page. The reference code has this defect as shipped. A change that returns focus to the row or the list after those swaps is a legitimate top-ranked change if your pilots showed people paying for it. Record the row as failing at the tag, with the actions, whether or not you fix it.

10.5 Activity 4: re-pilot with two new participants

The first four participants have done the tasks twice and know where everything is; a third pass from them measures their memory. Recruit two people who have not seen the list and run the procedure from Chapter 8 unchanged: the same plan and seed data, pseudonyms P5 and P6, one starting in each mode, on your branch, with the metrics file deleted first. If your change moved a check into the browser, the note-taker tallies each time the browser refused a submission, next to the task code. Copy the metrics file to research/metrics-after.csv and the notes to research/pilots/P5.md and P6.md, read both for names, and commit.

The edit errors have gone from two of six and two of eight to none in either mode, the add errors likewise, and every median server time is within a few milliseconds of before, which is what a change to a form and not to the storage should do. The two files are synthetic. They were written by tools/GenerateExampleMetrics.kt from fixed seeds, a test keeps them in step with the script, and git diff week-09 week-10 -- src is empty: no change in the tag produced the second file. They exist so that you can practise the comparison before your own data exists.

tools/GenerateExampleMetrics.kt
// Writes data/example-metrics.csv and data/example-metrics-postchange.csv: synthetic
// pilot data for the Week 10 analysis exercise. The random seeds are fixed, so the files
// are reproducible, and a test checks that the committed files match this script.
//
//   ./gradlew generateExampleMetrics
//
// Five participants per pilot, alternating HTMX and no-JS, each doing the Week 9 tasks
// in order. Without JavaScript a POST is followed by the redirect's GET, so those
// participants produce an extra T0_list row after each change, as the real server does.
// The post-change pilot has fewer validation errors on edit and add, which is the
// difference docs/redesign-example.md is about.

Your own comparison is written in the terms Appendix I sets: the before and after figures with their denominators, "two of four saves" and "none of four", and the number of participants each comes from; the time on task for the changed task, for P5 and P6 in each mode, beside the four from before; what did not move; and what the two participants said at the debrief, quoted. Then say what two participants can and cannot show: not that the change works for people in general, but that the failure the finding described did not happen in front of you again, which is the evidence this book asks for before a change is kept.

A change that did not help is written up the same way, with the same tables, and the decision to keep or revert it is given with its reason. The chain is marked on whether it closes, not on which way the numbers went; a reverted change with a full verification is a stronger portfolio section than a kept one with a thin one.

10.7 What to record

The chain has four links and a file behind each: the finding (research/findings.md, the heading), the measurement (research/metrics.csv, the rows, and the before table), the change (the commit hash and git diff against the tag), and the verification (research/regression.csv, research/metrics-after.csv, the after table and the two participants' notes). Merge the branch, tag the result with a name of your own, and write the tag in the findings file; Chapter 11 presents the chain and Chapter 12 links to it.

10.8 Further reading

GOV.UK's error summary pattern is the published design for telling a person what went wrong with a form, and the reference code's summary follows it (Government Digital Service, no date). Deque's account of how much of WCAG an automated checker can find is the reason most rows of the regression table are run by a person (Deque Systems, 2021).
