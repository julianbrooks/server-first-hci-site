9  Analysis and prioritisation

By the end you have a findings file that turns four participants' metrics and notes into ranked findings, each with the rows and lines behind it, and a backlog whose top row is the change you make in Chapter 10.

Before you start, check out the week-10 tag and run ./gradlew build; it now compiles tools/ as well, and ./gradlew tasks --group evaluation lists analyse. Have research/metrics.csv, research/pilots/P1.md to P4.md and research/plan.md from Chapter 8 open, and Appendix I to hand; this chapter uses its definitions without restating them.

9.1 Two kinds of bug

How do we know the task list works? A developer has three answers: it compiles, the tests pass, I used it and it worked for me. None of them says how anyone else fared. The audit in Chapter 4 found the first kind of bug, the kind you can see: a field with no label, a link with no text. The pilots recorded the second kind, the kind you can only measure. A participant without JavaScript who submitted a two-letter title saw the page reload and nothing else, because the status region is empty after a redirect, and said nothing about it at the debrief, because from where they sat nothing had happened. The server wrote a validation_error row at the second it happened. This chapter is where rows like that become findings, and where the notes say what the rows cannot.

9.2 Activity 1: read the notes before the numbers

Open the four notes files and read the procedural paragraph at the end of each one first. A cookie set late, a server restarted, a task read twice: each changes what that participant's rows mean, and the decision about them is made now, before any number is computed, so that the numbers cannot influence it. Start research/findings.md with a section called Data and write one line per participant: the pseudonym, the order of the modes, and any rows excluded or re-attributed and why. Rows under six hex characters that belong to a participant whose cookie was set late are re-attributed by timestamp, as Chapter 8 said; write the time range you used.

Count the rows per pseudonym and mode in research/metrics.csv and write the counts in the same section. A participant with rows in only one mode contributes nothing to the comparison between modes; they still contribute notes.

Run the tool on the example file at this tag first, so that you know what the table looks like when it is right:

The tool groups the rows by task code and mode and prints one line per group. n_success and errors are counts of rows, error_rate is errors over their sum, and the median and MAD are of the successful requests only; summarise is where that is decided:

tools/Analyse.kt
/** One summary per task code and js_mode, sorted. Median and MAD use the successful requests only. */
fun summarise(rows: List<MetricRow>): List<Summary> =
    rows.groupBy { it.taskCode to it.jsMode }
        .toSortedMap(compareBy({ it.first }, { it.second }))
        .map { (key, group) ->
            val successMs = group.filter { it.step == "success" }.map { it.ms }
            Summary(key.first, key.second, successMs.size, median(successMs), mad(successMs), group.size - successMs.size)
        }

median_ms and mad_ms are server time. In the example they lie between 10 and 48 milliseconds, and the gap between the modes is the cost of rendering a page rather than a fragment. They say nothing about participants; the one question they answer is whether a change slowed the server, which is Chapter 10's question. Error rate is the column that carries a finding: in the example, the edit task failed in two of six requests without JavaScript and two of eight with it, adding failed in two of six and one of seven, and nothing else failed.

Two things about the rows come from driving a browser against this code, and both change how you read the edit line. Without JavaScript every action writes two rows, the POST that answers 303 and the list GET the browser makes next, which is why T0_list has sixteen successes in the plain mode and three with HTMX; it is not a task, and its line only confirms that the redirects happened. And opening the edit form writes a T2_edit row in both modes: HTMX fetches the form as a fragment, and without JavaScript the Edit button loads the list with one row as a form, which the list route logs under the edit code. So for every edit there is one opening row and then one row per save, and the denominator for the edit error rate is the number of saves, which the tool does not know. For the example data that is two errors in five saves with HTMX and two in four without, not two in eight requests and two in six. Find the saves from the timestamps, write the denominator in the finding, and say that the tool's figure is per request.

Now run ./gradlew analyse -Pfile=research/metrics.csv and read your own table the same way. If the tool stops with a message that a column is missing, the file was edited in a spreadsheet that renamed the header; take the copy from data/ again.

9.4 Activity 3: time on task from the timestamps

The tool does not compute time on task, because which row ends a task is a judgement your plan made. Open research/metrics.csv in a spreadsheet, sort by session_id and then ts_iso, and for each participant, mode and task find the row your plan named as the end of that task and the row before it; the gap in seconds is the time on task as Appendix I defines it, a few seconds high for everyone in the same way. For four participants, five tasks and two modes that is forty numbers, an hour's careful work, and not worth automating for one study. Put them in a table in findings.md with a row per participant and a column per task and mode. The example data cannot be used for this, since each of its participants did one mode only.

Under each task, compute the median and MAD across the four participants in each mode, and for each participant the difference between their two modes. Then write the sentence Appendix I asks for: how many of the four were faster in which mode and by how much, naming anyone who went the other way. If two differences are a few seconds and two are a minute, you have two findings, not an average.

9.5 Activity 4: join the numbers to the notes

Read the notes for what they say about each task, and write one finding per thing the data and the notes agree happened. A finding is a paragraph with a short heading carrying three things: what the numbers say, with the rows behind them (the file, the pseudonym and the timestamps, so that a reader can find them); what the notes say, with the file and line, quoting the participant where there is a quote; and who it falls on, which is the inclusion column of your backlog. An illustrative finding, not from any pilot: "P2 and P4, both without JavaScript, submitted a blank title on their second edit (metrics.csv, P2 at 14:21:03 and 14:21:30, P4 at 15:02:11). P2 said 'I thought it had saved' (P2.md line 23). Falls on anyone using the plain path, which includes people on locked-down machines and some screen reader configurations." The confidence scores and the completion counts go in the finding for the task they belong to, and low confidence after a completed task is a finding about feedback in its own right.

Findings the log cannot see go in too: a participant who deleted the wrong task, a participant who never found Edit. Their denominators come from the notes, and they are not added to the logged errors, as Appendix I says.

Three findings is the minimum, each with a source a reader can open. A claim with no row and no line behind it is an impression, and goes in a section called Impressions, where nobody can mistake it for a finding.

9.6 Activity 5: prioritise against cost

Each finding becomes a backlog row, or updates a row the audit or the interviews already created, with evidence pointing at research/findings.md and the heading. Score the rows as Chapter 2 says. Then add what you could not add before you had measured anything: what a fix would cost, in files touched and in the checks it needs afterwards. A change to a template and its test is an afternoon. A change to the routes or the storage is a day, plus the parity table from Chapter 6 run again.

Rank the rows, highest score first and, within a score, lowest cost first. The top row is the change you make in Chapter 10. Under the ranking write one sentence for every row you are not fixing and why; a finding with a high score that needs a day stays on the backlog with that reason, and the reason is read by whoever picks the project up after you. A defect you could see, from the audit, and a defect you could only measure, from the pilots, sit in the same ranking. The method does not care which kind it is.

9.7 What to record

Commit research/findings.md and the updated backlog/backlog.csv. The findings file holds the Data section, the time-on-task table, the tool's output as you ran it, with the command and the commit of the metrics file it read, the findings, the impressions, and the ranking with its reasons. Do not edit research/metrics.csv. If a row is excluded, the finding says so and the row stays, because the chain in Chapter 11 is only as good as the data a reader can reopen.
