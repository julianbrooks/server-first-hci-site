3  Inline edit

By the end a task can be renamed in place by mouse, by keyboard and by screen reader, with one route serving both the HTMX partial and the full page.

Before you start, commit your work from Chapter 1 and check out week-07-lab1; git describe --tags prints the tag name when you are on it. Have a screen reader you can start (Appendix E says how for Windows, macOS and Linux) and keep Appendix D open for the attributes.

Inline edit is the pattern where a row turns into a form and back again without leaving the page. It is harder to get right than add or delete because a row now has three states, viewing, editing and editing with an error, and each of them has to work in both modes and keep the keyboard focus somewhere sensible. The tag has the finished feature; this chapter reads it, then checks it with a mouse, a keyboard and a screen reader. If you would rather build it than read it, start from week-06, take the tests from this tag with git checkout week-07-lab1 -- src/test, and use the code below as the target.

3.1 Activity 1: two templates for one row

A row in view mode is _item.peb. At this tag it has three controls.

src/main/resources/templates/tasks/_item.peb
<li id="task-{{ task.id }}" class="task{% if task.completed %} task-done{% endif %}">
  <span class="task-title" id="task-title-{{ task.id }}">{{ task.title }}</span>
  {% if task.completed %}<span class="task-state">Done</span>{% endif %}
  <div class="task-actions">
    <form action="/tasks/{{ task.id }}/toggle" method="post"
          hx-post="/tasks/{{ task.id }}/toggle" hx-target="#task-{{ task.id }}" hx-swap="outerHTML">
      <button type="submit" class="secondary" aria-describedby="task-title-{{ task.id }}">
        {% if task.completed %}Mark not done{% else %}Mark done{% endif %}
      </button>
    </form>
    <form action="/tasks" method="get"
          hx-get="/tasks/{{ task.id }}/edit" hx-target="#task-{{ task.id }}" hx-swap="outerHTML">
      <input type="hidden" name="edit" value="{{ task.id }}">
      <button type="submit" class="secondary" aria-describedby="task-title-{{ task.id }}">Edit</button>
    </form>
    <form action="/tasks/{{ task.id }}/delete" method="post"
          hx-delete="/tasks/{{ task.id }}" hx-target="#task-{{ task.id }}" hx-swap="outerHTML"
          hx-confirm="Delete '{{ task.title }}'?">
      <button type="submit" class="secondary" aria-describedby="task-title-{{ task.id }}">Delete</button>
    </form>
  </div>
</li>

All three are buttons inside forms, so a person using a keyboard or a screen reader meets the same kind of control three times, and each button is described by the task title through aria-describedby. The Edit form is a GET with a hidden edit field: without JavaScript it lands on /tasks?edit=<id>, which is the list page with that one row in edit mode; with HTMX it fetches /tasks/<id>/edit and swaps the fragment over the <li>. The mark done form POSTs to /tasks/<id>/toggle and swaps the row back in with its new state; the button's text says which way the toggle will go.

A row in edit mode is _edit.peb.

src/main/resources/templates/tasks/_edit.peb
<li id="task-{{ task.id }}" class="task task-editing">
  <form action="/tasks/{{ task.id }}/edit" method="post"
        hx-post="/tasks/{{ task.id }}/edit" hx-target="#task-{{ task.id }}" hx-swap="outerHTML">
    <label for="title-{{ task.id }}">Title</label>
    <input type="text" id="title-{{ task.id }}" name="title" value="{{ editTitle }}" autofocus
           aria-describedby="hint-{{ task.id }}{% if editError %} error-{{ task.id }}{% endif %}"{% if editError %} aria-invalid="true"{% endif %}>
    <small id="hint-{{ task.id }}">Between {{ minTitleLength }} and {{ maxTitleLength }} characters.</small>
    {% if editError %}<p id="error-{{ task.id }}" class="error-message" role="alert">{{ editError }}</p>{% endif %}
    <div class="task-actions">
      <button type="submit">Save</button>
      <a href="/tasks" hx-get="/tasks/{{ task.id }}/view" hx-target="#task-{{ task.id }}" hx-swap="outerHTML">Cancel</a>
    </div>
  </form>
</li>

The <li> keeps the same id, so an outerHTML swap in either direction replaces exactly one row. The field has a visible label tied by for, and the label, hint and error all carry the task id so the ids stay unique when two rows are on the page. autofocus puts the cursor in the field: the browser does this on a full page load, and HTMX does it when it swaps in content that carries the attribute. After a failed save the field is marked aria-invalid="true" and the error paragraph is added to its aria-describedby, so a screen reader reads the error when the field is focused, and the paragraph has role="alert" so it is read when it appears. Cancel is a plain link to the list, enhanced with an hx-get that fetches the view row.

The list page chooses between the two.

src/main/resources/templates/tasks/index.peb
{% extends "_layout/base.peb" %}

{% block title %}Tasks{% endblock %}

{% block content %}
<h1>Tasks</h1>

{% include "tasks/_add_form.peb" %}

<section aria-labelledby="list-heading">
  <h2 id="list-heading">Your tasks</h2>
  <ul id="task-list" class="task-list">
    {% for task in tasks %}
      {% if editingId == task.id %}
        {% include "tasks/_edit.peb" with {"task": task} %}
      {% else %}
        {% include "tasks/_item.peb" with {"task": task} %}
      {% endif %}
    {% endfor %}
  </ul>
</section>
{% endblock %}

editingId is set only when the URL carries edit, so at most one row is a form.

3.2 Activity 2: four routes, each in two modes

src/main/kotlin/routes/TaskRoutes.kt
fun Route.configureTaskRoutes(store: TaskStore) {
    get("/") { call.seeOther("/tasks") }
    get("/tasks") { call.listTasks(store) }
    post("/tasks") { call.addTask(store) }
    get("/tasks/{id}/edit") { call.editTask(store) }
    post("/tasks/{id}/edit") { call.saveTask(store) }
    get("/tasks/{id}/view") { call.viewTask(store) }
    post("/tasks/{id}/toggle") { call.toggleTask(store) }
    // HTMX sends DELETE; a form without JavaScript can only POST, so delete has two routes.
    delete("/tasks/{id}") { call.deleteTask(store) }
    post("/tasks/{id}/delete") { call.deleteTask(store) }
}

listTasks now reads the form state out of the query string.

src/main/kotlin/routes/TaskRoutes.kt
/**
 * The list page. The query string carries form state after a redirect: `edit` opens one
 * task's edit form in place, `error` and `title` show a failed submission.
 */
private suspend fun ApplicationCall.listTasks(store: TaskStore) {
    val editingId = request.queryParameters["edit"]
    val error = request.queryParameters["error"]?.let(Task::messageFor)
    val title = request.queryParameters["title"]
    val formState =
        if (editingId == null) {
            mapOf("addError" to error, "addTitle" to title)
        } else {
            mapOf(
                "editingId" to editingId,
                "editError" to error,
                "editTitle" to (title ?: store.getById(editingId)?.title),
            )
        }
    respondHtml(renderTemplate("tasks/index.peb", listContext(store) + formState))
}

When edit is present the context carries the id, the error message if there is one, and the title to show in the field: the typed text after a failed save, otherwise the stored title. The error arrives as a code and is turned into a message by Task.messageFor, as in Chapter 1; the message itself never travels in a URL.

src/main/kotlin/routes/TaskRoutes.kt
/** HTMX gets the edit form in place of the item; without JavaScript the list page opens with that task in edit mode. */
private suspend fun ApplicationCall.editTask(store: TaskStore) {
    val task = store.getById(parameters["id"].orEmpty()) ?: return respond(HttpStatusCode.NotFound)
    if (isHtmxRequest()) {
        respondHtml(renderTemplate("tasks/_edit.peb", editContext(task, task.title)))
    } else {
        seeOther(tasksPath(edit = task.id))
    }
}

private suspend fun ApplicationCall.saveTask(store: TaskStore) {
    val task = store.getById(parameters["id"].orEmpty()) ?: return respond(HttpStatusCode.NotFound)
    val title = receiveParameters()["title"]?.trim().orEmpty()
    when (val result = Task.validate(title)) {
        is ValidationResult.Error ->
            if (isHtmxRequest()) {
                respondHtml(
                    renderTemplate("tasks/_edit.peb", editContext(task, title, result.message)) +
                        renderStatus(result.message, isError = true),
                )
            } else {
                seeOther(tasksPath(edit = task.id, error = result.code, title = title))
            }
        ValidationResult.Success -> {
            val updated = task.copy(title = title)
            store.update(updated)
            if (isHtmxRequest()) {
                respondHtml(renderTemplate("tasks/_item.peb", itemContext(updated)) + renderStatus("Saved \"${updated.title}\"."))
            } else {
                seeOther(tasksPath())
            }
        }
    }
}

/** Cancel: HTMX swaps the item back in; without JavaScript the Cancel link is a plain link to the list. */
private suspend fun ApplicationCall.viewTask(store: TaskStore) {
    val task = store.getById(parameters["id"].orEmpty()) ?: return respond(HttpStatusCode.NotFound)
    if (isHtmxRequest()) {
        respondHtml(renderTemplate("tasks/_item.peb", itemContext(task)))
    } else {
        seeOther(tasksPath())
    }
}

private suspend fun ApplicationCall.toggleTask(store: TaskStore) {
    val updated = store.toggleComplete(parameters["id"].orEmpty()) ?: return respond(HttpStatusCode.NotFound)
    if (isHtmxRequest()) {
        val state = if (updated.completed) "done" else "not done"
        respondHtml(renderTemplate("tasks/_item.peb", itemContext(updated)) + renderStatus("Marked \"${updated.title}\" $state."))
    } else {
        seeOther(tasksPath())
    }
}

Read the four handlers against the templates. editTask answers an HTMX request with _edit.peb for that task, and a plain request with a redirect to /tasks?edit=<id>, so a bookmarked or pasted edit URL still opens the list in edit mode. saveTask validates with the same Task.validate the add form uses. On failure, HTMX gets the edit row again with the typed title and the error, plus the status fragment marked as an error; a browser gets a redirect that carries edit, the error code and the typed title, which listTasks renders back into the same form. On success both modes end with the row in view mode: a fragment and a status for HTMX, a redirect for the browser. viewTask is Cancel, and toggleTask flips completed and announces which way it went. Every message that names a title is text handed to _status.peb.

src/main/kotlin/routes/TaskRoutes.kt
/** Builds /tasks with only the query parameters that carry information. */
private fun tasksPath(edit: String? = null, error: String? = null, title: String? = null): String {
    val params =
        buildList {
            if (edit != null) add("edit=${edit.encodeURLParameter()}")
            if (error != null) add("error=${error.encodeURLParameter()}")
            if (title != null) add("title=${title.encodeURLParameter()}")
        }
    return if (params.isEmpty()) "/tasks" else "/tasks?" + params.joinToString("&")
}

private fun itemContext(task: Task): Map<String, Any?> = mapOf("task" to task.toPebbleContext())

private fun editContext(task: Task, title: String, error: String? = null): Map<String, Any?> =
    TITLE_LIMITS + itemContext(task) + mapOf("editTitle" to title, "editError" to error)

tasksPath builds every redirect, adding only the parameters that carry information, so the plain list is still /tasks.

3.3 Activity 3: check it three ways and in two modes

Start the server and add two tasks. With the mouse, press Edit on one, change the title, press Save: the row swaps back and the status box says it was saved. Press Edit again and Cancel: the original row returns, unchanged. Blank the field and Save: the row stays a form, the field has a red border, the message is under it, and the status box repeats the message.

Now the keyboard. Press Tab from the address bar until the first Edit button has focus and press Enter. Focus should land in the title field with the cursor in it; if it lands nowhere and you are back at the top of the page, the response was a full page rather than the fragment, which means the request went out without the header. Type a title and press Enter: a form with one text field submits on Enter, so Save needs no click. Tab to Cancel and press Enter; Tab to Mark done and press Space.

Then the screen reader. Navigate to the Edit button: you should hear "Edit" and the task title, from aria-describedby. Press it and listen: the field announces as "Title", an edit field, with the hint. Blank it and save: you should hear the message twice, once as the alert appears and once as the status region changes. Save a valid title: you should hear it was saved. Write down what you heard at each of the three points; a screen reader that stays silent at one of them is a finding, and Chapter 4 says what to do with it. If the error is read when it appears but not when you return to the field, the id in aria-describedby and the id on the paragraph disagree.

Last, the other mode. From a second terminal, with <id> copied from a row's id attribute in the page source:

curl -i http://localhost:8080/tasks/<id>/edit
curl -i -d 'title=' http://localhost:8080/tasks/<id>/edit

The first prints a 303 whose Location is /tasks?edit=<id>; the second a 303 whose Location ends error=blank_title&title=. Open each Location in the browser and you see the list page with that row as a form, the second with the error shown. Then switch JavaScript off (the click paths for two browsers are in Chapter 6) and go through the same three flows: Edit reloads the page with the row as a form, Save reloads it as a row, Cancel is a link back to the list, and the address bar shows the state at every step. If after a successful save the form is still open, the redirect carried edit; a success goes to tasksPath() with no arguments.

Two things about focus differ between the modes and are not defects. After an HTMX swap the focus is wherever the new markup puts it, here the field; after a reload the browser honours autofocus the same way, and the page scrolls to the top first. The focus was checked in both modes by driving a browser against the tag; the scroll was not. And a page can carry only one autofocus, which editingId guarantees.

3.4 What to record

Commit. Keep the three screen reader observations from Activity 3 in research/notes.md under a heading for this chapter, with the date and the screen reader's name and version, in the form "pressed Save with an empty field; heard: ...". Anything you expected to hear and did not becomes a backlog row with story_type set to observation and evidence set to own observation; the columns are in Chapter 2 and the criterion numbers are in Chapter 4.
