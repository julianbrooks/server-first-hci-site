5  Partials and pagination

By the end the list is built from partials, paginated and filterable, and each of those views has a URL that works without JavaScript.

Before you start, commit your work and check out week-08. If Page is unresolved when you build, you are not on it. Keep Appendix C open for the include syntax, and give the list something to page through: with the server running, add fifteen tasks from a second terminal.

for i in $(seq 1 15); do curl -s -o /dev/null -d "title=Task $i" http://localhost:8080/tasks; done

A list of a dozen tasks is fine as one page. A list of a hundred is not: a person using a screen reader walks it row by row, and everyone scrolls. A filter and pages cut the list down, and both have to produce a URL, because a view you cannot bookmark, share or reach with JavaScript off is a view that exists only while the script is running.

5.1 Activity 1: the page in parts

The row template _item.peb is unchanged in shape from Chapter 3; what is new is that the list around it is now two more partials. _list.peb renders one page of rows.

src/main/resources/templates/tasks/_list.peb
<ul id="task-list" class="task-list" aria-describedby="result-count">
  {% for task in page.items %}
    {% if editingId == task.id %}
      {% include "tasks/_edit.peb" with {"task": task, "pageNumber": page.currentPage} %}
    {% else %}
      {% include "tasks/_item.peb" with {"task": task, "pageNumber": page.currentPage} %}
    {% endif %}
  {% endfor %}
</ul>
<p id="result-count">
  {% if page.totalItems == 0 %}
    No tasks{% if query %} match "{{ query }}"{% endif %}.
  {% else %}
    Showing {{ page.items | length }} of {{ page.totalItems }}{% if query %} matching "{{ query }}"{% endif %}.
  {% endif %}
</p>

The <ul> is described by the paragraph after it, so a screen reader that lands on the list hears how many rows it holds and whether a filter is on. The empty case is a sentence in that paragraph rather than a fake row. _pager.peb renders the page controls, and renders nothing when there is one page.

src/main/resources/templates/tasks/_pager.peb
{% if page.totalPages > 1 %}
<nav class="pager" aria-label="Pages">
  <ul>
    {% if page.currentPage > 1 %}
    <li><a href="/tasks?q={{ query | urlencode }}&page={{ page.currentPage - 1 }}"
           hx-get="/tasks?q={{ query | urlencode }}&page={{ page.currentPage - 1 }}"
           hx-target="#task-area" hx-push-url="true">Previous</a></li>
    {% endif %}
    <li aria-current="page">Page {{ page.currentPage }} of {{ page.totalPages }}</li>
    {% if page.currentPage < page.totalPages %}
    <li><a href="/tasks?q={{ query | urlencode }}&page={{ page.currentPage + 1 }}"
           hx-get="/tasks?q={{ query | urlencode }}&page={{ page.currentPage + 1 }}"
           hx-target="#task-area" hx-push-url="true">Next</a></li>
    {% endif %}
  </ul>
</nav>
{% endif %}

Each link carries two sets of attributes again: an href with the query and the page number for the browser, and an hx-get with the same URL for HTMX. aria-current="page" marks the current position. The query is passed through urlencode because it goes into a URL, not into text.

index.peb puts the filter form above them and wraps list and pager in one element.

src/main/resources/templates/tasks/index.peb
{% extends "_layout/base.peb" %}

{% block title %}Tasks{% endblock %}

{% block content %}
<h1>Tasks</h1>

{% include "tasks/_add_form.peb" %}

<section aria-labelledby="filter-heading">
  <h2 id="filter-heading">Filter</h2>
  {# Typing filters the list after a 300 ms pause. The button does the same without JavaScript. #}
  <form action="/tasks" method="get" role="search"
        hx-get="/tasks" hx-target="#task-area" hx-push-url="true"
        hx-trigger="input changed delay:300ms from:#filter-input, submit">
    <label for="filter-input">Show tasks whose title contains</label>
    <input type="search" id="filter-input" name="q" value="{{ query }}" autocomplete="off">
    <button type="submit">Filter</button>
  </form>
</section>

<section aria-labelledby="list-heading">
  <h2 id="list-heading">Your tasks</h2>
  {# hx-history-elt: HTMX saves and restores this element when the back button returns to a pushed URL. #}
  <div id="task-area" hx-history-elt>
    {% include "tasks/_list.peb" %}
    {% include "tasks/_pager.peb" %}
  </div>
</section>
{% endblock %}

The filter is a GET form with a visible button, which is the whole of its no-JavaScript behaviour. hx-trigger adds the typing: input changed delay:300ms from:#filter-input fires after a pause in typing and only when the value has changed, and submit keeps the button working with the script on. #task-area is the target every list request swaps into, and hx-history-elt tells HTMX this is the element to save and restore when the back button returns to a pushed URL.

One source for the row markup is what makes the two modes stay equal. _item.peb is included by _list.peb, and _list.peb is rendered both into the page and as the fragment, so a change to a button's label or an aria-describedby lands in both modes at once. The 2025 version of this application had a separate fragment route with its own copy of the list markup, and the copies drifted.

5.2 Activity 2: a page of tasks

src/main/kotlin/utils/Pagination.kt
package utils

/**
 * One page of a list. Pages are numbered from 1. [paginate] clamps the requested page
 * into range, so a page number that no longer exists shows the last page rather than
 * an error.
 */
data class Page<T>(
    val items: List<T>,
    val currentPage: Int,
    val totalPages: Int,
    val totalItems: Int,
) {
    fun toPebbleContext(): Map<String, Any> =
        mapOf(
            "items" to items,
            "currentPage" to currentPage,
            "totalPages" to totalPages,
            "totalItems" to totalItems,
        )

    companion object {
        const val DEFAULT_SIZE = 10

        fun <T> paginate(items: List<T>, requestedPage: Int, pageSize: Int = DEFAULT_SIZE): Page<T> {
            require(pageSize > 0) { "pageSize must be positive" }
            val totalPages = maxOf(1, (items.size + pageSize - 1) / pageSize)
            val current = requestedPage.coerceIn(1, totalPages)
            val from = (current - 1) * pageSize
            val to = minOf(from + pageSize, items.size)
            val pageItems = if (from < items.size) items.subList(from, to) else emptyList()
            return Page(pageItems, current, totalPages, items.size)
        }
    }
}

Page<T> is one page of any list. paginate clamps the requested number into range, so a page number that no longer exists, because the tasks on it were deleted, shows the last page rather than an error. toPebbleContext is the shape templates see; the page size lives in one constant and no template states it.

listTasks is now one route with two answers.

src/main/kotlin/routes/TaskRoutes.kt
/**
 * The list. A full page, or just the list and pager when HTMX is filtering or paging.
 * The query string also carries form state after a redirect: `edit` opens one task's
 * edit form in place, `error` and `title` show a failed submission.
 */
private suspend fun ApplicationCall.listTasks(store: TaskStore) {
    val query = request.queryParameters.query()
    val view = ListView.from(store, query, request.queryParameters.page())
    // The same URL returns a fragment or a page depending on this header, so caches must not mix them.
    response.headers.append(HttpHeaders.Vary, "HX-Request")
    if (isHtmxRequest()) {
        val found = view.page.totalItems
        val status = if (query.isEmpty()) "" else "$found ${plural(found, "task")} ${if (found == 1) "matches" else "match"} \"$query\"."
        respondHtml(renderTaskArea(view) + renderStatus(status))
    } else {
        val editingId = request.queryParameters["edit"]
        val error = request.queryParameters["error"]?.let(Task::messageFor)
        val title = request.queryParameters["title"]
        val formState =
            if (editingId == null) {
                mapOf("addError" to error, "addTitle" to title)
            } else {
                mapOf(
                    "editingId" to editingId,
                    "editError" to error,
                    "editTitle" to (title ?: store.getById(editingId)?.title),
                )
            }
        respondHtml(renderTemplate("tasks/index.peb", view.context + formState))
    }
}

With HX-Request set it renders _list.peb and _pager.peb and a status that announces the match count; without it, the whole page with the form state from the query string as in Chapter 3. The Vary: HX-Request header is on both answers: it tells any cache between the server and the browser that the response depends on that header, so a fragment is never served to a browser that asked for the page. The two helpers under the route are where the query string is read.

src/main/kotlin/routes/TaskRoutes.kt
/** The page of tasks the list templates show, newest first, and the filter that produced it. */
private class ListView(val page: Page<Map<String, Any>>, val query: String) {
    val context: Map<String, Any?>
        get() = TITLE_LIMITS + mapOf("page" to page.toPebbleContext(), "query" to query)

    companion object {
        fun from(store: TaskStore, query: String, pageNumber: Int): ListView {
            val tasks = store.search(query).asReversed().map { it.toPebbleContext() }
            return ListView(Page.paginate(tasks, pageNumber), query)
        }
    }
}

/** The filter and page a form was submitted from, carried in hidden fields so the person returns to the same place. */
private data class Place(val query: String, val pageNumber: Int) {
    val context: Map<String, Any?>
        get() = mapOf("query" to query, "pageNumber" to pageNumber)

    fun path(edit: String? = null, error: String? = null, title: String? = null) =
        tasksPath(query, pageNumber, edit, error, title)
}

private val TITLE_LIMITS = mapOf("minTitleLength" to Task.MIN_TITLE_LENGTH, "maxTitleLength" to Task.MAX_TITLE_LENGTH)

private fun Parameters.place() = Place(query(), page())

private fun Parameters.query() = this["q"]?.trim().orEmpty()

private fun Parameters.page() = this["page"]?.toIntOrNull()?.takeIf { it > 0 } ?: 1

/** Builds /tasks with only the query parameters that carry information. */
private fun tasksPath(query: String = "", page: Int = 1, edit: String? = null, error: String? = null, title: String? = null): String {
    val params =
        buildList {
            if (edit != null) add("edit=${edit.encodeURLParameter()}")
            if (error != null) add("error=${error.encodeURLParameter()}")
            if (title != null) add("title=${title.encodeURLParameter()}")
            if (query.isNotEmpty()) add("q=${query.encodeURLParameter()}")
            if (page > 1) add("page=$page")
        }
    return if (params.isEmpty()) "/tasks" else "/tasks?" + params.joinToString("&")
}

ListView is the page of tasks and the filter that produced it. Place is the filter and page a form was submitted from, so that an edit, a toggle or a delete on page 3 of a filtered list returns you to page 3 of that filtered list rather than to the top of everything. Every form in _item.peb carries the place in hidden fields.

src/main/resources/templates/tasks/_item.peb
<li id="task-{{ task.id }}" class="task{% if task.completed %} task-done{% endif %}">
  <span class="task-title" id="task-title-{{ task.id }}">{{ task.title }}</span>
  {% if task.completed %}<span class="task-state">Done</span>{% endif %}
  <div class="task-actions">
    <form action="/tasks/{{ task.id }}/toggle" method="post"
          hx-post="/tasks/{{ task.id }}/toggle" hx-target="#task-{{ task.id }}" hx-swap="outerHTML">
      <input type="hidden" name="q" value="{{ query }}">
      <input type="hidden" name="page" value="{{ pageNumber }}">
      <button type="submit" class="secondary" aria-describedby="task-title-{{ task.id }}">
        {% if task.completed %}Mark not done{% else %}Mark done{% endif %}
      </button>
    </form>
    <form action="/tasks" method="get"
          hx-get="/tasks/{{ task.id }}/edit" hx-target="#task-{{ task.id }}" hx-swap="outerHTML">
      <input type="hidden" name="edit" value="{{ task.id }}">
      <input type="hidden" name="q" value="{{ query }}">
      <input type="hidden" name="page" value="{{ pageNumber }}">
      <button type="submit" class="secondary" aria-describedby="task-title-{{ task.id }}">Edit</button>
    </form>
    <form action="/tasks/{{ task.id }}/delete" method="post"
          hx-delete="/tasks/{{ task.id }}" hx-target="#task-area" hx-confirm="Delete '{{ task.title }}'?">
      <input type="hidden" name="q" value="{{ query }}">
      <input type="hidden" name="page" value="{{ pageNumber }}">
      <button type="submit" class="secondary" aria-describedby="task-title-{{ task.id }}">Delete</button>
    </form>
  </div>
</li>

tasksPath adds only the parameters that carry information, so the plain list is still /tasks and a filtered first page is /tasks?q=report. The delete form now targets #task-area rather than its own row, so that deleting the last row on a page redraws the page count instead of leaving a page with nothing on it; Chapter 6 has the delete handler.

5.3 Activity 3: the pushed URL is a real URL

Type a few letters into the filter and wait. The list changes without a reload, the status box says how many tasks match, and the address bar now reads /tasks?q= and what you typed. That is hx-push-url="true": HTMX pushes the URL it requested into the browser history. Press Next and the address bar reads page=2 as well.

Now press the browser's reload button. You get the whole page, with the filter field filled in and page 2 showing. That works only because GET /tasks?q=...&page=2 answers a plain request with the full page and an HTMX request with the fragment: the same URL, two answers, told apart by the header. The 2025 version of this code fetched its fragments from a separate /tasks/fragment route, so the URL HTMX pushed was that one, and reloading it showed a bare list with no layout. One URL for both answers is what makes the pushed URL real.

Press Back. HTMX restores the saved #task-area from its history cache; when the cache has nothing, it requests the URL again with HX-History-Restore-Request: true, and isHtmxRequest() in Chapter 1 treats that as a request for the whole page. Copy the URL into a new tab, and it opens the same view.

Check the mechanics in the Network tab. A filter request shows HX-Request: true among the request headers and Vary: HX-Request among the response headers, and its response is a <ul> followed by a <nav> and the status <div>, with no <html>. If a request goes out on every keystroke, the delay or changed modifier is missing from hx-trigger. If typing sends nothing and only the button works, from:#filter-input names an id that is not on the field. If the status says that zero tasks match after you clear the field, the handler is announcing a count for an empty query.

Then switch JavaScript off (Chapter 6 has the click paths) and do the same: type, press Filter, and the page reloads with ?q= in the address bar; Previous and Next are links and reload the page; Edit on page 2 of a filtered list and Save brings you back to page 2 of that list, because the hidden fields carried the place through the redirect. The footer says which mode you are in.

5.4 What to record

Commit. Record the URL of three views, a filtered list, a second page, and a row in edit mode on a filtered page, with a screenshot of each working with JavaScript off, as Appendix J says. Anything that did not work in one of the modes is a backlog row with evidence set to own observation.
