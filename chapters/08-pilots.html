8  Pilots

By the end you have run four pilot sessions with consenting participants, each in both modes, and you have a metrics file and a set of notes that Chapter 9 can work from.

Before you start, you need the plan and seed data from Chapter 7 and a dry run that passed; the participant information sheet from Appendix G and the consent form from Appendix H, copied into research/ with the blanks filled from your institution's page; and four people from outside your pair who have agreed to give you twenty minutes each.

8.1 What four people can tell you

Every participant does the same tasks twice, once with HTMX and once with JavaScript off, and the comparison is between a person's two passes rather than between two groups of people. This is a within-subject design. It uses each participant twice, which with four of them matters, and it removes the largest source of noise, that people differ from each other far more than the two modes do. It brings one problem of its own: the second pass is always easier, because the participant has just done the tasks. Counterbalancing halves that problem. P1 and P3 start with HTMX, P2 and P4 start without JavaScript, so that each mode is first for two people. It does not remove it, and with two people per order you cannot separate the order effect from the mode effect; say so when you report.

What the design supports is a descriptive comparison: for each participant, the time on task and the errors in each mode, side by side, and then how many of the four were faster or made fewer errors in which mode and by how much. It supports the observation that a failure happened in front of you, which is enough to put it on the backlog. It does not support a claim about people in general, and it does not support a hypothesis test; with four participants a p-value is theatre, and this book does not compute one. Appendix I says how to write the comparison up.

8.2 Activity 1: prepare the room

Start the server, copy research/seed-tasks.csv to data/tasks.csv, and delete data/metrics.csv if it holds anything from the dry run; the first request writes a fresh file. Have the application open in a browser with no other tabs, DevTools closed, and the bookmarks bar hidden. Work in pairs: one of you facilitates and one takes notes, and you swap between sessions. Have research/plan.md open where the facilitator can read from it and a file research/pilots/P1.md open where the note-taker can type.

Start research/consent-log.md with one line per participant: pseudonym, date, which mode they did first, and that consent was given. Nothing else about them goes in it.

8.3 Activity 2: run a session

Hand the participant the information sheet and give them time to read it. Then the facilitator says, in their own words, something of this length:

"Thanks for doing this. We are testing the task list, not you, so there is nothing you can get wrong. I will read you a few short tasks and you do them; I will not help, but you can stop at any point. The server records what it does, under the code P1 rather than your name, and my partner is taking notes. Nothing is recorded or filmed. Are you happy to go ahead?"

The participant initials the consent form, you write the pseudonym and the date on it, and the form goes in the folder, not in the repository. Set the sid cookie to the pseudonym as in Chapter 7 and check that the footer shows it. Set the mode for the first pass the way the same chapter describes, and check the footer again.

Give the participant a minute with the list before the first task, untimed. Then, for each task, read the scenario from the plan once, and watch. The note-taker writes the time the scenario was read, what the participant did first, every hesitation of more than a few seconds and what they were looking at during it, anything they said, word for word where you can, whether they noticed the status message or the redirected page, and whether the task was completed, not completed, or completed after help. When the participant says they have finished, or the time limit passes, ask one question: "On a scale of one to five, how confident are you that that worked?" Write the number down with the task code. Then the next task.

Do not help. If the participant is stuck, let them be stuck; where they look and what they try is the finding. After about two minutes, ask "what are you looking for?", which tells you what they expected without telling them where it is. If they are still stuck, say "let's move to the next task" and record the task as not completed, with the reason. If they are frustrated rather than stuck, offer to stop. A participant who wants to leave, leaves, and their rows stay in the log unless they ask for them to go.

Between the passes, switch the mode, reload, check the footer, and tell the participant that the page will now work slightly differently. Run the same tasks in the same order. The second pass is faster for everyone; that is the order effect, and it is why half your participants did this pass first.

8.4 Activity 3: debrief

Ask three questions and write the answers down as said: which task was hardest and why; whether anything surprised them or did not do what they expected; and whether there was a moment when they were not sure something had worked. If they used the keyboard alone or a screen reader, ask whether anything was unreachable. Do not explain the design or defend it; if they ask why something works the way it does, say you will tell them after the last session. Thank them, remind them that they can ask for their rows to be deleted by quoting the pseudonym, and show them where that is written on the information sheet.

8.5 Activity 4: check the log before they leave

While the participant is still there, open data/metrics.csv and look at the rows for their pseudonym. There should be rows in both modes, the number of validation_error rows should match the errors the note-taker saw, and every task in the plan should have the row the plan said would mark its end. If a task has no row, do not ask the participant to repeat it; a repeat would be a third pass and not the same measurement. Note what is missing in research/pilots/P1.md and keep the note-taker's record of that task instead. If the rows carry six hex characters instead of the pseudonym, the cookie was never set; the timestamps will still let you attribute them, so write the start and end times of the session in the notes now and set the cookie for the next person before they sit down.

Reset for the next participant: copy the seed tasks back, set the cookie to the next pseudonym, set the mode for their first pass.

8.6 What to record

When the fourth session is done, copy data/metrics.csv to research/metrics.csv and commit it with research/pilots/P1.md to P4.md and research/consent-log.md. The metrics file holds pseudonyms and timings and nothing else, and Appendix F says why that can go in the repository when the consent forms cannot. Read the notes for names before committing; a participant who said "I'd do it the way Sam does" has named someone, and the name comes out.

Write one paragraph at the end of each participant's notes on what went wrong procedurally: a cookie set late, a task read twice, a server restarted. Chapter 9 reads those paragraphs before it reads the numbers.

8.7 Further reading

Nielsen's argument for five participants in a formative test is the source of the small-sample tradition this chapter sits in, and worth reading for what it does and does not claim (Nielsen, 2012). The W3C's page on involving people with disabilities in evaluation is short and says what to do when a participant uses assistive technology (W3C Web Accessibility Initiative, 2021).

Nielsen, J. (2012) “How many test users in a usability study?” Nielsen Norman Group. Available at: https://www.nngroup.com/articles/how-many-test-users/ (Accessed: October 4, 2026).
W3C Web Accessibility Initiative (2021) “Involving users in evaluating web accessibility.” Available at: https://www.w3.org/WAI/test-evaluate/involving-users/ (Accessed: October 4, 2026).
