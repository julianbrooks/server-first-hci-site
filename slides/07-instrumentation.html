Measuring rather than asking

  • Every request the application handles writes one row to a metrics file
  • The log sees that a request arrived, what for, whether it succeeded, how long the server took, and when
  • It does not see the participant read the screen, hesitate, look for a button, or say "did that work?"
  • Those come from the person sitting next to the participant with a notebook

The server log is a narrow instrument and the chapter is honest about what it cannot see. It records requests, not people. The notebook records the rest, and the analysis chapter puts the two halves together; the plan you write today says which errors you expect from each.

Write the evaluation plan

  • research/plan.md: the tasks, the measures, and the design of the sessions
  • A task is a scenario you can read aloud: "find every task about the quarterly report; use the filter and tell me how many there are"
  • Each task carries one of the codes in utils/TaskCodes.kt
  • The metrics record the code and nothing else about the task, so the plan is the place that says what T1_filter meant
  • Choose three to five of filter, edit, add, delete and mark done

A task is something a participant is asked to do, written as a scenario rather than an instruction, so that where they look and what they try is the finding. The code is the join between the plan and the log. The list page load has its own code and is not a task anyone is asked to do; it appears in the log after every redirect.

The task codes

src/main/kotlin/utils/TaskCodes.kt
object TaskCodes {
    const val LIST = "T0_list"
    const val FILTER = "T1_filter"
    const val EDIT = "T2_edit"
    const val ADD = "T3_add"
    const val DELETE = "T4_delete"
    const val TOGGLE = "T5_toggle"

    val all = listOf(LIST, FILTER, EDIT, ADD, DELETE, TOGGLE)
}

Six codes, stated here and nowhere else. The first is the page load and the redirects that follow a change without JavaScript. The other five are the participant tasks, and your plan uses three to five of them.

Success and error, written so a facilitator can see them

  • Success is something you can see or hear: the participant says "three", the new title is in the list, the task is gone
  • The log counts one kind of error on its own: a submission the server rejected, recorded as validation_error with the reason
  • Everything else, such as deleting the wrong task, succeeds as far as the server is concerned
  • Say in the plan which errors come from the log and which from the notes

Two definitions of error live side by side and must not be added together. The server knows about rejected submissions and nothing else; a participant who deletes the wrong task has, as far as the log is concerned, deleted a task. The plan says which is which so that the analysis chapter is not tempted to sum them.

Seed data, order, time, design

  • Decide the ten or so titles the list holds at the start of every session, so a scenario can name "Submit invoices"
  • Put delete last, because it is the destructive one
  • A time after which the facilitator moves on: two minutes is enough for any of these
  • Four participants, every one doing the tasks in both modes; two start with HTMX, two without
  • The comparison is within each participant

Seed data you control is what lets a scenario name a task and a participant find it. The order and the time limit are facilitation rules the pilots chapter relies on. The design section is short: the pilots chapter explains what it can and cannot support, and the plan only has to record it.

The schema, first half

src/main/kotlin/utils/Logger.kt
 * - `ts_iso`: when the row was written, UTC, ISO 8601, for example `2026-11-18T14:03:21.512Z`.
 * - `session_id`: the value of the `sid` cookie. A facilitator sets it to a participant
 *   code before a session; otherwise it is six random hex characters.
 * - `request_id`: `r_` followed by eight hex characters, unique to one request.
 * - `task_code`: one of the [TaskCodes] constants.
 * - `step`: `success`, `validation_error`, `client_error` or `server_error`.

The comment on LogEntry is the schema of the metrics file, and it is the only place in the code or the book where the columns are listed. The timestamp is UTC in ISO 8601. The session id is whatever the sid cookie holds, which is why a later activity sets that cookie to a participant code.

The schema, second half

src/main/kotlin/utils/Logger.kt
 * - `outcome`: `ok` for success; for a validation error the code from `Task.validate`
 *   (`blank_title`, `min_length`, `max_length`); for another error `http_` and the status,
 *   or the exception class name.
 * - `ms`: the server's time handling the request, in milliseconds. It is not time on task.
 *   Time on task is the gap between a participant's consecutive `ts_iso` values.
 * - `http_status`: the status code the server sent.
 * - `js_mode`: `htmx` when HTMX made the request, otherwise `nojs`.

Step and outcome carry the meaning of the row: success, or a validation error with the code from the model, or a client or server error with the status. The ms column is the server's time handling one request. The last column says which mode the request came from.

Two columns that are misread

  • ms is the time the server spent handling one request
  • It is not time on task
  • Time on task is the gap between a participant's consecutive timestamps
  • The 2025 version called ms "server-timed time-on-task", and that was wrong
  • session_id is whatever the sid cookie holds

The ms column measures the server, not the person, and a server takes tens of milliseconds for everything in this application. The number the analysis wants is the gap between one row and the next for the same participant, which is why the plan says which row marks the end of each task. The 2025 misreading produced tables of medians in the tens of milliseconds, which told nobody anything.

One request, one row

src/main/kotlin/utils/Timing.kt
        val ms = elapsedMs(started)
        val status = response.status()?.value ?: 200
        val validationOutcome = attributes.getOrNull(ValidationOutcomeKey)
        when {
            validationOutcome != null ->
                Logger.validationError(sessionCode, requestId, taskCode, validationOutcome, ms, status, jsMode)
            status >= 400 -> {
                val step = if (status >= 500) "server_error" else "client_error"
                Logger.write(LogEntry(sessionCode, requestId, taskCode, step, "http_$status", ms, status, jsMode))
            }
            else -> Logger.success(sessionCode, requestId, taskCode, ms, status, jsMode)
        }

Every route handler runs inside timed, which reads or sets the cookie, times the handler, and writes one row when it finishes. The row is a success, or a validation error when the handler reported one, or a client or server error from the status. The 2025 code logged a validation error and then a success for the same request and counted every failure twice; one request, one row, is what makes an error rate possible.

The add handler is wrapped in timed with its task code and mode, and the validation branch records the code before answering. It then answers differently in each mode, a fragment with the error for HTMX and a redirect for a plain form, and timed writes the validation error row either way with the status the server sent. Nothing about the response shape changes what is logged.

Truthful rather than tidy

  • A rejected submission is a 200 in HTMX mode and a 303 without JavaScript
  • The step and outcome columns carry the meaning
  • Do not change the routes to send 400 on validation errors so the column looks cleaner
  • HTMX 2 does not swap a 4xx response by default, and the participant would see nothing happen

The status column records what the server sent, and what it sent was decided in the parity chapter for reasons that still hold. The log is not the place to fix that; it is the place to record it. Anything that counts failures by status counts wrong, and the step column is there so that nothing has to.

Label a participant's session

  • The first visit sets a sid cookie to six random hex characters; every row from that browser carries them
  • Before a session, replace the value with the participant's pseudonym
  • In the browser console on a tab showing the application: document.cookie = "sid=P1; path=/", then reload
  • The footer shows the mode and the session code the next row will carry
  • The cookie is readable from JavaScript on purpose

Labelling is what lets the rows be told apart later and deleted on request. The check is the footer, which the route tests at this tag assert shows a sent code, and that the row carries it. The cookie is deliberately not HTTP-only, so that this one line in the console works.

Dry run both modes

  • ./gradlew run from the project root; the metrics file is written relative to where the server starts
  • Add your seed tasks through the form; copy data/tasks.csv to research/seed-tasks.csv
  • Delete data/metrics.csv, so the seeding does not sit in your data
  • Set the cookie to DRY1; work through your tasks with JavaScript on, including a two-letter title
  • Turn JavaScript off, reload, check the footer, and do it again

The dry run is the proof that the instrument works before anyone is timed with it. Starting the server from another directory puts the metrics file there, which is the first thing to check when the file seems not to exist. The two-letter title is there to produce one rejected submission on purpose.

Check three things

  • The js_mode column contains both htmx and nojs
  • The rejected title is one validation_error row with min_length in the outcome column, and no other row for that request
  • The session_id column reads DRY1 throughout
  • When the rows are right, delete the file again: the pilots start with an empty log

Three columns, three checks. If every row says nojs with JavaScript on, the HTMX script is not loading, and the footer will have told you so. When the rows are right the file is deleted, because the dry run is yours and the pilots' data must not contain it.

What goes wrong

  • The footer still shows six hex characters: the cookie was set in another tab's console, or the page was not reloaded; a missing path=/ is not the cause, since the browser defaults it
  • The footer shows the previous participant's code: two people's rows will merge under one pseudonym, which cannot be undone
  • The file does not exist: nothing has been requested since you deleted it, or the server runs from another directory
  • A line in the terminal with no row in the file: the handler is not inside timed(), which at this tag means the code has been edited

The first two are cookie mistakes and the footer catches both, which is why the chapter says to read it before every session. The third is the working directory. The fourth should not happen on an unedited tag; if it does, the diff from the tag is where to look.

What to record

  • Commit research/plan.md and research/seed-tasks.csv
  • Do not commit data/metrics.csv; the tag's .gitignore keeps it out
  • Under each task in the plan, one sentence saying which row in the log marks it as finished
  • For a filter in HTMX mode, the last T1_filter row before the participant answers; for an edit, the T2_edit row from the save, not from opening the form

The plan and the seed data are committed; the log is not, until the pilots chapter says what to keep of it. The sentence under each task is the one the analysis depends on, because the gap from the previous row to that one is the time on task. Decide it now, while the tasks are fresh, not when the data is in front of you.
