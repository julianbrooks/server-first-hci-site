Parity and validation

Server-First HCI

What you will have built

  • Every route validates its input on the server
  • Every HTMX interaction has a full-page equivalent
  • Both paths checked, flow by flow, in two browsers
  • The trade-offs written down

The last chapter built the views; this one checks that every one of them, and every form, behaves in both modes and records the result. Validation is read first because it is where the two paths differ most visibly. The record at the end is a table of flows in both modes and a list of what the two paths cost.

Before you start

  • Finish the last chapter on the week-08 tag
  • Two browsers to hand: Chrome or Edge, and Firefox
  • Your backlog open

Nothing new is checked out; this chapter reads the rest of the week-08 tag. Two browsers matter because they switch JavaScript off differently, and the pass is run in both. Every row that fails goes into the backlog, so have it open.

Validation lives on the server

  • The server is the only place both paths pass through
  • A required attribute would stop a blank title before the server saw it, in both modes
  • You would never see the server's error path, the one a person gets when the attribute is missing, the browser is old, or a script posts directly
  • The title fields carry no required on purpose; adding it is an enhancement to consider after the pilots

The 2025 version of this material presented server-side validation as a security boundary, which it is, but the reason this chapter gives is about testing. If the browser stops the blank title, you never exercise the path the server takes when the browser does not, and that path is the one that has to be right for everyone. The attribute can come later, as an enhancement, once the pilots have shown what people type.

The rules in one place

src/main/kotlin/model/Task.kt
        const val MIN_TITLE_LENGTH = 3
        const val MAX_TITLE_LENGTH = 100

        private val DISPLAY_FORMAT = DateTimeFormatter.ofPattern("yyyy-MM-dd HH:mm")

        /** Messages by validation code. The code is what a redirect carries and what the metrics record. */
        private val MESSAGES =
            mapOf(
                "blank_title" to "Enter a title.",
                "min_length" to "Title must be at least $MIN_TITLE_LENGTH characters.",
                "max_length" to "Title must be $MAX_TITLE_LENGTH characters or fewer.",
            )

The two limits are constants, and the messages are built from them, so a message cannot name a different number from the one the check uses. The validate function returns a code and a message: the code is what travels in a redirect and what the metrics record, and messageFor turns a code read back from a URL into its message, or nothing. The limits are also passed into every form's context, and the hint under each field reads them.

No template states a number

  • The limits reach every form as minTitleLength and maxTitleLength
  • The hint under each field reads them
  • The 2025 version had a hint that said one limit while the check enforced another
  • Participants found it by typing a title the hint allowed and the server refused
  • The fix was to remove every number from the templates, not to correct one

This is the one-place rule applied to code. The 2025 defect was not a wrong number; it was a second copy of a number, and the two copies drifted. The fix that lasts is the one that leaves a single copy.

The error summary

src/main/resources/templates/tasks/_add_form.peb
  {% if addError %}
  <div class="error-summary" role="alert" tabindex="-1" autofocus>
    <h3>There is a problem</h3>
    <ul>
      <li><a href="#task-title" id="add-error">{{ addError }}</a></li>
    </ul>
  </div>
  {% endif %}

The add form shows a failed submission as an error summary above the form, in the pattern the GOV.UK design system documents. The summary has role alert, so it is read when it appears; tabindex minus one and autofocus, so focus lands on it after a reload; and a link whose target is the field, so one key press moves you to the problem. The link's id is what the field's aria-describedby points at, so focusing the field reads the error as well as the hint.

The error branch

src/main/kotlin/routes/TaskRoutes.kt
    when (val result = Task.validate(title)) {
        is ValidationResult.Error ->
            if (isHtmxRequest()) {
                val view = ListView.from(store, place.query, place.pageNumber)
                respondHtml(
                    renderTaskArea(view) +
                        renderAddForm(view, title, result.message) +
                        renderStatus(result.message, isError = true),
                )
            } else {
                seeOther(tasksPath(place.query, place.pageNumber, error = result.code, title = title))
            }

In HTMX mode the response is the task area unchanged, the form out of band with the error in it, and the status marked as an error. In the other mode it is a redirect to the place the form was submitted from with the code and the typed title in the query string, and the list route renders the same form with the same error. The success branch returns to page one in both modes, because the new task is newest and newest is first.

200, not 4xx

  • HTMX 2 does not swap the body of a 4xx or 5xx response unless the page configures it to
  • A 422 with the form in its body would leave the page unchanged and the person none the wiser
  • Returning 200 and letting the markup carry the meaning is the smaller choice
  • A status code therefore no longer says whether a request succeeded
  • The metrics record the outcome, not the code

The 2025 material returned 400 on a validation error, and HTMX 2 would have shown the participant nothing. Configuring HTMX's response handling in the layout is possible but is one more thing to teach for the same screen. The consequence is carried forward to the instrumentation chapter: anything that counts failures by status counts wrong, so the log records a step and an outcome.

The edit form shows its error under the field rather than as a summary, because the form has one field and sits inside a list. The field is marked invalid and the error paragraph is added to its description, as in the last chapter. The Cancel link carries the filter and page in its href and its hx-get, so cancelling returns you to the place you were.

Delete, and the one thing the plain path cannot do

src/main/kotlin/routes/TaskRoutes.kt
    // HTMX 2 sends a DELETE's form fields in the query string; a plain form POSTs them in the body.
    val params = if (request.httpMethod == HttpMethod.Delete) request.queryParameters else receiveParameters()
    val place = params.place()
    val task = store.getById(parameters["id"].orEmpty()) ?: return respond(HttpStatusCode.NotFound)
    store.delete(task.id)
    if (isHtmxRequest()) {
        val view = ListView.from(store, place.query, place.pageNumber)
        respondHtml(renderTaskArea(view) + renderStatus("Deleted \"${task.title}\"."))
    } else {
        seeOther(place.path())
    }

HTMX 2 sends the fields of a form that triggers a DELETE in the query string, where HTMX 1 sent them in the body, and a plain form POSTs them in the body; the handler reads whichever the method implies, so the place survives either way. The delete form has hx-confirm, so with the script on a browser dialog asks before the request goes. With the script off there is no dialog, because a form submits when its button is pressed, and that gap goes on the list of costs.

Switch JavaScript off

  • Chrome or Edge: F12, then Ctrl-Shift-P (Cmd-Shift-P on a Mac), type "Disable JavaScript", Enter
  • It stays off while the developer tools are open and comes back when you close them
  • Firefox: about:config, accept the warning, search javascript.enabled, toggle to false
  • It stays off in every tab until you toggle it back
  • Reload the list: the footer reads "no JavaScript"

Two browsers, two mechanisms, and the difference matters when the footer disagrees with you. In Chrome the setting is tied to the developer tools window, so closing it turns the script back on. If the footer still reads HTMX after a reload, the script ran, which in Chrome means the developer tools were closed.

The pass: every flow, both modes

  • Add, and add with a blank title
  • Filter, and page
  • Edit, edit with a blank title, and cancel
  • Mark done
  • Delete

Nine flows, and the chapter's table says for each what to do and what you should see: the page reloads, the address bar carries the code or the page number, the summary takes focus, the typed text is kept. Do the action, then read the address bar and the page before the next one. Then switch the script back on and run the same table again.

Reading the Network tab

  • With the script off, every request is of type document
  • A request of type xhr or fetch means the script is running
  • The filter doing nothing while you type is correct: typing is the enhancement, the button is the baseline
  • A 405 in the server log: a form's method is wrong
  • A reload after an error loses the typed title: the redirect was built without it

The Network tab is the instrument for this pass. The request type tells you which mode you are in regardless of what the footer says, and the server log tells you when a form is pointed at the wrong method. The last two lines are the failures the chapter names next to the table.

What the two paths cost

  • Every handler has two branches and every behaviour has two tests; a change made in one branch and not the other is the most common defect in this codebase
  • The modes differ and cannot match: delete confirms only with the script on, and the announcement exists only with the script on
  • The status codes are not the whole truth
  • State travels in URLs, including the typed title, which lands in history and the server log

The chapter lists eight costs and asks you to copy them into your own parity record. The first is the one the tests exist for, because nothing else catches it. The last is a privacy point: a title is the person's own text, and the privacy appendix is about why that matters.

And the rest of the bill

  • The markup is longer: hidden q and page fields on every form, a plain attribute and an hx- one on every control
  • One URL with two answers needs Vary; a cache that ignores it serves a fragment as a page
  • The plain path is slower per action: a whole page each time
  • The hx- attributes and the header check are a second vocabulary on top of HTML and HTTP

None of these is hidden; each is visible in the templates and the routes you have read. The second vocabulary is the reason the HTMX patterns appendix exists. The slow plain path is the one participants will notice in the pilots, and the metrics will show it as a redirect followed by a second request.

What they buy

  • A page that works when the script does not load, is blocked or is off
  • One piece of HTML for the browser and the screen reader alike
  • The GOV.UK service manual requires it for services the public has no choice but to use
  • We think the costs are worth paying for an application like this one
  • For a drawing tool or a game they would not be, and saying so is part of the trade-off

This is a position, not a law. The book states it, gives the source for the public-sector case, and says where it would not apply. Your own parity record should do the same: the costs, the benefit, and the kind of application you are building.

What goes wrong

  • The footer still reads "HTMX" in Chrome: the developer tools were closed, so the script came back
  • A 405 in the log: a form's method is wrong
  • The typed title is gone after an error: the redirect was built without it
  • A change made in one branch of a handler and not the other, which only the tests catch

The first is the mechanism from the switching slide. The second and third are the two failures the chapter names next to the flow table. The fourth is why every behaviour has two tests, and why the regression checks later in the book are built from this chapter's table.
