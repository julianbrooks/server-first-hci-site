What you will have built

  • A working task list, cloned and read, with its one gap filled
  • Add and delete that work with JavaScript off
  • The same page enhanced with HTMX
  • One request header that tells the two modes apart

This session is a reading of the task list the rest of the book evaluates and redesigns, and then one piece of building. You clone the code, follow a request from the browser to the page, and implement delete in both modes. By the end the application adds and deletes tasks without JavaScript and does the same, with an announcement, when HTMX is running.

The server sends finished HTML

  • The browser shows the page without running a script
  • Every link and form works with JavaScript off
  • HTMX is a small script layered on top: fetch a fragment, swap it in
  • If the script fails to load, is blocked or is off, the page is still the page

The application sends the browser complete HTML, and the browser displays it as it is. HTMX is then added on top as a library, not a framework, that lets a form or link fetch a fragment of HTML and swap it into the page instead of reloading. The point to hold on to is the last line: when the script is absent for any reason, nothing is lost but the polish.

Why this book takes the position

  • The GOV.UK service manual requires progressive enhancement
  • Hypermedia Systems makes the longer argument
  • The narrower reason: the HTML the server sends is the HTML a screen reader reads
  • One place to get structure, labels and announcements right, and one place to check them

The chapter gives two sources for the position and one reason of its own. The sources are the GOV.UK service manual, which requires this way of building for government services, and the book Hypermedia Systems. The reason this book cares is narrower: a screen reader reads what the server sent, so there is one artefact to get right and one to test, rather than a server response and a client-side rendering that can disagree.

Two ways to reach every interaction

  • A plain form submission that ends in a redirect
  • An HTMX request that ends in a fragment
  • One request header tells them apart
  • Every handler answers both

Every interaction in the task list is reachable in two ways, and this pattern recurs in every chapter. The plain path is a form submission followed by a redirect; the enhanced path is a request HTMX makes, answered with a fragment of HTML. The server tells them apart by one header, and the rule of the codebase is that one handler serves both, so the two modes cannot drift apart.

Run it and follow a request

  • ./gradlew run, then open http://localhost:8080/tasks
  • Add a task
  • Watch the terminal print one line per request: method, path, status
  • Four files turn that request into the page

Start the server and add a task, and watch the terminal, which prints one line for every request the server handles. If the page is blank, a server from last time is still on the port; stop it with Ctrl-C in that terminal and run again. The rest of this part of the session reads the four files that turn the request into the page: the entry point, the templating, the layout and the list page.

The header check

src/main/kotlin/Templating.kt
/**
 * True when HTMX made the request and wants a fragment back. HTMX also sends HX-Request
 * when it restores a page from history, but then it expects the full page, so that case
 * returns false.
 */
fun ApplicationCall.isHtmxRequest(): Boolean =
    request.headers["HX-Request"] == "true" && request.headers["HX-History-Restore-Request"] != "true"

HTMX sends the header HX-Request with the value true on every request it makes, and a route that sees it returns a fragment. HTMX also sends the header when it restores a page from history, and then it wants the whole page back, which is why the second condition is there. This function is the only place the header is read; every route calls it rather than looking at the headers itself.

The one live region

src/main/resources/templates/_layout/base.peb
<body>
  {% include "_layout/_header.peb" %}
  <main id="main" class="container" tabindex="-1">
    {# The one live region on the page. Fragments update its content out of band through tasks/_status.peb. #}
    <div id="status" role="status" aria-live="polite" aria-atomic="true"></div>
    {% block content %}{% endblock %}
  </main>
  {% include "_layout/_footer.peb" %}
</body>

The layout every page extends has one live region, the div with role status. It is empty on load, which is correct for a region that announces later changes, and the fragments update its content out of band. The stylesheet and the HTMX script are served by this application rather than a CDN, because lab networks block CDNs.

The add form carries two sets of attributes

src/main/resources/templates/tasks/_add_form.peb
  <form action="/tasks" method="post" hx-post="/tasks" hx-target="#task-list" hx-swap="afterbegin">
    <label for="task-title">Title</label>
    <input type="text" id="task-title" name="title" value="{{ addTitle }}"
           aria-describedby="title-hint{% if addError %} add-error{% endif %}"{% if addError %} aria-invalid="true"{% endif %}>
    <small id="title-hint">Between {{ minTitleLength }} and {{ maxTitleLength }} characters.</small>
    {% if addError %}<p id="add-error" class="error-message" role="alert">{{ addError }}</p>{% endif %}
    <button type="submit" id="add-button">Add task</button>
  </form>

The form has action and method, which a browser uses, and hx-post, hx-target and hx-swap, which HTMX uses when its script is running. The label is tied to the field by for and the hint by aria-describedby. After a failed submission the field is marked aria-invalid and the error paragraph is added to its description, so a screen reader reads the error with the field.

Without JavaScript: POST, redirect, GET

  • addTask reads the title, validates it, saves it
  • Answers 303 See Other with Location: /tasks
  • The browser GETs the list; a refresh repeats the GET, not the POST
  • A failed validation redirects to /tasks?error=min_length&title=ab
  • An unknown error code renders nothing

With JavaScript off the browser posts the form and the handler answers with a redirect, so the browser fetches the list and shows the new task. A refresh now repeats the GET, which is what makes this pattern safe; nothing is submitted twice. A failed validation also redirects, with the error code and the typed text in the URL, and the list route turns the code back into a message. A code it does not recognise renders nothing, so a crafted URL cannot put text on the page.

With HTMX: three fragments in one body

  • The item, inserted at the start of #task-list
  • The add form, out of band, replacing #add-section
  • The status, out of band, into the live region
  • Same handler, same validation, different response

The same POST arrives with the header set, and the response is three fragments in one body. HTMX inserts the first where the form's hx-target and hx-swap say, and takes the other two out of the response because they carry hx-swap-oob, replacing the add section and the live region's content wherever those are on the page. After a failure the form comes back holding the typed title and the error, and the status carries the message.

The status fragment

src/main/resources/templates/tasks/_status.peb
{# Swapped into the live region in the layout. innerHTML keeps the region itself in place,
   which is what makes screen readers announce the change. #}
<div hx-swap-oob="innerHTML:#status">{% if message %}<span{% if error %} class="error"{% endif %}>{{ message }}</span>{% endif %}</div>

The swap is innerHTML into the status element, which puts the message inside the live region and leaves the region itself in place. Screen readers announce changes to a region that already exists; a region inserted with its message already inside is often not announced, and the 2025 version of this code made that mistake. This has been checked by reading the HTMX source and not yet with a screen reader on a lab machine, which is what the third activity is for.

Nothing builds HTML with a title in it

  • Every fragment, including the one-line status, is a template
  • renderStatus passes the message as text
  • autoEscaping(true) escapes every { value }
  • One test posts <b>bold</b> & "quoted" and checks it arrives as text

No line in the routes file concatenates a title into HTML; the title goes into a template context and the engine escapes it. That is what makes a hostile title arrive on the page as text, and the test named in the chapter posts one and checks the output. The two other engine settings matter too: templates are re-read on every request, so an edit shows without a restart.

Check both modes with curl

curl -i -d 'title=Buy milk' http://localhost:8080/tasks
curl -i -H 'HX-Request: true' -d 'title=Buy milk' http://localhost:8080/tasks
curl -i -d 'title=ab' http://localhost:8080/tasks

From a second terminal, with the server running, these three requests show the two shapes. The first prints a 303 with Location /tasks; the second prints 200 and a body that begins with a list item, continues with the add section marked out of band, and ends with the status div. The third is a 303 whose Location carries the error code and the typed title. The browser's Network tab shows the same two shapes.

The test that describes the HTMX delete

src/test/kotlin/routes/TaskRoutesTest.kt
    fun `DELETE as HTMX removes the task and returns only the status`() =
        withApp { store, client ->
            val task = Task(title = "Remove me").also(store::add)
            val response = client.delete("/tasks/${task.id}") { header(HTMX_HEADER, "true") }
            assertEquals(HttpStatusCode.OK, response.status)
            val body = response.bodyAsText()
            assertFalse(body.contains("<li"))
            assertContains(body, "Deleted &quot;Remove me&quot;.")
            assertNull(store.getById(task.id))

Read the assertions as a specification. The response to a DELETE with the header is 200, its body contains no list item, it contains the deletion message, and the task is gone from the store. The other test, for the plain path, expects a 303 to /tasks and the same absence from the store.

Build delete in both modes

  • In _item.peb, a form in the <li>: action="/tasks/{{ task.id }}/delete", method="post"
  • Plus hx-delete, hx-target="#task-{{ task.id }}", hx-swap="outerHTML"
  • The button gets aria-describedby="task-title-{{ task.id }}"
  • In TaskRoutes.kt, delete("/tasks/{id}") and post("/tasks/{id}/delete"), one handler
  • In HTMX mode respond with renderStatus and nothing else; otherwise seeOther(tasksPath())

A form without JavaScript can only GET or POST, so the plain path is a POST to a delete URL, while HTMX sends a real DELETE. Both routes call one handler, which looks the task up, answers 404 when there is none, deletes it, and branches on the header check. In HTMX mode there is no content for the target, so the outerHTML swap removes the row and the live region announces the deletion; in the other mode the handler redirects to the list.

What goes wrong

  • The test report says two tests were skipped: the @Disabled lines are still there
  • The HTMX test fails because the body contains <li: the handler returned the item too
  • The log shows DELETE /tasks/... - 405: only the POST route exists
  • The row stays until a reload: hx-target names an id that is not on the <li>
  • delete is unresolved: add the import beside get and post

These are the five failures the chapter names, and each has one cause. The skipped tests and the missing import are the first two things to check, because both look like the code is wrong when it is the scaffolding. The 405 means HTMX is sending DELETE and only the POST route is there; the row that stays until a reload means the swap had nowhere to go.
