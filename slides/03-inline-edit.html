Inline edit

Server-First HCI

What you will have built

  • A task that can be renamed in place
  • By mouse, by keyboard and by screen reader
  • One route serving both the HTMX partial and the full page
  • Three screen reader observations written down

Inline edit is the pattern where a row turns into a form and back again without leaving the page. The tag has the finished feature; this session reads it, then checks it with a mouse, a keyboard and a screen reader, in both modes. What you write down at the three listening points is the record the session produces.

Three states for one row

  • Viewing, editing, and editing with an error
  • Each works in both modes
  • Each keeps the keyboard focus somewhere sensible
  • Harder than add or delete for that reason

Add and delete have one state each. A row with inline edit has three, and every one of them has to work with the script on and off and leave the focus where a person can find it. That is why this chapter reads the finished code rather than building it under time pressure.

The row in view mode

src/main/resources/templates/tasks/_item.peb
    <form action="/tasks" method="get"
          hx-get="/tasks/{{ task.id }}/edit" hx-target="#task-{{ task.id }}" hx-swap="outerHTML">
      <input type="hidden" name="edit" value="{{ task.id }}">
      <button type="submit" class="secondary" aria-describedby="task-title-{{ task.id }}">Edit</button>
    </form>
    <form action="/tasks/{{ task.id }}/delete" method="post"
          hx-delete="/tasks/{{ task.id }}" hx-target="#task-{{ task.id }}" hx-swap="outerHTML"
          hx-confirm="Delete '{{ task.title }}'?">
      <button type="submit" class="secondary" aria-describedby="task-title-{{ task.id }}">Delete</button>
    </form>

Every control on the row is a button inside a form, so a person using a keyboard or a screen reader meets the same kind of control three times, and each button is described by the task title through aria-describedby. The Edit form is a GET with a hidden edit field: without JavaScript it lands on the list page with this row in edit mode, with HTMX it fetches the edit fragment and swaps it over the row. The delete form is the one you built, with a confirmation that only the script can show.

The row in edit mode

src/main/resources/templates/tasks/_edit.peb
  <form action="/tasks/{{ task.id }}/edit" method="post"
        hx-post="/tasks/{{ task.id }}/edit" hx-target="#task-{{ task.id }}" hx-swap="outerHTML">
    <label for="title-{{ task.id }}">Title</label>
    <input type="text" id="title-{{ task.id }}" name="title" value="{{ editTitle }}" autofocus
           aria-describedby="hint-{{ task.id }}{% if editError %} error-{{ task.id }}{% endif %}"{% if editError %} aria-invalid="true"{% endif %}>
    <small id="hint-{{ task.id }}">Between {{ minTitleLength }} and {{ maxTitleLength }} characters.</small>
    {% if editError %}<p id="error-{{ task.id }}" class="error-message" role="alert">{{ editError }}</p>{% endif %}
    <div class="task-actions">
      <button type="submit">Save</button>
      <a href="/tasks" hx-get="/tasks/{{ task.id }}/view" hx-target="#task-{{ task.id }}" hx-swap="outerHTML">Cancel</a>
    </div>
  </form>

The list item keeps the same id, so an outerHTML swap in either direction replaces exactly one row. The field has a visible label tied by for, and the label, hint and error all carry the task id so the ids stay unique when two rows are on the page. Cancel is a plain link to the list, enhanced with an hx-get that fetches the view row.

What the edit row does for focus and errors

  • autofocus puts the cursor in the field: the browser on a page load, HTMX on a swap
  • After a failed save the field is aria-invalid="true"
  • The error paragraph is added to the field's aria-describedby
  • The paragraph has role="alert", so it is read when it appears

Two mechanisms carry the error to a screen reader. The alert role reads the message when the paragraph appears, and the description reads it again when the field is focused. Both depend on the ids matching, which is the usual thing that breaks.

The list page chooses

  • editingId is set only when the URL carries edit
  • At most one row is a form
  • A page can carry only one autofocus, which this guarantees

The list template includes the edit row for the one task whose id matches and the view row for every other. The id comes from the query string, so a bookmarked or pasted edit URL opens the list with that row as a form. The one-autofocus rule falls out of this for free.

Four routes, each in two modes

src/main/kotlin/routes/TaskRoutes.kt
fun Route.configureTaskRoutes(store: TaskStore) {
    get("/") { call.seeOther("/tasks") }
    get("/tasks") { call.listTasks(store) }
    post("/tasks") { call.addTask(store) }
    get("/tasks/{id}/edit") { call.editTask(store) }
    post("/tasks/{id}/edit") { call.saveTask(store) }
    get("/tasks/{id}/view") { call.viewTask(store) }
    post("/tasks/{id}/toggle") { call.toggleTask(store) }
    // HTMX sends DELETE; a form without JavaScript can only POST, so delete has two routes.
    delete("/tasks/{id}") { call.deleteTask(store) }
    post("/tasks/{id}/delete") { call.deleteTask(store) }
}

Four routes are new since the last tag: open the edit form, save it, cancel back to the view row, and toggle done. Each has one handler that branches on the header check, so the two modes cannot drift apart. Delete is the pair of routes you added, calling one handler.

Opening the form

src/main/kotlin/routes/TaskRoutes.kt
private suspend fun ApplicationCall.editTask(store: TaskStore) {
    val task = store.getById(parameters["id"].orEmpty()) ?: return respond(HttpStatusCode.NotFound)
    if (isHtmxRequest()) {
        respondHtml(renderTemplate("tasks/_edit.peb", editContext(task, task.title)))
    } else {
        seeOther(tasksPath(edit = task.id))
    }
}

An HTMX request gets the edit row for that task. A plain request gets a redirect to the list with edit in the query string, so the list page renders with that row as a form. A task that is not there is a 404 in either mode, and the status page handler turns that into the 404 page.

Saving, when validation fails

src/main/kotlin/routes/TaskRoutes.kt
    when (val result = Task.validate(title)) {
        is ValidationResult.Error ->
            if (isHtmxRequest()) {
                respondHtml(
                    renderTemplate("tasks/_edit.peb", editContext(task, title, result.message)) +
                        renderStatus(result.message, isError = true),
                )
            } else {
                seeOther(tasksPath(edit = task.id, error = result.code, title = title))
            }

Save validates with the same function the add form uses. On failure, HTMX gets the edit row again with the typed title and the error, plus the status fragment marked as an error; a browser gets a redirect that carries edit, the error code and the typed title, which the list route renders back into the same form. The message itself never travels in a URL; the code does, and the model turns it back into text.

Saving, cancelling and toggling

  • On success both modes end with the row in view mode: a fragment and a status, or a redirect
  • viewTask is Cancel
  • toggleTask flips completed and announces which way it went
  • Every message that names a title is text handed to the status template

Read the three remaining handlers against the templates. Success returns the view row and a saved message to HTMX, and a redirect to the list otherwise. Cancel and toggle follow the same shape, and nothing in the file builds HTML with a title in it.

Building the redirect

src/main/kotlin/routes/TaskRoutes.kt
private fun tasksPath(edit: String? = null, error: String? = null, title: String? = null): String {
    val params =
        buildList {
            if (edit != null) add("edit=${edit.encodeURLParameter()}")
            if (error != null) add("error=${error.encodeURLParameter()}")
            if (title != null) add("title=${title.encodeURLParameter()}")
        }
    return if (params.isEmpty()) "/tasks" else "/tasks?" + params.joinToString("&")
}

Every redirect in the file goes through this function, which adds only the parameters that carry information. The plain list is still /tasks, and a successful save goes there with no arguments. A failed save carries edit, the error code and the title, in that order.

Check it with the mouse

  • Add two tasks
  • Edit, change the title, Save: the row swaps back and the status says it was saved
  • Edit, then Cancel: the original row returns, unchanged
  • Blank the field and Save: the row stays a form, the message is under it, the status repeats it

The mouse pass is the quickest and finds the least. Watch the status box as well as the row, because the announcement is the thing the keyboard and screen reader passes depend on. If the message is under the field but the status box is empty, the error branch is not rendering the status.

Check it with the keyboard

  • Tab from the address bar to the first Edit button, press Enter
  • Focus lands in the title field with the cursor in it
  • Type a title and press Enter: a form with one text field submits on Enter
  • Tab to Cancel and press Enter; Tab to Mark done and press Space

If focus lands nowhere and you are back at the top of the page, the response was a full page rather than the fragment, which means the request went out without the header. Enter submits a one-field form, so Save needs no click. Space activates a button and Enter activates a link; use the right one for each.

Check it with a screen reader

  • On the Edit button: "Edit" and the task title, from aria-describedby
  • In the field: "Title", an edit field, with the hint
  • Blank it and save: the message twice, once as the alert appears and once as the status changes
  • Save a valid title: that it was saved
  • Write down what you heard at each of the three points

The screen reader pass is the one the chapter is built around, and the record is what you heard, in the screen reader's words. Silence at any of the three points is a finding, and the auditing chapter says what to do with it. If the error is read when it appears but not when you return to the field, the id in aria-describedby and the id on the paragraph disagree.

The other mode, from a second terminal

curl -i http://localhost:8080/tasks/<id>/edit
curl -i -d 'title=' http://localhost:8080/tasks/<id>/edit

Copy the id from a row's id attribute in the page source. The first prints a 303 whose Location carries edit and the id; the second prints a 303 whose Location ends with the blank title error code and an empty title. Open each Location in the browser and you see the list page with that row as a form, the second with the error shown.

Then with JavaScript off

  • Edit reloads the page with the row as a form
  • Save reloads it as a row
  • Cancel is a link back to the list
  • The address bar shows the state at every step

The click paths for switching JavaScript off in two browsers are in the parity chapter. Go through the same three flows and read the address bar after each; the state is in the URL because the redirect put it there. If after a successful save the form is still open, the redirect carried edit, and a success should go to the list with no arguments.

Two differences that are not defects

  • After an HTMX swap, focus is wherever the new markup puts it, here the field
  • After a reload, the browser honours autofocus the same way, but scrolls to the top first
  • A page can carry only one autofocus, which editingId guarantees

The two modes do not behave identically about focus and cannot. The swap leaves the page where it was and moves focus into the field; the reload starts from the top and then moves focus. Record the difference if you notice it, but it is not a backlog row.

What goes wrong

  • Focus lands nowhere and you are at the top: the request went out without the header
  • The error is read when it appears but not from the field: the two ids disagree
  • After a successful save the form is still open: the redirect carried edit
  • Silence at one of the three listening points: a finding, not a mistake in your testing

Each symptom has one cause in this codebase. The first means HTMX did not handle the request, usually because the script did not load; check the footer. The second and third are a template id and a redirect argument. The fourth is the reason the session exists.
