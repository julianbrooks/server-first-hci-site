Pilots

Server-First HCI

What you will have built

  • Four pilot sessions with consenting participants
  • Each participant in both modes
  • A metrics file and a set of notes the analysis chapter can work from
  • A consent log, and a paragraph per participant on what went wrong procedurally

This session is run, not read. The plan and the instrument from the last chapter are used on four people, each doing the tasks twice, and the output is the file the server wrote and the notes the note-taker kept. The last line is the part people skip and the analysis chapter reads first.

Before you start

  • The plan and seed data from the last chapter, and a dry run that passed
  • The participant information sheet and the consent form, copied into research/ with the blanks filled from your institution's page
  • Four people from outside your pair who have agreed to give you twenty minutes each

Three things, and none of them can be done during the session. The dry run is the one that gets skipped; a pilot run on an instrument that was not checked produces rows nobody can use. The participants come from outside your pair because your partner has already seen every screen.

Every participant does the tasks twice

  • Once with HTMX, once with JavaScript off
  • The comparison is between a person's two passes, not between two groups of people
  • This uses each participant twice, which with four of them matters
  • It removes the largest source of noise: people differ from each other far more than the two modes do
  • It brings one problem of its own: the second pass is always easier

This is a within-subject design, and the chapter is careful about what it buys and what it costs. With four people a between-groups comparison would be two against two, and the difference between any two people swamps the difference between the modes. The price is the order effect, which the next slide halves and does not remove.

Counterbalancing

  • P1 and P3 start with HTMX; P2 and P4 start without JavaScript
  • Each mode is first for two people
  • That halves the order problem; it does not remove it
  • With two people per order you cannot separate the order effect from the mode effect
  • Say so when you report

Counterbalancing spreads the order effect across both modes so that neither gets all of the advantage of going second. It cannot cancel the effect with four people, and the chapter asks you to say so in the write-up rather than pretend otherwise. The consent log records which mode each person did first.

What four people can tell you

  • For each participant, time on task and errors in each mode, side by side
  • Then how many of the four were faster or made fewer errors in which mode, and by how much
  • That a failure happened in front of you, which is enough to put it on the backlog
  • Not a claim about people in general
  • Not a hypothesis test: with four participants a p-value is theatre, and this book does not compute one

The design supports a descriptive comparison and the observation of failures, and the chapter says so plainly. A finding is "participants without JavaScript failed the edit task in two of six attempts", with the rows to show for it, not a generalisation. The metrics appendix says how to write the comparison up.

Prepare the room

  • Start the server; copy research/seed-tasks.csv to data/tasks.csv; delete data/metrics.csv if it holds anything
  • The application in a browser with no other tabs, DevTools closed, the bookmarks bar hidden
  • One of you facilitates and one takes notes; swap between sessions
  • research/plan.md open for the facilitator; research/pilots/P1.md open for the note-taker
  • research/consent-log.md: pseudonym, date, which mode first, consent given; nothing else

The room is set before the first participant arrives and reset between them. The browser is bare so that nothing on screen names you, your other work or anyone else. The consent log is one line per participant and holds nothing a person could be recognised from.

What the facilitator says

  • Hand over the information sheet and give them time to read it
  • "We are testing the task list, not you, so there is nothing you can get wrong"
  • "I will read you a few short tasks and you do them; I will not help, but you can stop at any point"
  • "The server records what it does, under the code P1 rather than your name; my partner is taking notes; nothing is recorded or filmed"
  • "Are you happy to go ahead?"

The chapter gives the script at this length and asks you to say it in your own words. The four things it has to contain are that the test is of the software, that you will not help, what is recorded and under what name, and that they can stop. Then the participant initials the consent form, you write the pseudonym and the date on it, and the form goes in the folder, not the repository.

Before the first task

  • Set the sid cookie to the pseudonym and check that the footer shows it
  • Set the mode for the first pass and check the footer again
  • Give the participant a minute with the list, untimed

Two footer checks, every time, because the cookie and the mode are the two things that cannot be fixed after the rows are written. The untimed minute lets the participant see the page before the first scenario, so the first task measures the task and not the first sight of the list. Then read the first scenario once.

During a task

  • Read the scenario from the plan once, and watch
  • The note-taker writes: the time read; what they did first; every hesitation of more than a few seconds and what they were looking at
  • Anything they said, word for word where you can
  • Whether they noticed the status message or the redirected page
  • Completed, not completed, or completed after help; then "on a scale of one to five, how confident are you that that worked?"

The note-taker's record is the half of the data the server cannot write. Hesitations and where the participant was looking during them are the findings the analysis chapter turns into backlog rows. The confidence question is asked once per task, and the number is written down with the task code.

Do not help

  • If the participant is stuck, let them be stuck; where they look and what they try is the finding
  • After about two minutes, ask "what are you looking for?", which tells you what they expected without telling them where it is
  • If they are still stuck, say that you will move to the next task, and record it as not completed with the reason
  • If they are frustrated rather than stuck, offer to stop
  • A participant who wants to leave, leaves, and their rows stay in the log unless they ask for them to go

The two-minute rule is the one facilitators find hardest, because the urge to point at the button is strong. The question after two minutes is chosen because it reveals the participant's expectation without correcting it. The last line is consent in practice: leaving is always allowed, and the data stays unless the participant asks otherwise.

Between the passes

  • Switch the mode, reload, check the footer
  • Tell the participant that the page will now work slightly differently
  • Run the same tasks in the same order
  • The second pass is faster for everyone; that is the order effect

The switch is the same mechanism as the parity chapter, and the footer check is the proof it took. The participant is told the page will work differently, not how, so that the second pass is not steered. The order effect is expected and is why half of your participants did this pass first.

Debrief

  • Which task was hardest, and why
  • Whether anything surprised them or did not do what they expected
  • Whether there was a moment when they were not sure something had worked
  • If they used the keyboard alone or a screen reader: whether anything was unreachable
  • Write the answers down as said; do not explain or defend the design

Three questions, four for a participant using assistive technology, with the answers written as said. If they ask why something works the way it does, say you will tell them after the last session, because the explanation would steer the next participant if it reached them. Remind them that they can ask for their rows to be deleted by quoting the pseudonym, and show them where that is written on the information sheet.

Check the log before they leave

  • Open data/metrics.csv and find the rows for their pseudonym
  • Rows in both modes; the validation_error rows match the errors the note-taker saw
  • Every task in the plan has the row the plan said would mark its end
  • A task with no row: do not ask them to repeat it; a repeat would be a third pass, not the same measurement
  • Note what is missing in their file and keep the note-taker's record of that task instead

The check happens while the participant is still there, because only then can you tell which rows are theirs beyond doubt. A missing row is recorded as missing, and the note-taker's timing stands in for it. Repeating the task would measure a third attempt and not a second pass.

Reset for the next participant

  • Copy the seed tasks back to data/tasks.csv
  • Set the cookie to the next pseudonym
  • Set the mode for their first pass, and check the footer

Three steps, in that order, before the next person sits down. The seed data is reset so that every participant sees the same list and the scenarios still name tasks that exist. The cookie is set before they arrive, not after, which is the mistake the next slide starts with.

What goes wrong

  • The rows carry six hex characters instead of the pseudonym: the cookie was never set; write the session's start and end times in the notes now, and set it for the next person before they sit down
  • A cookie set late, a task read twice, a server restarted: write it in the procedural paragraph
  • A participant names someone, "I'd do it the way Sam does": the name comes out of the notes before committing
  • The last participant's tasks are still in the list: the seed data was not copied back

The hex-character rows are not lost; the timestamps attribute them, as long as you write the session's start and end down while you still know them. Everything procedural goes in one paragraph at the end of that participant's notes, and the analysis chapter reads those paragraphs before it reads the numbers. The name is the one that cannot wait.

What to record

  • After the fourth session, copy data/metrics.csv to research/metrics.csv
  • Commit it with research/pilots/P1.md to P4.md and research/consent-log.md
  • The metrics file holds pseudonyms and timings and nothing else, which is why it can go in the repository when the consent forms cannot
  • Read the notes for names before committing
  • One paragraph at the end of each participant's notes on what went wrong procedurally

The committed copy of the metrics file is the one later chapters and the portfolio link to; the one under data is ignored by the tag's gitignore. The consent forms stay in the folder. The procedural paragraph is the honest record of the session, and the analysis starts from it.
