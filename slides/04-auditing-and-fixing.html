Auditing and fixing

Server-First HCI

What you will have built

  • An audit of the task list against WCAG 2.2
  • Each defect recorded against its criterion
  • One defect fixed, with a diff you can explain
  • An audit record saying what you checked and what you did not

This session is the method the rest of the book runs on your own work: four passes over the page and a backlog row for every finding. You run it first on a tag that has defects added to it, so that there is something to find. By the end one of them is fixed and the fix is checked by the pass that found it.

Before you start

  • Commit your work and check out week-07-lab2-audit; git describe --tags prints the name
  • Install axe DevTools in Chrome, Edge or Firefox
  • Have a screen reader you can start
  • Open backlog/backlog.csv

The browser extension comes from the browser's own extension store and takes a minute. The screen reader is the same one you used in the last session. The backlog is where every finding goes, with the columns from the needs-finding chapter.

This tag is not your code

  • Four or so accessibility defects were added to it in one commit
  • No comment in the code points at them
  • Some are found by a checker in a second; some only by a person using a keyboard or a screen reader
  • The method is the point, and it is the same one you run on your own work from here on

The tag is not the code you left at the end of the inline edit chapter. The defects are real ones of the kind that reach production, and they are spread across what a tool can see and what only a person can. Do not go looking for them by reading the diff; run the passes.

Pass one: the automated checker

  • Start the server, open the list, add two or three tasks so the page has rows
  • F12, the axe DevTools tab, "Scan ALL of my page"
  • Results grouped by rule: the element, an explanation, the criteria it maps to
  • axe's critical, serious, moderate and minor are its words for impact, not WCAG levels

The scan takes a few seconds and groups what it finds by rule. Each result names the rule, shows the element it fired on, links to an explanation and lists the WCAG success criteria it maps to. The impact labels are the tool's own; the backlog uses WCAG's levels, A and AA.

Record before you judge

  • Every issue is a backlog row now, before you decide whether it matters
  • story_type is audit
  • evidence is the axe rule name and the criterion number with its level
  • title says where on the page it is
  • Nothing reported at all: check git describe --tags, and that the tab is the list, not the 404 page

Write the row first and judge it later, because the judging is a separate step with its own scoring. The evidence column carries the rule and the criterion so that a reader can look both up. An empty scan on this tag means you are on the wrong tag or scanning the wrong page.

What a checker cannot tell you

  • It reads the DOM
  • It can tell that a field has no label, an image has no alternative, two colours are too close, an attribute points at an id that does not exist
  • It cannot tell whether an announcement was made
  • Or whether a label's text makes sense, or where the focus went after a swap

An automated checker is fast and incomplete in a predictable way. Everything it finds is a property of the markup at one instant; everything it misses is about behaviour over time or meaning. The other three passes exist for those.

Pass two: the keyboard

  • Put the mouse out of reach; click once in the address bar, then Tab, and keep going
  • The first stop is the skip link, which appears when focused and moves you to the content on Enter
  • Every control reached in reading order, each with a visible focus ring
  • Enter activates a button or a link; Space activates a button
  • Go through add, edit and delete; press Escape and Shift-Tab to check nothing holds the focus

The keyboard pass needs no setup and finds a different class of defect from the checker. Watch where the focus goes and whether you can see it; a control you cannot reach, or cannot see that you have reached, is a finding. The skip link is the first thing you meet and the first thing to check.

The keyboard criteria

  • 2.1.1 Keyboard and 2.1.2 No Keyboard Trap, both Level A
  • 2.4.1 Bypass Blocks and 2.4.3 Focus Order, both Level A
  • 2.4.7 Focus Visible and 2.4.11 Focus Not Obscured (Minimum), both Level AA
  • A finding here is a row with evidence set to keyboard pass and the criterion

Six criteria cover the keyboard pass, and the chapter's table says what you are checking for each. Reachable and operable, able to leave again, a skip link, a sensible order, a visible indicator, and an indicator not hidden behind other content. Record the criterion with the finding, because that is what you check the fix against later.

Pass three: the screen reader

  • NVDA on Windows, VoiceOver on macOS, Orca on Linux; the appendix has the keys
  • Read the page from the top once; then move by heading, then by form field
  • Each field: a name, its type, its hint; "edit text" with no name has no label
  • Add a task and listen for the status; submit a blank title and listen for the error
  • Links and images; then each button, listening for which task it belongs to

The chapter says what to listen for and leaves the key commands to the appendix. Move through the page the way a person who cannot see it does: by headings, by form fields, by links, and listen for what is missing or wrong. The two live announcements, the status after an add and the error after a blank title, are the ones a checker cannot test.

The screen reader criteria

  • 1.1.1 Non-text Content and 1.3.1 Info and Relationships, Level A
  • 2.4.4 Link Purpose (In Context) and 3.3.1 Error Identification, Level A
  • 3.3.2 Labels or Instructions and 4.1.2 Name, Role, Value, Level A
  • 4.1.3 Status Messages, Level AA
  • Write down what it said, in its words: "Heard: 'button'" is evidence -- "label missing" is a conclusion

Seven criteria cover this pass. The record is the screen reader's words next to each finding, with the screen reader's name as the evidence, and the conclusion you draw from the words goes in the notes column. A reader of the backlog can check a quotation; they cannot check a conclusion.

Pass four: contrast

  • Inspect a piece of text and click the colour swatch next to its color in the Styles pane
  • The picker shows the ratio against the background and whether it meets AA and AAA
  • Check body text, each kind of button, the status box, the error text, the footer link and the focus ring
  • Text needs 4.5 to 1, or 3 to 1 if it is large; control parts you need to see, including the focus ring, need 3 to 1
  • 1.4.3 Contrast (Minimum) and 1.4.11 Non-text Contrast, both Level AA

The browser's own colour picker does the arithmetic, and the WebAIM checker does the same from two hex values. The list of things to check is the chapter's; the focus ring is the one people forget, and it is a control part, so it needs three to one against what surrounds it. Two criteria cover the pass.

Two things that look wrong and are not

  • The Pico stylesheet is minified, which looks alarming in the inspector and is how a production stylesheet ships
  • The #status region is empty when the page loads, which is correct for a region that announces later changes

Both of these get reported by students as defects on this tag, and neither is one. The minified stylesheet is the vendored copy of Pico as it is distributed. The empty live region is the design from the first chapter: a region that exists before its message is what makes the message announced.

Choose one and fix it

  • Score the rows as the needs-finding chapter says; mark the ones you would fix
  • Fix the highest score you can change in the time, with a criterion to check it against
  • Make a branch; find the cause in the template or the stylesheet, not the symptom
  • The smallest change that removes the cause
  • Run the pass that found it again, the axe scan again, and ./gradlew test

A finding with no criterion is still a finding, but you cannot prove this afternoon that you fixed it, so choose one that has a criterion. Hiding an element from the checker with aria-hidden makes the report go away and the problem stay; the cause is in the markup or the stylesheet. The template smoke test loads every template, so a broken tag fails the build, and the three checks together are the verification.

The reference fix

  • week-07-lab2-fixed is the state after every seeded defect is fixed
  • git diff week-07-lab2-audit week-07-lab2-fixed is our fix
  • Read it only after your own fix is committed
  • Anything it changes that you did not find is a backlog row with evidence set to reference diff
  • The pass that should have caught it is the one to practise

The reference diff is for after, not before, because the method is what you are learning and the diff short-circuits it. Once your own fix is committed, read it and compare. Each change you did not find is a row, and the useful question is which of the four passes should have found it.

What goes wrong

  • axe still reports the issue after your change: reload with the cache bypassed, Ctrl-Shift-R; the stylesheet is cached and the templates are not
  • The scan reports nothing: wrong tag, or the 404 page
  • The build fails after a template edit: the smoke test found a broken tag
  • The report goes away but the problem stays: the fix hid the element from the checker

The cached stylesheet is the one that costs the most time, because the fix is right and the browser is showing the old file. The empty scan is a wrong tag or a wrong tab. The last line is the one to be honest with yourself about: a fix the checker accepts and a screen reader does not is not a fix.

What to record

  • The new backlog rows, the fix commit, and the before and after evidence as the screenshot appendix says
  • research/audit.md, one short section per pass: the tool and its version, the date, what you checked, what you did not
  • The last item is the useful one when the pilots find something the audit missed

The audit record is new this chapter and is short. Each pass gets the tool, the version, the date, and two lists: what was checked and what was not. When a pilot participant finds something in week 9 that the audit did not, the second list is what tells you whether the method missed it or the pass was never run.
