Partials and pagination

Server-First HCI

What you will have built

  • A list built from partials
  • Paginated and filterable
  • Each of those views has a URL that works without JavaScript
  • The address bar tells the truth in both modes

The list grows this session, and so does the page around it. Two new partials render one page of rows and the controls to move between pages, a filter form sits above them, and the list route learns to answer with a fragment or a whole page from the same URL. The test at the end is that every view you can reach by typing can be reached by a bookmark.

Fifteen tasks in one line

for i in $(seq 1 15); do curl -s -o /dev/null -d "title=Task $i" http://localhost:8080/tasks; done

With the server running, this posts fifteen titles through the same route the form uses. The page size is one constant in Pagination.kt, and fifteen is more than it, so you now have two pages. Delete and re-run it whenever the list gets short.

Why page and filter

  • A dozen tasks is fine as one page; a hundred is not
  • A person using a screen reader walks a list row by row, and everyone scrolls
  • A filter and pages cut the list down
  • Both have to produce a URL
  • A view you cannot bookmark, share or reach with JavaScript off exists only while the script is running

The reason to paginate is the person reading the list, not the server. A long list costs a screen reader user one key press per row and costs everyone a scroll. The constraint on the solution is the last line: a filtered view that lives only in the script's memory is not a view the book counts.

One page of rows

src/main/resources/templates/tasks/_list.peb

The list partial renders one page of rows, choosing the edit row for the task being edited and the view row for every other. The row template is unchanged in shape from the last chapter. The list is described by a paragraph after it, which the next slide shows.

The count the list is described by

<p id="result-count">

    No tasks{% if query %} match "{{ query }}"{% endif %}.

The unordered list carries aria-describedby pointing at this paragraph, so a screen reader that lands on the list hears how many rows it holds and whether a filter is on. The empty case is a sentence in the same paragraph rather than a fake row in the list. Nothing here states the page size.

The pager

src/main/resources/templates/tasks/_pager.peb
    {% if page.currentPage > 1 %}
    <li><a href="/tasks?q={{ query | urlencode }}&page={{ page.currentPage - 1 }}"
           hx-get="/tasks?q={{ query | urlencode }}&page={{ page.currentPage - 1 }}"
           hx-target="#task-area" hx-push-url="true">Previous</a></li>
    {% endif %}
    <li aria-current="page">Page {{ page.currentPage }} of {{ page.totalPages }}</li>

Each link carries two sets of attributes again: an href with the query and the page number for the browser, and an hx-get with the same URL for HTMX. The current position is marked with aria-current. The query goes through urlencode because it is going into a URL, not into text, and the whole nav renders nothing when there is one page.

The filter form

src/main/resources/templates/tasks/index.peb
  <form action="/tasks" method="get" role="search"
        hx-get="/tasks" hx-target="#task-area" hx-push-url="true"
        hx-trigger="input changed delay:300ms from:#filter-input, submit">
    <label for="filter-input">Show tasks whose title contains</label>
    <input type="search" id="filter-input" name="q" value="{{ query }}" autocomplete="off">
    <button type="submit">Filter</button>
  </form>

The filter is a GET form with a visible button, and that is the whole of its behaviour without JavaScript. The hx-trigger adds the typing: input, changed and a 300 millisecond delay mean a request after a pause in typing and only when the value changed, and submit keeps the button working with the script on. The target is the task area, and hx-push-url puts the requested URL into the browser history.

The task area

src/main/resources/templates/tasks/index.peb
<section aria-labelledby="list-heading">
  <h2 id="list-heading">Your tasks</h2>
  {# hx-history-elt: HTMX saves and restores this element when the back button returns to a pushed URL. #}
  <div id="task-area" hx-history-elt>
    {% include "tasks/_list.peb" %}
    {% include "tasks/_pager.peb" %}
  </div>
</section>

One element wraps the list and the pager, and every list request swaps into it. The hx-history-elt attribute tells HTMX that this is the element to save and restore when the back button returns to a pushed URL. The page is now a container and three partials.

One source for the row markup

  • _item.peb is included by _list.peb
  • _list.peb is rendered into the page and as the fragment
  • A change to a button's label or an aria-describedby lands in both modes at once
  • The 2025 version had a separate fragment route with its own copy of the list markup, and the copies drifted

This is what makes the two modes stay equal. There is one template for a row and one for a page of rows, and the route renders the same templates whether it is answering a browser or HTMX. The 2025 code had two copies of the list markup, and an accessibility fix made in one of them did not reach the other.

A page of anything

src/main/kotlin/utils/Pagination.kt
        fun <T> paginate(items: List<T>, requestedPage: Int, pageSize: Int = DEFAULT_SIZE): Page<T> {
            require(pageSize > 0) { "pageSize must be positive" }
            val totalPages = maxOf(1, (items.size + pageSize - 1) / pageSize)
            val current = requestedPage.coerceIn(1, totalPages)
            val from = (current - 1) * pageSize
            val to = minOf(from + pageSize, items.size)
            val pageItems = if (from < items.size) items.subList(from, to) else emptyList()
            return Page(pageItems, current, totalPages, items.size)
        }

Page is one page of any list, and paginate clamps the requested number into range, so a page that no longer exists because its tasks were deleted shows the last page rather than an error. The page size lives in one constant in this file and no template states it. The context the templates see is the four values at the top of the class.

One route, two answers

src/main/kotlin/routes/TaskRoutes.kt
private suspend fun ApplicationCall.listTasks(store: TaskStore) {
    val query = request.queryParameters.query()
    val view = ListView.from(store, query, request.queryParameters.page())
    // The same URL returns a fragment or a page depending on this header, so caches must not mix them.
    response.headers.append(HttpHeaders.Vary, "HX-Request")
    if (isHtmxRequest()) {
        val found = view.page.totalItems
        val status = if (query.isEmpty()) "" else "$found ${plural(found, "task")} ${if (found == 1) "matches" else "match"} \"$query\"."
        respondHtml(renderTaskArea(view) + renderStatus(status))

With the header set the route renders the list and the pager and a status that announces the match count; without it, the whole page with the form state from the query string as in the last chapter. The Vary header is on both answers. It tells any cache between the server and the browser that the response depends on that header, so a fragment is never served to a browser that asked for the page.

Where the form was submitted from

src/main/kotlin/routes/TaskRoutes.kt
/** The filter and page a form was submitted from, carried in hidden fields so the person returns to the same place. */
private data class Place(val query: String, val pageNumber: Int) {
    val context: Map<String, Any?>
        get() = mapOf("query" to query, "pageNumber" to pageNumber)

    fun path(edit: String? = null, error: String? = null, title: String? = null) =
        tasksPath(query, pageNumber, edit, error, title)
}

Place is the filter and page a form was submitted from, so that an edit, a toggle or a delete on page three of a filtered list returns you to page three of that filtered list rather than to the top of everything. Every form in the row template carries the place in hidden fields. The path function adds only the parameters that carry information, so the plain list is still /tasks.

The delete form targets the whole area

  • The delete form now targets #task-area rather than its own row
  • Deleting the last row on a page redraws the page count instead of leaving a page with nothing on it
  • The parity chapter has the handler

In the last chapter delete swapped out its own row. With pages, removing the last row on a page would leave an empty page with a pager that still claimed it existed, so the response redraws the whole area. The handler is read in the next chapter, where it is the one route that behaves differently between HTMX versions.

The pushed URL is a real URL

  • Type a few letters into the filter and wait: the list changes, the status says how many match
  • The address bar now reads /tasks?q= and what you typed; Next adds page=2
  • Press reload: the whole page, with the filter filled in and page 2 showing
  • The same URL, two answers, told apart by the header
  • The 2025 /tasks/fragment route pushed a URL that reloaded as a bare list with no layout

This is the test of the chapter. HTMX pushes the URL it requested into the history, and that works only because the same URL answers a plain request with the full page. The 2025 version fetched its fragments from a separate route, so the URL it pushed was that one, and reloading it showed a list with no layout.

Back, and a new tab

  • Press Back: HTMX restores the saved #task-area from its history cache
  • When the cache has nothing, it requests the URL again with HX-History-Restore-Request: true
  • isHtmxRequest() treats that as a request for the whole page
  • Copy the URL into a new tab: the same view

The header check from the first chapter has its second condition for this moment. A history restore request carries the HTMX header but wants a whole page, and the function returns false for it. A new tab is the plainest test: no history, no script state, the URL alone.

What goes wrong

  • A request goes out on every keystroke: delay or changed is missing from hx-trigger
  • Typing sends nothing and only the button works: from:#filter-input names an id that is not on the field
  • The status says zero tasks match after you clear the field: a count announced for an empty query
  • Page is unresolved: you are not on the tag

The Network tab shows the first two. A filter request has the HTMX header among the request headers and Vary among the response headers, and its response is a list, a nav and the status div with no html element around them. The third is a logic error in the handler's status message.

Then with JavaScript off

  • Type, press Filter: the page reloads with ?q= in the address bar
  • Previous and Next are links and reload the page
  • Edit on page 2 of a filtered list, Save: back on page 2 of that list, because the hidden fields carried the place through the redirect
  • The footer says which mode you are in

The parity chapter has the click paths for switching the script off in two browsers. Every view reached by typing is reached by the button, and the hidden fields carry the place through every redirect. The footer is the quickest check of which mode you are in.
