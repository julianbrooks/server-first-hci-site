What you will have built

  • A README in which every claim links to the data, code or screenshot that supports it
  • A reflection of two paragraphs
  • A tag that a stranger can clone, build and read

The last session adds a README and a tag, and nothing else. Everything the README points at was produced by an earlier chapter, and this session's work is to point at it, check that every link resolves, and tag the result. About two hours and no new code.

Before the lab

  • Read crit/notes.md from the crit
  • Have the assessment page open: it holds the pass criteria, and nothing here restates them
  • About two hours and no new code

The crit notes are the to-do list for the first activity. The assessment page is your module's, and the chapter points at it rather than copying its criteria. Nothing is built this session.

What the portfolio is

  • The README of your repository and the files it points at
  • Not a separate document, a slide deck or a folder of screenshots
  • Written for a reader who was not there and has little time
  • That reader opens the README at the tag, follows the links, and decides whether each claim is supported by what they find
  • A claim with no link is an assertion, and the assessment treats it as one

The portfolio is the front page of the work, not a report about it. The reader's test is the one on the fourth line, and every sentence of the README is written for it. The last line is the rule that the rest of the session serves.

Everything already exists

  • The consent record, notes, stories and backlog; the audit record and fix
  • The metrics file; the pilot notes; the analysis
  • The regression checklist and re-pilot; the screenshots; the three crit files
  • This chapter adds the README and a tag
  • If a link you want to write has nothing to point at, the honest response is a sentence saying so, not a link to the nearest thing

If you have followed the chapters in order, every file the README needs is already committed. The portfolio finds gaps rather than creating evidence; a gap found is stated as a limitation. Pointing at the nearest thing is the failure the crit was meant to catch.

Act on the crit

  • For each question in crit/notes.md: add the link, gather the evidence, or write the limitation
  • Gather and commit before you write a word of the README; a link to an uncommitted file breaks at the tag
  • Re-running a pilot is not expected unless the crit found a flaw in the method
  • Polish the record; do not rerun the study

The three actions are the ones the crit chapter set out. The order matters: evidence is committed first, so that the README's links have something to resolve to at the tag. A flaw in the method, such as a participant who was told the answer, is the one reason to run a pilot again.

The README, first three sections

  • What the application is, in two sentences, and how to run it, by pointing at the setup appendix; the tag the portfolio describes
  • How many participants, in which modes, in the pilots and the re-pilot; that consent was recorded, with a link; no names, no student numbers, nothing a participant could be recognised from
  • The findings, one sentence each, each followed by a link to the rows or lines that support it
  • A finding with an accessibility cause names its success criterion by number

Each section is a few sentences and the links that support them, and the whole file fits on two screens. A finding is a claim about what happened, such as participants without JavaScript failing the edit task in two of six attempts, followed by a link to those rows and to the line of the notes where a participant said why. The reference repository's worked example at the week-10 tag shows the shape at paragraph length.

The README, last four sections

  • The fixes, one to three, each with the finding it addresses, the criterion it serves, and a link to the commit or diff
  • A fix that did not move its measurement is still a fix; say what the measurement did and what you make of it
  • The verification: the completed regression checklist, the re-pilot data, and the before and after figures side by side
  • The limitations, one paragraph: what you did not do, what the sample does not support, the crit questions you could not answer
  • The reflection

A regression check that failed and was not fixed is said in the verification section, not left as a blank row. A limitation stated here is professional practice; the same limitation discovered by the reader is a gap. The reflection is the next slide.

Links

  • Relative paths within the repository, with a line or row where one applies
  • #L41-L46 after a file path works on GitHub and GitLab
  • A reader who has cloned the repository opens the same path
  • Links to your working copy, a cloud drive or a chat message resolve for nobody else

A link is a path a stranger can follow from the tag, in the forge's web view or in a clone. Line and row anchors turn a claim about rows 41 to 46 into something the reader can see in one click. Anything outside the repository is not a link in this sense.

The reflection

  • Two paragraphs of prose, no headings, bullets or template
  • First: where the chain from finding to verification was strongest, where it was weakest, and which question from the crit you could not answer
  • Second: what you would measure that you did not, who you would recruit, and which backlog row you would take on, with the row named
  • Every sentence checkable against a file in the repository

The reflection is held to the same standard as the rest of the README: a reader should be able to check each sentence against a file. The first paragraph is about the evidence you have; the second is about the evidence you would gather next. The named backlog row is what makes the second paragraph a plan rather than a sentiment.

Two things that make a reflection worthless

  • A set of headings with one sentence under each, "what went well" and "what was challenging", says nothing a reader can act on
  • Write sentences that connect
  • Praise for your own work does not belong in it
  • The evidence is in the sections above; the reflection is for what the evidence does not show

Both failures come from treating the reflection as a form to fill in. The template version produces one sentence per heading and no argument; the praise version restates the findings as achievements. What the reader wants is the part of the story the files cannot tell.

Check one: no personal data anywhere

  • Search the working tree for email addresses with git grep -n -i -E '[a-z0-9._-]+@[a-z0-9.-]+\.[a-z]+'; the only hit should be your own
  • Search the history for each participant's real name with git log -p -S'<name>'
  • A name in an old commit is still in the repository after the file was changed
  • Open every screenshot and look at the browser tabs, the bookmark bar and the window title
  • If a name is in the history, tell the module team before you tag; the fix rewrites history and is not yours to do alone

Three searches: the tree for addresses, the history for names, the screenshots by eye. The history search is the one people skip, and it is the one that finds a name that was removed from a file a month ago. Rewriting history is a decision for the module team, which is why the chapter says to tell them first.

Check two: every link resolves

  • Open the README on the forge's web view at the commit you are about to tag and click every link
  • A link that works in your editor and not on the web view points at a file that was never committed
  • The metrics file is the usual one: the reference repository ignores data/*.csv apart from the example files
  • If the pilot data was not copied into a committed location when the pilots ended, copy it now, commit the copy, and point the links at it

The web view is the reader's view, so that is where the check is done. The metrics file catches people because it worked in the editor all along; the tag's gitignore kept it out of every commit. The pilots chapter asked for the copy; this is where you find out whether it was made.

Check three: it runs from a clean clone

git clone <your repository address> check
cd check
git checkout <the commit you will tag>
./gradlew run

In a directory outside your working copy, clone, check out the commit, and run. Open the page as the setup appendix says, add a task, stop the server with Ctrl-C and delete the clone. If the clone fails to build and your working copy does not, a file the build depends on was never committed, and git status in the working copy names it.

Tag and push

git tag -a <tag name> -m "Portfolio"
git push origin <tag name>

Write the tag name in the first section of the README and commit that change before you tag, or the README at the tag names a tag that does not yet exist. If you change anything afterwards, tag again with a new name and update the README. A moved tag is one the reader cannot trust.

What goes wrong

  • The README at the tag names a tag that does not yet exist: the name was written after tagging
  • A link that works in your editor and not on the web: the file was never committed
  • The metrics file is missing at the tag: data/*.csv is ignored, and the copy was never made
  • A name in the history: tell the module team before you tag
  • The clean clone fails to build: git status in the working copy names the file

Each of the three checks has a failure, and two more come from the order of the last steps. All of them are found by doing the checks in the order the chapter gives, before the tag. After the tag, the fix is a new tag and an updated README, never a moved tag.

What to record

  • The README and the tag
  • Nothing else is new this chapter; everything the README points at was recorded by the chapter that produced it
  • Where and how the tag is submitted, and by when, is on your module's assessment page

The record is the thing itself: a README that a stranger can read and a tag they can clone. Submission mechanics are the module's, not the book's, and the assessment page carries them. This is the end of the strand, and the last chapter stops where the README does.
