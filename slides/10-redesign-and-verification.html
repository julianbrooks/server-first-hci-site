Redesign and verification

Server-First HCI

What you will have built

  • One change, written down before it was made
  • Twenty regression checks recorded
  • A re-pilot with two new participants
  • The chain: finding, measurement, change, verification, a file behind each

This session closes the loop the strand opened in week one. The change is small, the checks are the same twenty every time, and the verification is two more people doing the same tasks. The deliverable is the chain, and it is marked on whether it closes, not on which way the numbers went.

Smaller than the bug report

  • The finding named a task, a mode and a cause
  • The change removes the cause and nothing else
  • A few files and thirty lines is the shape of most fixes here
  • Ten files is two fixes, or a redesign the evidence did not ask for

Students arrive wanting to redesign the page. The finding does not support that; it supports one change. If a change touches ten files, ask which finding asked for each of them.

Three layers for a validation change

  • A browser attribute such as minlength: stops the submission before it leaves the page
  • A CSS rule on :user-invalid: shows the state to anyone who can see it
  • The server's aria-invalid and aria-describedby: catches what the other two miss, and is what a screen reader hears

Each layer catches different people. Chapter 6 left the browser attributes off on purpose so that the server's path was the one measured; this is the point where students decide, from their own data, whether to add them. The server layer is already in the code and stays whatever they add.

What that does to the instrument

  • A submission the browser blocks never reaches the server
  • So the validation_error rows for that task fall to zero
  • Whether or not people stopped making the mistake
  • The zero is the fix and the blind spot together

This is the measurement point of the whole strand. A change that moves a check earlier also moves it out of the log. The note-taker counts browser-blocked submissions in the re-pilot and the write-up gives that count beside the zero. A student who reports the zero alone has reported the instrument going blind as a success.

Write the change down first

  • Which files
  • What a participant sees differently in each mode, one sentence each
  • Which number should move, and which way
  • Which numbers should not move: the median server time; the parity rows for the routes touched
  • The criterion to check against

Written under the top finding before an editor is opened. This is the acceptance criterion, and it is written now so that the result cannot rewrite it. Students who skip this step find afterwards that whatever happened was what they expected.

Make it

  • The smallest change that removes the cause, in both modes, on a branch
  • ./gradlew test: the template smoke test and the route tests in both modes
  • Do the changed task yourself in both modes; read the footer to know which
  • Commit with a message naming the finding and the criterion

Three things catch people. A changed stylesheet is cached and a changed template is not, so a CSS change that does not appear needs Ctrl-Shift-R. HTMX does not swap a 4xx response by default, so sending 400 on a validation error makes the error vanish with JavaScript on. A fragment given autofocus moves focus every time it is swapped in, which is right for an error and wrong for a status message. The commit hash is the third link in the chain.

The twenty regression checks

  • The table is in the chapter and is the one the assessment reads
  • Run every row against the branch, in both modes where the test allows
  • research/regression.csv: id, pass, notes
  • Failed on the branch, passed at the tag: a regression, fixed before the re-pilot
  • Failed at the tag too: a finding, on the backlog with its criterion

Structure, keyboard, forms, dynamic content, visual, no-JavaScript: twenty rows, most of them run by a person because an automated checker finds under half of what WCAG asks. Any Level A failure the student introduced is fixed before anything else.

Row 9 fails at the tag

  • After an HTMX swap, focus should stay on or return to a sensible control
  • The add field and the filter field keep focus: they are outside the swapped element
  • Save, Cancel, Mark done, Delete and Next are inside the element they replace
  • After the swap nothing is focused; the keyboard starts again from the top of the page

Found by driving a browser against the tag. The reference code has this defect as shipped, and students record the row as failing at the tag with the five actions, whether or not they fix it. A change that returns focus to the row or the list after those swaps is a legitimate top-ranked change if the pilots showed people paying for it.

Re-pilot with two new participants

  • The first four have done the tasks twice; a third pass measures their memory
  • Two people who have not seen the list, P5 and P6, one starting in each mode
  • The same plan, the same seed data, the procedure from chapter 8 unchanged, on the branch
  • If a check moved into the browser, the note-taker tallies each refused submission
  • research/metrics-after.csv, research/pilots/P5.md, P6.md, read for names

Recruiting two more people is the step that slips. Book them before the session. The assessment accepts one participant with two as the aim; it does not accept the original four.

Against the before table from last week: edit errors from two of six and two of eight to none, add errors likewise, every median server time within a few milliseconds. That is the shape of a change to a form and not to the storage.

The example files are synthetic

  • Written by tools/GenerateExampleMetrics.kt from fixed seeds; a test keeps them in step
  • git diff week-09 week-10 -- src is empty: no change in the tag produced the second file
  • They exist so that you can practise the comparison before your own data exists

Say this plainly. The files show the shape of a comparison that worked; they do not record one. A student who cites them as evidence that a fix worked has cited a random number generator.

Writing the comparison

  • Before and after with denominators: "two of four saves", "none of four"
  • Time on task for the changed task, P5 and P6 in each mode, beside the four from before
  • What did not move
  • What the two participants said, quoted
  • What two people can show: the failure did not happen in front of you again

Not that the change works for people in general. The evidence this book asks for before a change is kept is that the failure the finding described did not recur in front of you. A change that did not help is written up the same way, and a reverted change with a full verification is a stronger portfolio section than a kept one with a thin one.

The chain

  • Finding: research/findings.md, the heading
  • Measurement: research/metrics.csv, the rows, the before table
  • Change: the commit hash and git diff against the tag
  • Verification: research/regression.csv, research/metrics-after.csv, the after table, two participants' notes

Four links, a file behind each. Merge the branch, tag the result with a name of your own, write the tag in the findings file. The crit presents this chain and the portfolio links to it; a link with no file behind it is where the questions will go.
