Module launch

Server-First HCI

What changes from here

  • Until now your code faced a compiler and a test suite
  • From here it faces people: a screen reader, a keyboard, someone under time pressure
  • You still write Kotlin; the routes and the server logic are yours
  • The question each session asks is not "does it work" but "who can use it"

The programming you have done so far was judged by a compiler and a test suite, and both are indifferent to who is sitting at the keyboard. From here the work is judged by whether a person can get a task done with it, including a person using a screen reader, a person who cannot use a mouse, and a person with ten minutes before a deadline. The Kotlin does not go away; the templates and the evidence join it.

Three positions the book takes

  • The server renders the page, and the page works with JavaScript off
  • Accessibility is checked from the first commit against WCAG 2.2, by criterion number
  • Design changes follow measurement: a plan, pilots, analysis, one fix, verification

Every chapter sits on one or more of these three. The first is an architecture, the second a discipline, the third a method. The next three slides take them in turn, and the rest of the strand is the three applied to one small application.

Server-first

  • The server sends finished HTML; the browser shows it without running a script
  • HTMX is a small script on top that swaps fragments into the page
  • Every link and form works when the script is absent
  • One piece of HTML for the browser and for the screen reader

This is progressive enhancement, which the GOV.UK service manual requires for government services. The reason the book takes the position is narrower than the general argument: the HTML the server sends is what a screen reader reads, so there is one place to get the structure, labels and announcements right and one place to check them. The first chapter walks through how a request becomes a page.

Accessibility from the first commit

  • WCAG 2.2 success criteria, named by number and level
  • Four passes: an automated checker, the keyboard, a screen reader, a contrast check
  • A finding is a backlog row with the criterion and what you saw or heard
  • "Heard: 'button'" is evidence; "label missing" is a conclusion

Accessibility here is not a checklist at the end; it is the way every feature is checked as it is built. The four passes are introduced in the auditing chapter and then run on your own work for the rest of the strand. The record is what the tool reported or what the screen reader said, in its words, against the criterion it maps to.

Evidence-led

  • The server writes one metrics row per request, in both modes
  • Four participants, each doing the tasks with HTMX and with JavaScript off
  • Median and MAD, not the mean; no p-values from four people
  • A backlog in which every row points at its evidence

The second half of the strand finds out whether people can use what you built, by measuring rather than asking. The instrument is narrow and honest: the server records that a request arrived, what for, whether it succeeded and when, and a person with a notebook records the rest. With four participants the output is a descriptive comparison and a set of findings, not a claim about people in general.

What you will build

  • A task list: add, edit in place, mark done, delete
  • A filter and pages, each with a URL you can bookmark
  • Validation on the server, with errors a screen reader announces
  • Instrumentation that labels each participant's rows with a code
  • Everything works with JavaScript off

The application is small on purpose, so that getting it right in both modes and for every kind of user is possible in the time. You clone a working version at the start and fill the gaps the chapters leave, reading the reference code at each tag. By the last lab the same list has been audited, measured with four people, changed once on the evidence, and verified.

Six weeks, two labs a week

  • Week 6: server-first, then needs-finding and consent
  • Week 7: inline edit, then auditing and fixing
  • Week 8: partials and pagination, then parity and validation
  • Week 9: instrumentation, then four pilots; the assessment is launched
  • Weeks 10 and 11: analysis and redesign; then the crit and the portfolio

Each lab works through one chapter against the tag that chapter names, and each week's work becomes evidence for the next. The order matters: the backlog from week 6 is what the audit adds to, the plan from week 9 is what the pilots run, and the pilots are what the analysis works from. Your module's schedule page has the dates, the rooms and the deadline.

How a chapter is laid out

  • One sentence saying what you will have built by the end
  • Before the lab: what to read or install, three items at most
  • Numbered activities: what to do, how to check it worked, what it looks like when it has not
  • What to record for the portfolio
  • Further reading, if any

Every chapter follows the same skeleton, so you know where to look at nine in the morning when a step is not working. The failure mode is written next to the instruction, not in a separate troubleshooting page. The "what to record" section at the end is the one the portfolio chapter depends on; nothing is recorded twice.

Consent and personal data

  • What a participant says is personal data, however small the study
  • Collect the minimum: a pseudonym such as P1, no names, student numbers or email addresses
  • Say where the data is kept and when it is deleted, and keep to it
  • A participant can stop, see their data, or have it deleted
  • A name committed to a git history cannot be deleted

Two chapters involve other people, the interviews in week 6 and the pilots in week 9, and both start with consent. The appendix on privacy and consent holds the principles, and the consent form and participant information sheet are in the appendices too. The last line is the one with no fix afterwards: replace a name with the pseudonym before you save, not later.

People-centred language

  • "A person using a screen reader", "a person navigating by keyboard", "participant"
  • Not "blind user", "disabled user", or "the user" when a specific person is meant
  • Someone whose trackpad broke this morning is, for today, navigating by keyboard
  • The barrier is in the design, and so is its removal

The language is a discipline, not a courtesy. A label like "blind user" assumes everyone under it needs the same thing and says nothing about the situation; the job story form in the next chapter is built to avoid that. The keyboard example is the one to remember: the story about keyboard access belongs to more people than any label covers.

The job story

When [situation],
I want to [motivation],
so I can [outcome],
because [constraint].

This is the form the book uses to write a need down, in place of a requirement or a persona. A requirement names a solution; a story names the situation, so the solution can change when the evidence does. You write five or six of these in the second lab, each with the line in your interview notes it came from.

The evidence chain

  • Finding: a backlog row and the notes it points at
  • Measurement: rows of the metrics file and the figures computed from them
  • Fix: a commit
  • Verification: the regression checklist and the re-pilot
  • A claim with no file behind it is an assertion

Four links, each with a file behind it, run from the first interview to the last commit. The crit in week 11 is where peers look for the link that only holds together because you remember it doing so, and the portfolio is where every link becomes a path in the README. If a link has no file, the honest response is a sentence saying so.

The portfolio

  • The README of your repository and the files it points at
  • Not a separate document, a slide deck or a folder of screenshots
  • Every claim followed by a link to the rows, lines, commit or screenshot that supports it
  • A tag a stranger can clone, build and read
  • Nothing in it names a person

The portfolio is the front page of the work, written for a reader who was not there and has little time. That reader opens the README at the tag you name, follows the links, and decides whether each claim is supported by what they find. The assessment page on your module's site holds the criteria; the portfolio chapter says how to write the README.

What goes wrong

  • A server from last time is still on port 8080, so the page is blank
  • JavaScript is still off in the browser from the last parity check
  • A participant's name typed into the notes, kept to tidy up later
  • A metrics file that still holds the dry run when the first participant sits down

Each chapter names its own failure modes next to the instruction they belong to; these four recur across the strand. The first two cost minutes, the third cannot be undone once committed, and the fourth puts your own rows into the participants' data. Ask early when something does not match the chapter; the line numbers assume the tag the chapter names.

Before the first lab

  • Work through the setup appendix until ./gradlew build passes
  • Clone the starter and run it; add a task
  • Read the first chapter from start to finish
  • Read the Kotlin primer if you have not written Kotlin before
  • Your module's schedule page has the dates and the room

The first lab assumes the build passes and the server runs, so do both before you arrive. The chapter is short enough to read in one sitting, and reading it first means the lab is spent building rather than orienting. If the setup fails, the appendix names the usual causes, and the first lab is the place to ask.

What to record

  • One repository, from today; everything you record goes into it
  • From the first lab: a sentence on each mode, what happened when you added a task
  • From the second: a consent record, notes, stories and a backlog
  • Each chapter ends by saying what to keep

The strand runs on what you record as you go, and nothing is reconstructed at the end. The first lab asks for two sentences, the second for four files, and every chapter after that names what it adds. Keep one repository for all of it, with no personal data in it, and the portfolio in week 11 is a README that points at what is already there.
