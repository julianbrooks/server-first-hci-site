Crit

Server-First HCI

What you will have built

  • One evidence chain presented to a group of peers in five minutes
  • Their questions answered from the files rather than from memory
  • A written response to each of theirs
  • The questions you could not answer, recorded

Nothing in this session changes the code. You put one chain of evidence in front of people who were not there when you built it, and they look for the step that only holds together because you remember it doing so. What you take away is a list of the questions you could not answer from a file.

Before the lab

  • Finish the evidence chain from the redesign chapter
  • Have the application running at the tag that holds your fix
  • Bring the before and after screenshots, named as the screenshot appendix says
  • Nothing in this chapter changes the code

The chain has to be finished, not finishable, because the crit tests what exists. The server runs at the tag with your fix so that the fixed behaviour can be shown live. The screenshots carry the links that cannot be shown live in five minutes.

What a crit is for

  • A conversation about one piece of work with the evidence in the room
  • People who were not there find the step that only holds because you remember it doing so
  • Find it now, while there is a week to fix it, rather than when the marker reaches it

A crit is not a presentation to be judged; it is a search for gaps by people who do not share your memory of the work. The gap they find is the one you would otherwise discover from the marker's comments. A week is enough time to add a link, gather a piece of evidence or write a limitation.

The chain has four links

  • The finding: a backlog row and the notes it points at
  • The measurement: rows of the metrics file and the figures computed from them
  • The fix: a commit
  • The verification: the regression checklist and the re-pilot
  • If one link has no file, you have found the gap before anyone else does

You present the four links in order, and each has a file behind it. The crit is the test of whether every link is a file or an assertion. Finding a missing file yourself, while preparing, is the best outcome of the preparation.

The evidence, not the person

  • "The focus ring is faint" is about the work
  • "You did not test it properly" is about you, and is not permitted here
  • The useful question asks to see something: which rows, which line of the notes, what the no-JS path did at the same point, what the screen reader said
  • A question that cannot be answered from a file is still useful: it tells the presenter what the portfolio is missing

The rule on the first two lines is the one the room holds to. The third line is the shape of a good question: it asks for a file, a row or a behaviour. The fourth is why unanswerable questions are kept, not deflected.

Prepare the chain

  • Choose the fix with the strongest measurement behind it, not the one you are proudest of
  • crit/outline.md: four headings, finding, measurement, fix, verification
  • Under each, the sentence you will say and the path of the file you will show
  • "Participants without JavaScript failed the edit task in two of six attempts", not "the edit task had problems"
  • Under a page; a prompt sheet, not a script

The outline is four sentences and four paths. Each sentence names the thing and the figure, so that a listener can check it against the file you show. If you fixed more than one thing, the one with the measurement wins.

Live, or a screenshot

  • Showing the fixed behaviour live is stronger than a picture, because a picture could be from any commit
  • Showing the broken behaviour live means checking out an earlier tag in your five minutes
  • The before screenshot carries that link
  • With a screen reader: test the volume in the room before your turn, and say what it announces as it announces it

Decide before the session what is live and what is a picture. The fix is live because that is the claim; the defect is a screenshot because the time is not there. The screen reader line is from experience: the people at the back will not hear it.

The format

  • Groups of five or six
  • Twelve minutes each: five to present, five for questions, two for the group to write
  • One person keeps time and says "two minutes" and "stop"
  • Agree the order at the start so nobody is surprised
  • The session fails when the first presenter takes twenty

Twelve minutes is tight on purpose. Five minutes holds one chain and not two, and the timekeeper's two words are the whole of their job. The order is agreed first so that nobody spends the session waiting to find out.

As the presenter

  • Say the four sentences from your outline in order, showing the file or the behaviour behind each
  • Narrate what is not visible: "I am pressing Tab; focus is on the Edit button; I press Enter"
  • When you have said the fourth sentence, stop, even with time left

The narration is for the people who cannot see your screen closely and for anyone in the room who cannot see it at all. Stopping early is permitted and stopping late is not. Five minutes is enough for one chain.

As a questioner

  • Ask for what you could not see
  • If the measurement was a rate, ask what the denominator was
  • If the fix was shown with JavaScript on, ask what the no-JS path does at the same point
  • If a screenshot stood in for a live step, ask which commit it came from
  • One question each, then a second round if there is time

Each of these asks for a file or a behaviour, which is what makes it answerable. The denominator question is the one that catches a rate with no rows behind it. If you think the fix might have broken something else, ask which regression check covers it.

Answering

  • From the evidence, or say that you cannot
  • "That is rows 41 to 46" is an answer
  • "I think it was about a third" is not
  • "I did not record that" is an honest answer you will act on
  • Do not argue: a question you disagree with is still one a marker could ask

Three kinds of answer, and the third is as good as the first if it is acted on. The written response is where you say why the evidence does not support a concern; the room is not. Arguing spends your five minutes and changes no file.

The written response

  • Three sentences per listener: what they saw, what they could not see, one question they would put to the portfolio
  • "What they saw" names a link in the chain and the file that carried it
  • "What they could not see" names a link that was asserted rather than shown
  • No name on it; it is going into a repository that must contain no names
  • crit/responses.md, one block per response, as given; do not tidy or summarise

The last two minutes of each turn are for writing, and the three sentences are the whole form. The chapter gives one example and marks it as illustrative rather than a response anyone gave. The responses are kept as given because the gaps they name are the evidence that you looked for gaps.

What the presenter records

  • crit/notes.md: for each question, what was asked, what you answered, what you will do
  • The evidence exists and the portfolio did not point at it: add the link
  • The evidence does not exist and can be gathered in the time left: gather it, and say where it will go
  • The evidence does not exist and cannot be gathered: write the limitation in a sentence
  • A question that leads to new work is a backlog row pointing at crit/notes.md

Write this after your turn, while you still remember the room. Three kinds of action cover every question, and the third is a sentence the portfolio states rather than something a reader discovers. The questions you could not answer are the most useful output of the day, and the portfolio chapter turns each into a link, a file or a stated limitation.

What goes wrong

  • The server is not running when your turn comes, because somebody stopped it to run their own: start yours before the session and leave that terminal alone
  • JavaScript is still off in the browser from your last parity check, so the HTMX path looks broken: check once before you begin
  • A screenshot that would have carried a link is on a laptop at home: the fallback for every live step is a file already in the repository
  • The first presenter takes twenty minutes

Three of these are fixed by checking before the session starts, and the fourth by the timekeeper. The repository is the fallback for everything: if it is not committed, it is not evidence you can show. Start your own server in your own terminal and do not touch anyone else's.

What to record

  • Commit crit/outline.md, crit/responses.md and crit/notes.md
  • Check that none of the three contains a name, a student number or an email address
  • Recording the session on video or audio is not part of this chapter
  • If your group wants to, everyone in the room consents first, and the recording stays out of the repository

Three files, and the usual check for personal data before they are committed. The questions you could not answer are carried into the portfolio chapter, where each becomes a link, a new file, or a stated limitation. A recording, if the group makes one, is personal data and is handled as the consent appendix says.
