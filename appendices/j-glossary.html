Appendix K: Glossary

This appendix defines the terms a reader of this book meets, each once, in alphabetical order.

Severity
The backlog's three-value column; its values are in Chapter 2.
Accessibility tree
The structure a browser builds from the page for assistive technologies: each element's role, name and state. A screen reader reads this, not the pixels, which is why a div styled as a button is not a button.
Alt text
The text an image carries in its alt attribute, read by a screen reader in the image's place. An image that decorates and says nothing has alt="", so it is skipped.
ARIA
Accessible Rich Internet Applications: HTML attributes such as role, aria-live, aria-describedby and aria-invalid that add meaning an element does not carry itself. The first rule of ARIA is to use the HTML element that already has the meaning.
aria-describedby
An attribute linking a control to the element whose text describes it, such as a hint or an error message, so that a screen reader reads the description when the control takes focus.
Audit
A review of a page against a standard, here WCAG 2.2, recording each defect against the success criterion it fails. Chapter 4 runs one.
axe DevTools
The browser extension from Deque that scans a page against its accessibility rules and lists what it found by rule, element and WCAG criterion. Installing it is in Appendix A; Chapter 4 runs it.
Backlog
The CSV file of things to fix, one row each, with the evidence that justifies the row. Its columns are defined in Chapter 2 and nowhere else.
Branch
A named line of commits in git. Your work lives on one called work, made from the starting tag as Appendix A says, and each chapter's tag is merged into it.
Browse mode and focus mode
The two states of a screen reader on a web page. In browse mode single keys move about the page, H to the next heading for instance; in focus mode keystrokes go to the control that has focus. The key that switches is in Appendix E.
Commit
A recorded snapshot of the files, with a message, on a branch; also the act of making one. Every chapter ends with one, and the portfolio's links resolve against a named commit.
Consent
A participant's agreement to take part after being told what will be recorded, kept and deleted, and that they can stop at any time. For a short interview between classmates spoken consent is enough; the form in Appendix H records that it was given.
Contrast ratio
The ratio between the luminance of text or a control and its background, from 1:1 to 21:1. WCAG asks 4.5:1 for normal text and 3:1 for large text, controls and focus indicators.
Cookie
A small named value the server asks the browser to keep and send back with every later request. The reference code sets one, sid, so that a participant's rows in the metrics file can be grouped; it holds a short random code, never a name, and Chapter 7 sets it to the participant code before a session.
Counterbalancing
Giving half the participants one order of conditions and half the other, so that the order effect falls evenly on both; Chapter 8 starts two participants with HTMX and two with JavaScript off.
Crit
A session in which one person presents one piece of work with its evidence and the audience responds to the evidence. Chapter 11.
CSS rule
A selector and a block of declarations, such as button { color: white }: the selector says which elements the rule applies to, and the declarations say what they look like. The reference code's own rules are in static/css/app.css, under the Pico stylesheet.
CSV
Comma-separated values: a plain-text table with one row per line and commas between the cells, which a spreadsheet opens and a program reads. The backlog, the metrics file and the regression record are all CSV.
curl
A command-line program that sends an HTTP request and prints the response; the chapters use it from a second terminal to see exactly what the server answers. Appendix A says where to run it on Windows.
Debounce
Waiting for a pause before acting, so that a stream of keystrokes produces one request rather than one per key; delay:300ms in the filter's hx-trigger is one.
Debrief
The conversation with a participant immediately after a pilot session, in which they say what was hard and why. Debrief notes carry the explanation that the metrics file cannot.
Developer tools
The panels every browser opens with F12: Network, Console, Elements and the accessibility pane among them. Appendix A says which the book uses and what for.
Diff
The lines that differ between two versions of the files, as git diff prints them: a line removed, a line added. A change is shown as its diff, and git diff <tag> <tag> shows what a chapter adds.
DOM
The Document Object Model: the tree of elements the browser builds from the HTML and that scripts, HTMX included, read and change. An automated checker reads it; a screen reader reads the accessibility tree built from it.
Error rate
The proportion of requests for a task that ended in an error, or of saves for the edit task. Defined with the other metrics in Appendix I.
Error summary
A block at the top of a form, after a failed submit, listing each error with a link to the field it belongs to. The plain path relies on it because there is no live region to announce the error.
Evidence chain
The four links from a finding to the measurement that showed it, the change that addressed it and the verification that the change worked, as Chapter 10 names them. Each link is a file, and each later link points back at the earlier one.
Facilitator
The person who runs a pilot session: reads the tasks, keeps time, does not help. The note-taker is the other person, writing down what the facilitator cannot watch for.
Finding
A paragraph in research/findings.md making a claim about what happened in the pilots, with its source: "participants without JavaScript failed the edit task in two of four saves", with the rows that show it. A backlog row points at a finding.
Focus
The one element on the page that receives keystrokes. Tab moves it forward and Shift-Tab back, and the focus ring shows where it is. A region that focus can enter and not leave is a keyboard trap. After a swap replaces the focused element, focus falls to the document unless something puts it elsewhere.
Fragment
A piece of HTML without the page around it, returned to an HTMX request and swapped into the page. The same template renders the fragment and the matching part of the full page.
Handler
The function a route runs to build its response: read the request, do the work, send the page or the fragment. In the reference code every handler answers both modes.
Heuristic
A rule of thumb for judging a design without testing it with people; Nielsen's ten usability heuristics are the set the book names, and the first, visibility of system status, is the one the status region serves.
Hex characters
The sixteen digits of base sixteen, 0 to 9 and a to f. The session cookie's default value is six of them.
Hosting service
Where a repository lives away from your machine: GitHub, GitLab or an institution's own forge. Your module names one; the portfolio's links are read on its web view.
HTML form
A <form> element with an action and a method, holding controls such as <input> and <button>; submitting it sends each control's name and value to the action's URL by that method. Every interaction in this book begins as one.
HTMX
A JavaScript library that lets HTML attributes such as hx-get, hx-post, hx-target and hx-swap make requests and swap the returned HTML into the page. The attributes the book uses are in Appendix D.
HX-Request
The header HTMX sends with every request it makes. The server uses it to decide between returning a fragment and a full page; a plain form submission does not carry it.
Hypermedia
HTML that carries its own controls, links and forms, telling the browser what can be done next. The server returns hypermedia, not data for a client to render; Hypermedia Systems is the long form of the argument.
Inclusion risk
The backlog column naming who is excluded by a defect; its values are in Chapter 2.
Instrumentation
Code in the server that records one row per request to a metrics file, with the task, outcome, duration and mode, and nothing that identifies a participant. Chapter 7 builds it.
Job story
A need written as a situation, a motivation, an outcome and the constraint behind them: "When ..., I want to ..., so I can ..., because ...". Chapter 2 uses the form in place of personas and user stories.
Ktor
The Kotlin web framework the reference code uses for routing and responses; its routing documentation is the reference for the calls the book names.
Landmark
A region of the page with a role a screen reader can jump to: header, nav, main, footer. The skip link targets the main landmark.
Level A, AA and AAA
WCAG's three conformance levels. Each success criterion has one: A is the minimum, AA is what this book works to, and AAA is beyond its scope.
Live region
An element with aria-live, or a role such as status or alert, whose changes a screen reader announces without focus moving. The status message after adding a task is one; it must be the same element before and after a swap or the announcement is lost.
MAD
Median absolute deviation: the median of each value's distance from the median. A measure of spread that one slow participant does not dominate, which is why the book pairs it with the median rather than using the mean and standard deviation.
Median
The middle value when the values are sorted, with half above it and half below. One extreme value does not pull it as it pulls the mean.
Metrics file
The CSV the instrumentation writes, one row per request. Its columns are defined once, in the reference code, and Chapter 7 says where.
Needs-finding
Finding out what people are trying to do and what stops them, by asking and watching, before deciding what to build.
Netty
The HTTP server engine that Ktor runs on. main starts it on the port and nothing else in the book touches it.
Order effect
The difference a second attempt makes because the participant has just done the task once; in a within-subject design it has to be counterbalanced and named when reporting.
Out-of-band swap
An element in an HTMX response marked hx-swap-oob, which HTMX swaps into the page by its id in addition to the main target. The book uses it to update the status message from any response.
Parity
The requirement that every task that can be completed with JavaScript on can be completed with it off, ending in the same state. Chapter 6 checks it.
Partial
A template that renders one part of a page, named with a leading underscore, included by the page template and rendered on its own for a fragment. Chapter 5 introduces them.
Participant
A person who takes part in an interview or a pilot. The book's word for them; not "user", "subject" or "tester".
Participant code
The code a participant is known by in every file, P1, P2 and so on, assigned when consent is given; a pseudonym in the data-protection sense (Appendix F). The only identity a participant has in the repository.
Pebble
The template engine the reference code uses to render HTML on the server. Its syntax is in Appendix C.
People-centred language
Naming the person and the situation rather than a label: "a person using a screen reader", not "a blind user". The situation is what the design has to work in, and it catches people the label would leave out.
Persona
A fictional person standing for a group of users, "a blind user" for instance. The book uses job stories instead, because a persona puts a label where the situation should be.
Personal data
Anything that identifies a living person, alone or with other information: a name, an email address, a student number, a face, a voice. The repository holds none of it; Appendix F has the rules.
Pilot
A session in which a participant attempts set tasks on the instrumented application while you take notes. Chapter 8 runs them; the first pilots evaluate, and the re-pilot verifies a fix.
Plain path
The way an interaction works with JavaScript off: a plain form submission, a server response and a full page. Every interaction in the book has one, and the enhanced path, with HTMX, is an enhancement of it.
Portfolio
The README of your repository and the files it links to, at a named tag. Chapter 12.
Post/Redirect/Get
The pattern in which a successful form POST answers with a redirect to a GET, so that refreshing the page fetches again rather than submitting again. Every form in the book ends this way on the plain path.
Prioritisation score
The score Chapter 2 defines from severity, the groups caught and the WCAG level, which Chapter 9 ranks by, with the cost of a change deciding between rows of equal score.
Progressive enhancement
Building the page so that HTML alone does the job, then adding CSS and JavaScript for the browsers that run them, without the baseline depending on the additions; the GOV.UK service manual requires it.
Query string
The part of a URL after ?, holding named values such as ?q=report&page=2. The reference code carries the filter, the page and an error code in it, never a message.
Re-pilot
A pilot run after a change, with the same tasks, to see whether the measurement moved.
README
The file at the root of a repository that its hosting service shows first. The portfolio is the README of your repository and the files it links to.
Redirect
A response that tells the browser to fetch another URL instead of showing a body, here always 303 See Other with a Location header after a successful form submission. The browser follows it with a GET.
Regression check
A check run after a change to confirm that something that worked still works. The twenty for this application are in Chapter 10.
Request header
A line a browser or script sends with a request, such as HX-Request: true, that describes the request without being part of its body. The server reads it to decide how to answer.
Route
A method and a path the server answers, with the handler that answers it: get("/tasks") in TaskRoutes.kt is one. Every route in the reference code has a plain and an enhanced answer.
Screen reader
Software that reads the accessibility tree aloud or to a braille display and lets a person navigate it from the keyboard. The book uses NVDA, VoiceOver and Orca, one per platform; installing them is in Appendix A.
Seed data
The tasks the list holds at the start of every pilot session, kept in research/seed-tasks.csv and copied back before each participant, so that every scenario names a task that is there.
Semantic HTML
Using the element that means the thing: button for an action, a for a link, label for a label, main for the main content. It gives the accessibility tree the right roles without ARIA.
Server-first
The approach in which the server renders every page and fragment and the browser is enhanced, not relied on. Chapter 1 makes the case.
Skip link
The first link on the page, visible when focused, that moves focus past the header to the main content (WCAG 2.4.1).
Status code
The three-digit number at the start of an HTTP response: 200 for a page or fragment, 303 for a redirect, 404 for nothing found, 405 for a method the route does not take. The reference code answers a failed validation with 200 on purpose, for the reason Chapter 6 gives.
Status message
Text that tells the person what just happened, such as the message after adding a task, without taking their focus. WCAG 4.1.3 asks that it is announced to a screen reader, which the live region does.
Success criterion
One testable statement in WCAG, numbered like 2.1.1, with a level. A defect is recorded against the criterion it fails.
Tag
A name for one commit in git. The reference code has a tag for each state the book teaches from; your portfolio is submitted at a tag you name.
Task code
The short identifier the instrumentation writes for each task a participant attempts, so that rows can be grouped by task. The codes are defined once, in the reference code.
Template
A file of HTML with placeholders that the server fills from a map of values before sending it; the reference code's templates are Pebble files under templates/. A partial is a template for one part of a page.
Think-aloud
A usability-testing method in which the participant narrates what they are doing and thinking. The book's pilots do not use it, because narrating changes the times being measured.
Time on task
How long a participant took to complete a task. Appendix I says how it is computed from the metrics file, and how it differs from the server's handling time for one request.
Usability
Whether people can use a thing to do what they set out to do: ISO 9241-11 defines it as effectiveness, efficiency and satisfaction, which the book measures as completion, time on task and confidence.
UUID
A universally unique identifier, a 36-character random id such as 00000000-0000-4000-8000-000000000001. Every task has one, so two tasks never share an id and an id says nothing about how many there are.
Validation
Checking submitted input on the server and returning the error with the form, in both paths. A check in the browser is an enhancement; the server's is the one that counts.
WCAG
The Web Content Accessibility Guidelines, version 2.2, the W3C recommendation the book audits against.
Within-subject design
An experimental design in which every participant experiences every condition, so that the comparison is between a person's own attempts rather than between two groups of people. Chapter 8 uses one, with the two modes as the conditions.
