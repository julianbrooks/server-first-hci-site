Appendix A: Setup

By the end of this appendix the reference code builds and serves on your own machine, you can switch JavaScript off and on in your browser, and the accessibility tools the book uses are installed.

You need three things: git, a browser, and an editor. Everything else is downloaded the first time the build runs: the Kotlin Toolchain, the JDK it compiles with, and the libraries. GitHub Codespaces is not supported.

A.1 Clone the starter and make a branch

The starter is the chapter-01-start tag of the reference repository; your module gives you the repository's address. Clone it, make a branch of your own from that tag, and check where you are:

git clone <repository address> server-first-hci
cd server-first-hci
git switch -c work chapter-01-start
git describe --tags

The last command prints chapter-01-start. Everything you write from here on, code and the files under research/ alike, is committed on work. The tags are states you bring into that branch, never states you check out and work on: a tag is read-only, so a commit made while one is checked out belongs to no branch and disappears from view at the next checkout, with one warning from git that is easy to miss.

Each chapter names the tag it works from. When a chapter tells you to bring a tag in, commit what you have and run, with that chapter's tag in place of this one:

git merge -X theirs chapter-03

-X theirs says that where your change and the tag's touch the same lines, the tag's version wins; everything else of yours is kept, and your version of the disputed lines stays in your history. That happens twice in the book, when your delete from Chapter 1 meets the reference's and when your audit fix from Chapter 4 meets the reference's, and each time the next chapter builds on the reference's version, which is why it wins. Afterwards git describe --tags prints a name that begins with the tag followed by the number of your own commits on top of it; if it begins with an earlier tag, the merge did not happen. When the compiler reports an unresolved reference, this is the first thing to check.

Your branch needs a home other than your machine. Create an empty repository of your own on the hosting service your module names, keep the reference repository as the place the tags come from, and point origin at yours:

git remote rename origin reference
git remote add origin <your repository address>
git push -u origin work

From then on git push sends your branch to your repository, and git fetch reference --tags brings in any tag the reference adds.

A.2 Build, run and stop

./kotlin run

kotlin is a script in the repository, the Kotlin Toolchain's wrapper, and it pins the Toolchain version the module was tested with. The first run downloads that Toolchain, then the JDK named in toolchain.module-template.yaml, then every library module.yaml declares; expect a few minutes and a few hundred megabytes, and these two lines early on:

This is the first run of the Kotlin CLI v0.13.0, so we need to download the Kotlin Toolchain.
Downloading https://github.com/adoptium/temurin25-binaries/releases/download/...

Later runs start in seconds. When the server is up the terminal shows two lines from Ktor:

Application started in 0.492 seconds.
Responding at http://0.0.0.0:8080

Open http://localhost:8080/tasks. The port is set once, in Main.kt, which reads the PORT environment variable and falls back to 8080:

/** Starts the server. The port comes from the PORT environment variable and defaults to 8080. */
fun main() {
    val port = System.getenv("PORT")?.toIntOrNull() ?: 8080
    embeddedServer(Netty, port = port, host = "0.0.0.0") { module() }.start(wait = true)
}

Stop the server with Ctrl-C in the terminal that is running it. A template edit is picked up on the next page load; a Kotlin edit needs the server stopped and started again.

You do not install a JDK. The Toolchain downloads the one the module file asks for into its own cache and uses it whatever java -version says on your machine, so a JDK already installed for another module does no harm. On Windows the wrapper is kotlin.bat, and the commands in this book are typed as kotlin run without the ./.

Four failures accounted for most of the time lost in the 2025 run.

Address already in use: a server from last time is still running, usually in a terminal you closed without stopping it. Find and stop it, or run on another port for now with PORT=8081 ./kotlin run and open the page on that port.

./kotlin: Permission denied: the wrapper script has lost its execute bit, which happens when a repository is copied or unzipped rather than cloned. chmod u+x kotlin fixes it; sh kotlin run works without fixing it.

The download hangs, or fails with curl: (28) or Could not download: the machine reaches the network through a proxy, which is the normal case on institutional lab machines. The wrapper's own download honours the shell's HTTPS_PROXY variable, and the Toolchain's downloads take the proxy as Java options, so set both for one terminal:

export HTTPS_PROXY=http://<host>:<port>
export KOTLIN_CLI_JAVA_OPTIONS="-Dhttps.proxyHost=<host> -Dhttps.proxyPort=<port>"

Whoever runs the network has the host and port. The Toolchain keeps everything it downloads under ~/.cache/JetBrains/Kotlin on Linux, ~/Library/Caches/JetBrains/Kotlin on macOS and %LOCALAPPDATA%\JetBrains\Kotlin on Windows, so a cache warmed once, on another network or by the module team before the lab, is enough for a run that downloads nothing.

A blank page or a 500: read the terminal. Pebble names the template file and the line for a syntax error, and a Kotlin exception has a stack trace whose first lines name the route.

A.3 Tests

./kotlin test

compiles everything and runs the tests under src/test; ./kotlin build compiles without running them. The route tests run every route in both modes against a temporary store, so a change that breaks the path that works with JavaScript off fails here before you reach a browser.

A.4 A second terminal and the developer tools

Several chapters check a route with curl from a second terminal while the server runs in the first. On Linux and macOS it is installed. On Windows run those commands in Git Bash, which came with git; the curl in PowerShell is an alias for a different command and rejects the options the chapters use.

The browser's developer tools open with F12, or Cmd-Option-I on a Mac, and the chapters use four of their panels. Network lists every request the page makes with its type, status and headers; click a request to read them. Console takes a line of JavaScript at its prompt. Elements, called Inspector in Firefox, shows the markup, and beside its Styles pane an Accessibility pane shows the name, role and state the selected element gives to assistive technology; Firefox has an Accessibility tab that shows the whole tree. The axe DevTools extension, below, adds a tab of its own.

A.5 Gradle

The repository also carries a Gradle build, build.gradle.kts, describing the same code from the same version catalogue, and ./gradlew build and ./gradlew run do what the kotlin commands above do. You do not need it: no command in this book is a Gradle command. It is there because IntelliJ IDEA imports the project through it and because the module's continuous integration builds every tag with both tools, so a tree that passes one and not the other is a defect in the repository, not on your machine. If you do run it, know that the Gradle wrapper needs a Java runtime on the machine before Gradle itself can start, and only then fetches the JDK the build compiles with. On a machine with none you see:

ERROR: JAVA_HOME is not set and no 'java' command could be found in your PATH.

The JDK the Toolchain downloaded will do. Point JAVA_HOME at it for one terminal, on Linux or macOS:

export JAVA_HOME=$(ls -d ~/.cache/JetBrains/Kotlin/extract.cache/*/jdk-25* | head -1)

A.6 Four lines of warning

On JDK 25 the server prints four lines beginning WARNING: A restricted method in java.lang.System has been called as it starts, whichever way you ran it. Ktor's request-logging plugin depends on a console library, jansi, which loads native code, and JDK 25 announces every such load it has not been told to allow. The lines are a notice, not an error, and the server behind them is fine; they go when Ktor's next release addresses them.

A.7 An editor

Visual Studio Code: open the repository folder (File, Open Folder) and install the Kotlin extension when prompted, or from the Extensions view. Run the build from the integrated terminal (Terminal, New Terminal); the commands above are the whole interface, and no other extension is needed for this book.

IntelliJ IDEA (the Community Edition is enough): choose Open and select the folder. If IDEA opens it as a plain directory, which it did on a machine with no Java installed, right-click build.gradle.kts in the Project pane and choose Link Gradle Project; that is what the Gradle build is for in the editor. It then asks for a JDK: choose Add JDK and browse to the one the Toolchain downloaded, under ~/.cache/JetBrains/Kotlin/extract.cache/ in the folder whose name ends jdk-25.0.4.1+1, or choose Download JDK and take Temurin 25. Set the same JDK under Settings, Build Tools, Gradle, Gradle JVM. Run from the gutter icon beside fun main in Main.kt, or from the terminal with ./kotlin run as above. JetBrains also publish a Kotlin Toolchain plugin that opens module.yaml directly; its documentation recommends an early-access build of IDEA, so this book does not depend on it.

A.8 JavaScript off

Every chapter has a check with JavaScript off. Both browsers have a DevTools setting that lasts only while DevTools is open, and Firefox also has a switch that stays.

Firefox: open DevTools (F12), open its settings (F1 while DevTools has focus) and tick "Disable JavaScript" under Advanced settings; it reverts when DevTools closes. For a switch that stays, type about:config in the address bar, search for javascript.enabled and toggle it to false; set it back to true when you have finished. Mozilla documents the settings panel here.

Chrome: open DevTools (F12), press Ctrl-Shift-P (Cmd-Shift-P on macOS), type "Disable JavaScript" and press Enter; the same setting is under Settings, Preferences, Debugger. It reverts when DevTools closes. Google documents it here.

Reload the page after switching. Whether it took effect is visible in the Network tab: with JavaScript off, submitting a form produces a document request and a redirect, not a request carrying the HX-Request header. The usual mistake is closing DevTools between the switch and the test, which switches JavaScript back on.

A.9 axe DevTools

The automated scan in Appendix E uses axe DevTools, a browser extension from Deque with a free tier. Install it from your browser's extension store, for Chrome or Firefox; it appears as a tab in DevTools.

A.10 A screen reader

One per platform. NVDA on Windows, free from NV Access. VoiceOver on macOS, built in. Orca on a Linux desktop running GNOME, usually installed already; its manual covers the rest. The keys that start each one and how to use it for a test are in Appendix E.
