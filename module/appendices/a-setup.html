Appendix A: Setup

By the end of this appendix the reference code builds and serves on your own machine, you can switch JavaScript off and on in your browser, and the accessibility tools the book uses are installed.

You need four things: a JDK, git, a browser, and an editor. Everything else, including Gradle itself and the libraries, is downloaded by the build the first time it runs. GitHub Codespaces is not supported.

A.1 JDK 21

The build asks for Java 21 (jvmToolchain(21) in build.gradle.kts), and a machine without a 21 installation gets an error naming the version it wanted. Install Temurin 21 from Adoptium or a 21 build from your operating system's packages, then check in a new terminal:

java -version

The first line should say 21. If it says another version, another JDK is first on your PATH or JAVA_HOME points at one. The wrapper reports a wrong JAVA_HOME in its own words:

ERROR: JAVA_HOME is set to an invalid directory: /nonexistent

Point JAVA_HOME at the 21 installation or unset it and let the wrapper find java on the path. On a lab machine where you cannot change the environment permanently, set it for one terminal: export JAVA_HOME=/path/to/jdk-21 on Linux or macOS. A build that fails with Unsupported class file major version is the same problem from the other side: something compiled with 21 is being run by an older JDK.

A.2 Clone the starter

The starter is the week-06-start tag of the reference repository; your module gives you the repository's address. Clone it and check out the tag:

git clone <repository address> server-first-hci
cd server-first-hci
git checkout week-06-start
git describe --tags

The last command prints the tag you are on. Each chapter names the tag it works from, and the first thing to check when the compiler reports an unresolved reference is whether you are on it.

A.3 Build, run and stop

./gradlew run

The first run downloads the Gradle distribution named in gradle/wrapper/gradle-wrapper.properties, then every library the build declares; expect a few minutes and a few hundred megabytes. Later runs start in seconds. When the server is up the terminal shows two lines from Ktor:

Application started in 0.928 seconds.
Responding at http://0.0.0.0:8080

Open http://localhost:8080/tasks. The port is set once, in Main.kt, which reads the PORT environment variable and falls back to 8080:

/** Starts the server. The port comes from the PORT environment variable and defaults to 8080. */
fun main() {
    val port = System.getenv("PORT")?.toIntOrNull() ?: 8080
    embeddedServer(Netty, port = port, host = "0.0.0.0") { module() }.start(wait = true)
}

Stop the server with Ctrl-C in the terminal that is running it. A template edit is picked up on the next page load; a Kotlin edit needs the server stopped and started again.

Four failures account for most of the lab time lost in 2025.

Address already in use: a server from last time is still running, usually in a terminal you closed without stopping it. Find and stop it, or run on another port for now with PORT=8081 ./gradlew run and open the page on that port.

./gradlew: Permission denied: the wrapper script has lost its execute bit, which happens when a repository is copied or unzipped rather than cloned. chmod u+x gradlew fixes it; sh gradlew run works without fixing it.

The download hangs, or fails with Could not download or Could not resolve: the machine reaches the network through a proxy that Gradle does not know about, which is the normal case on institutional lab machines. Put the proxy in ~/.gradle/gradle.properties:

systemProp.https.proxyHost=<host>
systemProp.https.proxyPort=<port>

The module team has the host and port. A Gradle cache warmed once, on another network or by the module team before the lab, is enough for a run that downloads nothing.

A blank page or a 500: read the terminal. Pebble names the template file and the line for a syntax error, and a Kotlin exception has a stack trace whose first lines name the route.

A.4 Tests

./gradlew test

runs the tests under src/test; ./gradlew build runs them and compiles everything else as well. The route tests run every route in both modes against a temporary store, so a change that breaks the no-JS path fails here before you reach a browser.

A.5 An editor

Visual Studio Code: open the repository folder (File, Open Folder) and install the Kotlin extension when prompted, or from the Extensions view. Run the build from the integrated terminal (Terminal, New Terminal); the commands above are the whole interface, and no other extension is needed for this book.

IntelliJ IDEA (the Community Edition is enough): choose Open and select the folder, and IDEA detects the Gradle project and imports it. Then check two settings: under File, Project Structure, Project, the SDK is a JDK 21; and under Settings, Build, Execution, Deployment, Build Tools, Gradle, the Gradle JVM is the same 21. When the two differ the build fails inside the IDE and passes in the terminal, which is confusing until you know where to look. Run from the gutter icon beside fun main in Main.kt, or from the terminal as above.

A.6 JavaScript off

Every chapter has a check with JavaScript off. Both browsers have a DevTools setting that lasts only while DevTools is open, and Firefox also has a switch that stays.

Firefox: open DevTools (F12), open its settings (F1 while DevTools has focus) and tick "Disable JavaScript" under Advanced settings; it reverts when DevTools closes. For a switch that stays, type about:config in the address bar, search for javascript.enabled and toggle it to false; set it back to true when you have finished. Mozilla documents the settings panel here.

Chrome: open DevTools (F12), press Ctrl-Shift-P (Cmd-Shift-P on macOS), type "Disable JavaScript" and press Enter; the same setting is under Settings, Preferences, Debugger. It reverts when DevTools closes. Google documents it here.

Reload the page after switching. Whether it took effect is visible in the Network tab: with JavaScript off, submitting a form produces a document request and a redirect, not a request carrying the HX-Request header. The usual mistake is closing DevTools between the switch and the test, which switches JavaScript back on.

A.7 axe DevTools

The automated scan in Appendix E uses axe DevTools, a browser extension from Deque with a free tier. Install it from your browser's extension store, for Chrome or Firefox; it appears as a tab in DevTools.

A.8 A screen reader

One per platform. NVDA on Windows, free from NV Access. VoiceOver on macOS, built in and toggled with Cmd-F5. Orca on a Linux desktop running GNOME, usually installed already and toggled with Super-Alt-S, or started with orca in a terminal when the shortcut is not bound; its manual covers the rest. How to use each one for a test is in Appendix E.
