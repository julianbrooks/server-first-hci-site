Appendix K: Glossary

This appendix defines the terms a reader of this book meets, each once, in alphabetical order.

Accessibility tree
The structure a browser builds from the page for assistive technologies: each element's role, name and state. A screen reader reads this, not the pixels, which is why a div styled as a button is not a button.
ARIA
Accessible Rich Internet Applications: HTML attributes such as role, aria-live, aria-describedby and aria-invalid that add meaning an element does not carry itself. The first rule of ARIA is to use the HTML element that already has the meaning.
aria-describedby
An attribute linking a control to the element whose text describes it, such as a hint or an error message, so that a screen reader reads the description when the control takes focus.
Audit
A review of a page against a standard, here WCAG 2.2, recording each defect against the success criterion it fails. Chapter 4 runs one.
Backlog
The CSV file of things to fix, one row each, with the evidence that justifies the row. Its columns are defined in Chapter 2 and nowhere else.
Browse mode and focus mode
The two states of a screen reader on a web page. In browse mode single keys move about the page, H to the next heading for instance; in focus mode keystrokes go to the control that has focus. The key that switches is in Appendix E.
Consent
A participant's agreement to take part after being told what will be recorded, kept and deleted, and that they can stop at any time. For a short interview between classmates spoken consent is enough; the form in Appendix H records that it was given.
Contrast ratio
The ratio between the luminance of text or a control and its background, from 1:1 to 21:1. WCAG asks 4.5:1 for normal text and 3:1 for large text, controls and focus indicators.
Crit
A session in which one person presents one piece of work with its evidence and the audience responds to the evidence. Chapter 11.
Debrief
The conversation with a participant immediately after a pilot session, in which they say what was hard and why. Debrief notes carry the explanation that the metrics file cannot.
Error rate
The proportion of attempts at a task that ended in an error. Defined with the other metrics in Appendix I.
Error summary
A block at the top of a form, after a failed submit, listing each error with a link to the field it belongs to. The no-JS path relies on it because there is no live region to announce the error.
Evidence chain
The links from data to finding to fix to verification. Each link is a file, and each later link points back at the earlier one. The assessment is marked on whether the chains close.
Finding
A claim about what happened in the pilots, with its source: "participants without JavaScript failed the edit task in two of six attempts", with the rows that show it.
Focus
The one element on the page that receives keystrokes. Tab moves it forward and Shift-Tab back, and the focus ring shows where it is. A region that focus can enter and not leave is a keyboard trap. After a swap replaces the focused element, focus falls to the document unless something puts it elsewhere.
Fragment
A piece of HTML without the page around it, returned to an HTMX request and swapped into the page. The same template renders the fragment and the matching part of the full page.
HTMX
A JavaScript library that lets HTML attributes such as hx-get, hx-post, hx-target and hx-swap make requests and swap the returned HTML into the page. The attributes the book uses are in Appendix D.
HX-Request
The header HTMX sends with every request it makes. The server uses it to decide between returning a fragment and a full page; a plain form submission does not carry it.
Hypermedia
HTML that carries its own controls, links and forms, telling the browser what can be done next. The server returns hypermedia, not data for a client to render (Gross, Stepinski and Akşimşek, 2023).
Inclusion risk
The backlog column naming who is excluded by a defect: a person using a screen reader, navigating by keyboard, with low vision, under cognitive load or with a motor impairment.
Instrumentation
Code in the server that records one row per request to a metrics file, with the task, outcome, duration and mode, and nothing that identifies a participant. Chapter 7 builds it.
Job story
A need written as a situation, a motivation, an outcome and the constraint behind them: "When ..., I want to ..., so I can ..., because ...". Chapter 2 uses the form in place of personas and user stories.
Ktor
The Kotlin web framework the reference code uses for routing and responses.
Landmark
A region of the page with a role a screen reader can jump to: header, nav, main, footer. The skip link targets the main landmark.
Level A, AA and AAA
WCAG's three conformance levels. Each success criterion has one: A is the minimum, AA is what this book works to, and AAA is beyond its scope. The assessment fails a submission with a Level A failure remaining.
Live region
An element with aria-live, or a role such as status or alert, whose changes a screen reader announces without focus moving. The status message after adding a task is one; it must be the same element before and after a swap or the announcement is lost.
MAD
Median absolute deviation: the median of each value's distance from the median. A measure of spread that one slow participant does not dominate, which is why the book pairs it with the median rather than using the mean and standard deviation.
Median
The middle value when the values are sorted, with half above it and half below. One extreme value does not pull it as it pulls the mean.
Metrics file
The CSV the instrumentation writes, one row per request. Its columns are defined once, in the reference code, and Chapter 7 says where.
Needs-finding
Finding out what people are trying to do and what stops them, by asking and watching, before deciding what to build.
No-JS path
The way an interaction works with JavaScript off: a plain form submission, a server response and a full page. Every interaction in the book has one, and the HTMX path is an enhancement of it.
Out-of-band swap
An element in an HTMX response marked hx-swap-oob, which HTMX swaps into the page by its id in addition to the main target. The book uses it to update the status message from any response.
Parity
The requirement that every task that can be completed with JavaScript on can be completed with it off, ending in the same state. Chapter 6 checks it.
Partial
A template that renders one part of a page, named with a leading underscore, included by the page template and rendered on its own for a fragment. Chapter 5 introduces them.
Participant
A person who takes part in an interview or a pilot. The book's word for them; not "user", "subject" or "tester".
Participant code
The pseudonym a participant is known by in every file, P1, P2 and so on, assigned when consent is given. The only identity a participant has in the repository.
Pebble
The template engine the reference code uses to render HTML on the server. Its syntax is in Appendix C.
People-centred language
Naming the person and the situation rather than a label: "a person using a screen reader", not "a blind user". The situation is what the design has to work in, and it catches people the label would leave out.
Personal data
Anything that identifies a living person, alone or with other information: a name, an email address, a student number, a face, a voice. The repository holds none of it; Appendix F has the rules.
Pilot
A session in which a participant attempts set tasks on the instrumented application while you take notes. Chapter 8 runs them; the first pilots evaluate, and the re-pilot verifies a fix.
Portfolio
The README of your repository and the files it links to, at a named tag. Chapter 12.
Post/Redirect/Get
The pattern in which a successful form POST answers with a redirect, 303 See Other, to a GET, so that refreshing the page fetches again rather than submitting again. Every no-JS form in the book ends this way.
Prioritisation score
Impact plus inclusion minus effort, each on a small scale, used in Chapter 9 to rank findings. The simpler severity score in Chapter 2 is used before there are measurements.
Progressive enhancement
Building the page so that HTML alone does the job, then adding CSS and JavaScript for the browsers that run them, without the baseline depending on the additions (Government Digital Service, no date).
Regression check
A check run after a change to confirm that something that worked still works. The twenty for this application are in Chapter 10.
Re-pilot
A pilot run after a change, with the same tasks, to see whether the measurement moved.
Screen reader
Software that reads the accessibility tree aloud or to a braille display and lets a person navigate it from the keyboard. The book uses NVDA, VoiceOver and Orca, one per platform; installing them is in Appendix A.
Semantic HTML
Using the element that means the thing: button for an action, a for a link, label for a label, main for the main content. It gives the accessibility tree the right roles without ARIA.
Server-first
The approach in which the server renders every page and fragment and the browser is enhanced, not relied on. Chapter 1 makes the case.
Session cookie
The cookie that identifies a browser session to the server so that a participant's rows in the metrics file can be grouped. It carries a short random code, never a name.
Severity
The backlog's three-value column: high blocks a task or excludes a group, medium makes a task harder, low is cosmetic.
Skip link
The first link on the page, visible when focused, that moves focus past the header to the main content (WCAG 2.4.1).
Status message
Text that tells the person what just happened, such as "Task added", without taking their focus. WCAG 4.1.3 asks that it is announced to a screen reader, which the live region does.
Success criterion
One testable statement in WCAG, numbered like 2.1.1, with a level. A defect is recorded against the criterion it fails.
Tag
A name for one commit in git. The reference code has a tag for each state the book teaches from; your portfolio is submitted at a tag you name.
Task code
The short identifier the instrumentation writes for each task a participant attempts, so that rows can be grouped by task. The codes are defined once, in the reference code.
Time on task
How long a participant took to complete a task. Appendix I says how it is computed from the metrics file, and how it differs from the server's handling time for one request.
Validation
Checking submitted input on the server and returning the error with the form, in both paths. A check in the browser is an enhancement; the server's is the one that counts.
WCAG
The Web Content Accessibility Guidelines, version 2.2, the W3C recommendation the book audits against (W3C, 2023).
Government Digital Service (no date) “Building a robust frontend using progressive enhancement.” GOV.UK Service Manual. Available at: https://www.gov.uk/service-manual/technology/using-progressive-enhancement (Accessed: October 4, 2026).
Gross, C., Stepinski, A. and Akşimşek, D. (2023) Hypermedia systems. Independently published. Available at: https://hypermedia.systems/ (Accessed: October 4, 2026).
