Appendix I: Evaluation metrics

This appendix defines each metric the book reports, says how it is computed from the metrics log, and ends with a quick reference. The log's columns are defined once, in Chapter 7; this page names columns and does not redefine them.

I.1 The metrics

Time on task is the time between the participant being given a task and finishing it, in seconds. The log gives the finishing point exactly: the timestamp of the request that completed the task, which the evaluation plan names for each task. It gives the starting point only approximately: the timestamp of the previous request for that session, which is the end of the previous task or the page load before the first. Time on task from the log is the gap between those two, and it includes the facilitator reading the scenario and the participant thinking before acting. That is the same for every task and both modes, so the within-subject comparison is unaffected; the absolute numbers are a few seconds high and should be described as such. Report the median and the median absolute deviation, defined below, never the mean.

The ms column is not time on task. It is the time the server spent handling one request, in milliseconds, and in this application it is tens of milliseconds whatever the participant is doing. It answers one question only: whether a change you made slowed the server down. The 2025 text treated it as time on task and read a median of 1,899 milliseconds as nineteen seconds; it was under two seconds of server time and said nothing about the participant.

Error rate is the number of requests for a task that did not succeed, divided by the total number of requests for that task, within one mode. The numerator is the rows for that task code whose step is not success; in a pilot that means the validation_error rows, since the other two steps indicate a broken server rather than a participant. The denominator is all rows for that task code. State both numbers: "2 of 6" says what "0.33" hides, which is that one more error would have made it a half. Alongside the rate, report how many participants hit at least one error, which the session_id column gives, since one person failing three times and three people failing once are different findings.

Errors the server cannot see, such as deleting the wrong task, come from the notes and are reported separately with their own denominator, the number of attempts the note-taker observed. Do not add the two kinds together.

Completion is whether the participant reached the success criterion in the plan, judged by the facilitator: completed, completed after help, or not completed. The log cannot judge it, because a server that deleted the wrong task has succeeded. Report it as a count out of four for each task and mode.

Confidence is the participant's answer, from one to five, to "how confident are you that that worked?", asked after each task. Report the four answers for each task and mode as they are; with four numbers a median is already a summary, and a mean implies a precision the scale does not have. Low confidence after a completed task is a finding about feedback.

This book does not use a questionnaire such as SUS. Ten items at the end of a twenty-minute session with four people yield a score with nothing to compare it against.

I.2 Median and MAD

The median of a set of values is the middle value when they are sorted, or the mean of the two middle values when the count is even. The median absolute deviation, MAD, is the median of each value's distance from the median:

MAD = median( |x - median(x)| )

Take the five participants' time on task for the first successful add in the example data at the week-10 tag, computed from the gap between each participant's page load and the T3_add row that succeeded: 25, 27, 44, 37 and 8 seconds. Sorted, they are 8, 25, 27, 37, 44, and the median is 27. The distances from 27 are 2, 0, 17, 10 and 19; sorted, 0, 2, 10, 17, 19, and the MAD is 10. The mean of the same five values is 28.2 and the sample standard deviation 13.7. Without the one participant who took eight seconds, the mean of the other four is 33.3, so one person moved it by five seconds, and most of that standard deviation is that one person's distance from the rest. With four or five values, one unusual participant moves the mean by as much as everyone else put together, and a standard deviation of five values estimates a quantity five values cannot estimate. The median and MAD describe the middle of what happened and are not moved by one person.

tools/Analyse.kt at the week-10 tag computes both:

tools/Analyse.kt
fun median(values: List<Double>): Double {
    if (values.isEmpty()) return Double.NaN
    val sorted = values.sorted()
    val middle = sorted.size / 2
    return if (sorted.size % 2 == 1) sorted[middle] else (sorted[middle - 1] + sorted[middle]) / 2
}

/** Median absolute deviation: the median distance from the median, a spread measure that outliers do not distort. */
fun mad(values: List<Double>): Double {
    if (values.isEmpty()) return Double.NaN
    val centre = median(values)
    return median(values.map { abs(it - centre) })
}

Note what the tool applies them to. It groups the log by task code and mode and reports the median and MAD of ms, the server time, together with the error rate as defined above:

tools/Analyse.kt
data class Summary(
    val taskCode: String,
    val jsMode: String,
    val successes: Int,
    val medianMs: Double,
    val madMs: Double,
    val errors: Int,
) {
    /** Errors as a share of all requests for this task code and mode. */
    val errorRate: Double
        get() = if (successes + errors == 0) Double.NaN else errors.toDouble() / (successes + errors)
}

Run it with ./gradlew analyse, or with -Pfile=data/example-metrics.csv to read another file. It does not compute time on task, because which row ends a task is a judgement the plan makes and the tool does not know; Chapter 9 does that part from the timestamps.

I.3 Reporting a within-subject comparison

Four participants did every task in both modes. For each task, the report is one table with a row per participant and columns for time on task in each mode and the difference, and a sentence under it. The sentence says how many of the four were faster in which mode and by how much, and names anyone who went the other way: "Three of four were faster with HTMX, by 4 to 11 seconds; P2 was 2 seconds slower." The same for errors: "Two of four made a validation error without JavaScript and none did with it; both errors were a blank title on the second edit." That is an effect described. It is not an effect tested. With four participants a hypothesis test has almost no power and a p-value says nothing a reader can use, so the book does not report one; it says what was seen, in whom, and how large it was, and lets the reader weigh it.

Say what the design cannot separate. Two participants did each order, so an order effect and a mode effect of similar size look alike; if the two who started without JavaScript were also the two who were slower with it, say so.

The example data at week-10 is between-subject, one mode per participant, and was generated before this design was settled; use it to practise the arithmetic, not as a model of the report.
