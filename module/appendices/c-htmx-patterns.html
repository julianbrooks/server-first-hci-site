Appendix D: HTMX patterns

This appendix collects the HTMX attributes and request patterns the book uses, with the accessible inline edit as the worked example.

HTMX is a script that reads hx- attributes on HTML elements, makes the request they describe, and swaps the HTML that comes back into the page (Big Sky Software, no date b). The reference code uses version 2.0.11, served by the application from static/js/htmx.min.js rather than a CDN. Nothing in the application depends on it: every form and link also carries the plain attributes a browser uses, and Chapter 6 is the check that they work. What follows is every attribute the code uses, where it uses it, and one worked example per pattern, included from a tag.

D.1 The request header

src/main/kotlin/Templating.kt
/**
 * True when HTMX made the request and wants a fragment back. HTMX also sends HX-Request
 * when it restores a page from history, but then it expects the full page, so that case
 * returns false.
 */
fun ApplicationCall.isHtmxRequest(): Boolean =
    request.headers["HX-Request"] == "true" && request.headers["HX-History-Restore-Request"] != "true"

HTMX sends HX-Request: true on every request it makes, and that header is how the server knows to answer with a fragment. When HTMX restores a page from history and has no saved copy, it requests the URL again with HX-History-Restore-Request: true and wants the whole page, which is why the function returns false then. A URL that answers both ways sends Vary: HX-Request, as listTasks does in Chapter 5.

D.2 The attributes

Attribute Does Where the code uses it
hx-get, hx-post, hx-delete Issue a request with that method to the URL, on the element's natural event: submit for a form, click for a link or button Every form and link in tasks/
hx-target CSS selector for the element to swap into; without it, the element itself #task-list, #task-<id>, #task-area
hx-swap How to swap: innerHTML is the default; outerHTML replaces the target; afterbegin and beforeend insert inside it outerHTML on rows; afterbegin for a new row at week-06-start
hx-swap-oob On an element in the response: take it out of band. "true" replaces the page element with the same id; "innerHTML:#status" puts the element's content inside #status _add_form.peb, _status.peb
hx-trigger The event that fires the request, with modifiers: changed, delay:300ms, from:<selector>; several events separated by commas The filter form
hx-push-url "true" pushes the request URL into the browser history after the swap The pager and the filter form
hx-confirm Shows a browser confirm() with the text and sends only if it is accepted The delete form
hx-history-elt Marks the element HTMX saves and restores when the back button returns to a pushed URL #task-area
hx-on:<event> Runs inline JavaScript on an event; hx-on::after-request is shorthand for hx-on:htmx:after-request Not used; see below
hx-indicator Names an element to show while a request is in flight Not used; requests here are too quick to need it
hx-disabled-elt Disables elements while a request is in flight Not used
hx-boost Makes every link and form inside an element use HTMX, with the full page as the response Not used; the forms carry both sets of attributes instead
hx-include, hx-vals Add fields or values to a request Not used; hidden fields carry the filter and page

D.3 A form that works both ways

src/main/resources/templates/tasks/_add_form.peb
  <form action="/tasks" method="post" hx-post="/tasks" hx-target="#task-area">
    <input type="hidden" name="q" value="{{ query }}">
    <label for="task-title">Title</label>
    <input type="text" id="task-title" name="title" value="{{ addTitle }}"
           aria-describedby="title-hint{% if addError %} add-error{% endif %}"{% if addError %} aria-invalid="true"{% endif %}>
    <small id="title-hint">Between {{ minTitleLength }} and {{ maxTitleLength }} characters.</small>
    <button type="submit" id="add-button">Add task</button>
  </form>

action and method are the browser's; hx-post and hx-target are HTMX's. The URL is the same in both, so one handler answers both and branches on the header. Chapter 1 follows this form through both modes.

D.4 Inline edit

The pattern the book uses as its worked example is a row that becomes a form and back. The Edit control is a form so that it has a plain path.

src/main/resources/templates/tasks/_item.peb
    <form action="/tasks" method="get"
          hx-get="/tasks/{{ task.id }}/edit" hx-target="#task-{{ task.id }}" hx-swap="outerHTML">
      <input type="hidden" name="edit" value="{{ task.id }}">
      <button type="submit" class="secondary" aria-describedby="task-title-{{ task.id }}">Edit</button>
    </form>

The browser GETs /tasks?edit=<id> and gets the list page with that row as a form; HTMX GETs /tasks/<id>/edit and gets the form on its own, which replaces the <li> because the target is the row and the swap is outerHTML.

src/main/resources/templates/tasks/_edit.peb
<li id="task-{{ task.id }}" class="task task-editing">
  <form action="/tasks/{{ task.id }}/edit" method="post"
        hx-post="/tasks/{{ task.id }}/edit" hx-target="#task-{{ task.id }}" hx-swap="outerHTML">
    <label for="title-{{ task.id }}">Title</label>
    <input type="text" id="title-{{ task.id }}" name="title" value="{{ editTitle }}" autofocus
           aria-describedby="hint-{{ task.id }}{% if editError %} error-{{ task.id }}{% endif %}"{% if editError %} aria-invalid="true"{% endif %}>
    <small id="hint-{{ task.id }}">Between {{ minTitleLength }} and {{ maxTitleLength }} characters.</small>
    {% if editError %}<p id="error-{{ task.id }}" class="error-message" role="alert">{{ editError }}</p>{% endif %}
    <div class="task-actions">
      <button type="submit">Save</button>
      <a href="/tasks" hx-get="/tasks/{{ task.id }}/view" hx-target="#task-{{ task.id }}" hx-swap="outerHTML">Cancel</a>
    </div>
  </form>
</li>

The form has the same <li> id as the row it replaced, so the response to Save, which is the row again, swaps back over it. autofocus on the field is honoured by HTMX when it swaps the content in, and by the browser on a full page load. Cancel is a plain link to the list with an hx-get for the view row. The handler is short because the templates carry the pattern.

src/main/kotlin/routes/TaskRoutes.kt
/** HTMX gets the edit form in place of the item; without JavaScript the list page opens with that task in edit mode. */
private suspend fun ApplicationCall.editTask(store: TaskStore) {
    val task = store.getById(parameters["id"].orEmpty()) ?: return respond(HttpStatusCode.NotFound)
    if (isHtmxRequest()) {
        respondHtml(renderTemplate("tasks/_edit.peb", editContext(task, task.title)))
    } else {
        seeOther(tasksPath(edit = task.id))
    }
}

Chapter 3 walks through the error path and the checks with a keyboard and a screen reader.

D.5 Updating the live region out of band

src/main/resources/templates/tasks/_status.peb
{# Swapped into the live region in the layout. innerHTML keeps the region itself in place,
   which is what makes screen readers announce the change. #}
<div hx-swap-oob="innerHTML:#status">{% if message %}<span{% if error %} class="error"{% endif %}>{{ message }}</span>{% endif %}</div>

A response can carry extra elements marked hx-swap-oob; HTMX lifts them out before the main swap and puts them where they say. The two forms differ in what survives. hx-swap-oob="true" on the add form's <section id="add-section"> replaces the page's section with the new one. hx-swap-oob="innerHTML:#status" puts the fragment's content inside the page's #status and leaves that element where it is, which matters because #status is a live region and screen readers announce changes to a region that already exists. The 2025 code used the "true" form on the status region, and that is the version that was not announced.

D.6 Removing an element

src/main/kotlin/routes/TaskRoutes.kt
private suspend fun ApplicationCall.deleteTask(store: TaskStore) {
    val task = store.getById(parameters["id"].orEmpty()) ?: return respond(HttpStatusCode.NotFound)
    store.delete(task.id)
    if (isHtmxRequest()) {
        // Nothing replaces the item, so the outerHTML swap removes it. The status is the only content.
        respondHtml(renderStatus("Deleted \"${task.title}\"."))
    } else {
        seeOther(tasksPath())
    }
}

An outerHTML swap with nothing to swap in removes the target. The delete response at this tag is only the out-of-band status, so the row goes and the deletion is announced.

D.7 Filtering as you type

src/main/resources/templates/tasks/index.peb
<section aria-labelledby="filter-heading">
  <h2 id="filter-heading">Filter</h2>
  {# Typing filters the list after a 300 ms pause. The button does the same without JavaScript. #}
  <form action="/tasks" method="get" role="search"
        hx-get="/tasks" hx-target="#task-area" hx-push-url="true"
        hx-trigger="input changed delay:300ms from:#filter-input, submit">
    <label for="filter-input">Show tasks whose title contains</label>
    <input type="search" id="filter-input" name="q" value="{{ query }}" autocomplete="off">
    <button type="submit">Filter</button>
  </form>
</section>

hx-trigger lists two events. input changed delay:300ms from:#filter-input fires after typing pauses and only if the value changed; submit keeps the button working. Without the delay modifier a request goes on every keystroke; without changed, on every keystroke that leaves the value the same, such as an arrow key.

D.8 Paging with a pushed URL

src/main/resources/templates/tasks/_pager.peb
{% if page.totalPages > 1 %}
<nav class="pager" aria-label="Pages">
  <ul>
    {% if page.currentPage > 1 %}
    <li><a href="/tasks?q={{ query | urlencode }}&page={{ page.currentPage - 1 }}"
           hx-get="/tasks?q={{ query | urlencode }}&page={{ page.currentPage - 1 }}"
           hx-target="#task-area" hx-push-url="true">Previous</a></li>
    {% endif %}
    <li aria-current="page">Page {{ page.currentPage }} of {{ page.totalPages }}</li>
    {% if page.currentPage < page.totalPages %}
    <li><a href="/tasks?q={{ query | urlencode }}&page={{ page.currentPage + 1 }}"
           hx-get="/tasks?q={{ query | urlencode }}&page={{ page.currentPage + 1 }}"
           hx-target="#task-area" hx-push-url="true">Next</a></li>
    {% endif %}
  </ul>
</nav>
{% endif %}

hx-push-url="true" pushes the request URL into history, so the back button, a bookmark and a reload all work. The URL pushed is the one in hx-get, so it has to be a URL the server answers with a full page when the header is absent; Chapter 5 is about why the code serves the fragment and the page from one URL for that reason.

D.9 Confirming a delete, and where DELETE puts its fields

src/main/resources/templates/tasks/_item.peb
    <form action="/tasks/{{ task.id }}/delete" method="post"
          hx-delete="/tasks/{{ task.id }}" hx-target="#task-area" hx-confirm="Delete '{{ task.title }}'?">
      <input type="hidden" name="q" value="{{ query }}">
      <input type="hidden" name="page" value="{{ pageNumber }}">
      <button type="submit" class="secondary" aria-describedby="task-title-{{ task.id }}">Delete</button>
    </form>

hx-confirm asks before the request goes; the plain form has no equivalent, which Chapter 6 lists as a cost. HTMX 2 puts the form's fields in the query string when the method is DELETE, where HTMX 1 put them in the body, so the handler reads the query for a DELETE and the body for a POST.

src/main/kotlin/routes/TaskRoutes.kt
private suspend fun ApplicationCall.deleteTask(store: TaskStore) {
    // HTMX 2 sends a DELETE's form fields in the query string; a plain form POSTs them in the body.
    val params = if (request.httpMethod == HttpMethod.Delete) request.queryParameters else receiveParameters()
    val place = params.place()

D.10 Responses HTMX does not swap

By default HTMX does not swap the body of a response with a 4xx or 5xx status; it raises an error event and leaves the page as it was. The behaviour is configurable through htmx.config.responseHandling. The reference code answers a failed validation with 200 and the re-rendered form, so that the form with its error reaches the page without configuring anything; Chapter 6 says what that costs.

D.11 Inline handlers

hx-on:click="..." runs JavaScript on a DOM event, and hx-on:htmx:after-request="...", or the shorthand hx-on::after-request, on an HTMX event. The 2025 code reset the add form with hx-on::after-request="this.reset()". It was removed because the event fires after any completed request, and a failed validation completes with 200, so the handler wiped the typed title at the moment the person needed to see it. The server now re-renders the form out of band instead, empty after a success and filled after a failure.

D.12 Seeing what HTMX is doing

The Network tab shows each request with its HX-Request header and the fragments in its response; a request of type document is the browser's own, one of type xhr or fetch is HTMX's. In the console, htmx.logAll() prints every HTMX event as it happens. The migration guide from HTMX 1 to 2 lists the changes that reach this code: where DELETE puts its parameters, the hx-on: form, and configurable response handling (Big Sky Software, no date a).
