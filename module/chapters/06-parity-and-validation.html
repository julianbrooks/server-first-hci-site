6  Parity and validation

By the end every route validates its input on the server, every HTMX interaction has a full-page equivalent, and you have checked both paths and written down the trade-offs.

Before you start, finish Chapter 5 on the week-08 tag, have two browsers to hand (Chrome or Edge, and Firefox), and open your backlog.

Validation lives on the server because the server is the only place both paths pass through. A browser's required attribute would stop a blank title before the server saw it, in both modes, and you would never see the server's error path, which is the one a person gets when the attribute is missing, the browser is old, or a script posts directly. The title fields in this application carry no required on purpose. Adding it is an enhancement to consider after the pilots in Chapter 8, not a default.

6.1 Activity 1: the rules in one place

src/main/kotlin/model/Task.kt
    companion object {
        const val MIN_TITLE_LENGTH = 3
        const val MAX_TITLE_LENGTH = 100

        private val DISPLAY_FORMAT = DateTimeFormatter.ofPattern("yyyy-MM-dd HH:mm")

        /** Messages by validation code. The code is what a redirect carries and what the metrics record. */
        private val MESSAGES =
            mapOf(
                "blank_title" to "Enter a title.",
                "min_length" to "Title must be at least $MIN_TITLE_LENGTH characters.",
                "max_length" to "Title must be $MAX_TITLE_LENGTH characters or fewer.",
            )

        fun validate(title: String): ValidationResult =
            when {
                title.isBlank() -> failure("blank_title")
                title.length < MIN_TITLE_LENGTH -> failure("min_length")
                title.length > MAX_TITLE_LENGTH -> failure("max_length")
                else -> ValidationResult.Success
            }

        /** The message for a code read back from a query string, or null when the code is not one of ours. */
        fun messageFor(code: String): String? = MESSAGES[code]

        private fun failure(code: String) = ValidationResult.Error(code, MESSAGES.getValue(code))
    }

The two limits are constants. The messages are built from them, so a message cannot name a different number from the one the check uses. validate returns a code and a message; the code is what travels in a redirect and what the metrics in Chapter 7 record, and messageFor turns a code read back from a URL into its message, or nothing. The limits are also passed into every form's context as minTitleLength and maxTitleLength, and the hint under each field reads them. No template in the application states a number.

The 2025 version had a hint that said one limit while the check enforced another, and participants in the pilots found it by typing a title that the hint allowed and the server refused. The fix was to remove every number from the templates, not to correct one.

6.2 Activity 2: the error in both modes

The add form now shows a failed submission as an error summary above the form, in the pattern the GOV.UK design system documents (Government Digital Service, no date b).

src/main/resources/templates/tasks/_add_form.peb
{# Re-rendered out of band after every POST /tasks, so the form shows the result:
   empty after success, the typed title and the error after a failed validation. #}
<section id="add-section" aria-labelledby="add-heading"{% if oob %} hx-swap-oob="true"{% endif %}>
  <h2 id="add-heading">Add a task</h2>
  {% if addError %}
  <div class="error-summary" role="alert" tabindex="-1" autofocus>
    <h3>There is a problem</h3>
    <ul>
      <li><a href="#task-title" id="add-error">{{ addError }}</a></li>
    </ul>
  </div>
  {% endif %}
  <form action="/tasks" method="post" hx-post="/tasks" hx-target="#task-area">
    <input type="hidden" name="q" value="{{ query }}">
    <label for="task-title">Title</label>
    <input type="text" id="task-title" name="title" value="{{ addTitle }}"
           aria-describedby="title-hint{% if addError %} add-error{% endif %}"{% if addError %} aria-invalid="true"{% endif %}>
    <small id="title-hint">Between {{ minTitleLength }} and {{ maxTitleLength }} characters.</small>
    <button type="submit" id="add-button">Add task</button>
  </form>
</section>

The summary has role="alert", so it is read when it appears; tabindex="-1" and autofocus, so focus lands on it after a reload; and a link whose target is the field, so one key press moves you to the problem. The link carries the id the field's aria-describedby points at, so focusing the field reads the error as well as the hint, and the field is marked aria-invalid. The typed title is kept.

src/main/kotlin/routes/TaskRoutes.kt
private suspend fun ApplicationCall.addTask(store: TaskStore) {
    val form = receiveParameters()
    val title = form["title"]?.trim().orEmpty()
    val place = form.place()
    when (val result = Task.validate(title)) {
        is ValidationResult.Error ->
            if (isHtmxRequest()) {
                val view = ListView.from(store, place.query, place.pageNumber)
                respondHtml(
                    renderTaskArea(view) +
                        renderAddForm(view, title, result.message) +
                        renderStatus(result.message, isError = true),
                )
            } else {
                seeOther(tasksPath(place.query, place.pageNumber, error = result.code, title = title))
            }
        ValidationResult.Success -> {
            val task = Task(title = title)
            store.add(task)
            if (isHtmxRequest()) {
                // The new task is newest, so it is on page 1.
                val view = ListView.from(store, place.query, 1)
                respondHtml(renderTaskArea(view) + renderAddForm(view) + renderStatus("Added \"${task.title}\"."))
            } else {
                seeOther(tasksPath(place.query, 1))
            }
        }
    }
}

Follow the error branch. In HTMX mode the response is the task area unchanged, the form out of band with the error in it, and the status marked as an error. In the other mode it is a redirect to the place the form was submitted from with the code and the typed title in the query string, and GET /tasks renders the same form with the same error. The success branch returns to page 1 in both modes, because the new task is newest and newest is first.

The HTMX response to a failed validation is 200 OK, not 4xx. HTMX 2 does not swap the body of a 4xx or 5xx response unless the page configures it to, so a 422 with the form in its body would leave the page unchanged and the person none the wiser. Returning 200 and letting the markup carry the meaning is the smaller choice; configuring HTMX's response handling in the layout is one more thing to teach for the same screen. The consequence is that a status code no longer says whether a request succeeded, which is why the metrics in Chapter 7 record the outcome and not the code.

The edit form shows its error inline rather than as a summary, because the form has one field and sits inside a list.

The Cancel link carries the filter and page in its href and its hx-get, so cancelling returns you to the place you were.

6.3 Activity 3: delete, and the one thing the plain path cannot do

src/main/kotlin/routes/TaskRoutes.kt
private suspend fun ApplicationCall.deleteTask(store: TaskStore) {
    // HTMX 2 sends a DELETE's form fields in the query string; a plain form POSTs them in the body.
    val params = if (request.httpMethod == HttpMethod.Delete) request.queryParameters else receiveParameters()
    val place = params.place()
    val task = store.getById(parameters["id"].orEmpty()) ?: return respond(HttpStatusCode.NotFound)
    store.delete(task.id)
    if (isHtmxRequest()) {
        val view = ListView.from(store, place.query, place.pageNumber)
        respondHtml(renderTaskArea(view) + renderStatus("Deleted \"${task.title}\"."))
    } else {
        seeOther(place.path())
    }
}

HTMX 2 sends the fields of a form that triggers a DELETE in the query string, where HTMX 1 sent them in the body; a plain form POSTs them in the body. The handler reads whichever the method implies, so the place survives either way. The delete form in _item.peb (Chapter 5) has hx-confirm, so with the script on, a browser dialog asks before the request goes. With the script off, there is no dialog: a form submits when its button is pressed. That gap goes on the list in Activity 5.

6.4 Activity 4: the no-JavaScript pass

Switch JavaScript off. In Chrome or Edge, open the developer tools (F12), press Ctrl-Shift-P (Cmd-Shift-P on a Mac), type "Disable JavaScript" and press Enter; it stays off while the developer tools are open, and comes back when you close them. In Firefox, type about:config in the address bar, accept the warning, search for javascript.enabled and toggle it to false; it stays off in every tab until you toggle it back. Reload the list. The footer reads "no JavaScript"; if it still reads "HTMX", the script ran, which in Chrome means the developer tools were closed.

Now go through every flow and record the result. For each one, do the action, then read the address bar and the page.

Flow Do You should see
Add Type a title, press Add task Page reloads, new row first, address bar /tasks
Add, blank Press Add task with the field empty Reload, address bar carries error=blank_title, summary at the top with focus on it, field marked, typed text kept
Filter Type in the filter, press Filter Reload, address bar carries q=, count paragraph names the filter
Page Press Next Reload, address bar carries page=2
Edit Press Edit, change the title, press Save Reload with the row as a form, then reload with it as a row, on the same page and filter
Edit, blank Press Edit, clear the field, press Save Reload with the form open, error under the field, address bar carries edit= and the code
Cancel Press Edit, then Cancel Back to the list, same page and filter
Mark done Press Mark done Reload, row marked Done, button reads Mark not done
Delete Press Delete No dialog; reload with the row gone

In the Network tab every request is of type document; a request of type xhr or fetch means the script is running. If the filter does nothing while you type, that is correct: typing is the enhancement, the button is the baseline. If the server log shows a 405, a form's method is wrong. If a reload after an error loses the typed title, the redirect was built without it.

Switch JavaScript back on and run the table again: the address bar changes without a reload, the status box appears, and Delete asks first. Any row that fails in either mode is a backlog row with evidence set to own observation, and it is the kind of row the regression checks in Chapter 10 are built from.

6.5 Activity 5: what the two paths cost

Here is what having both paths costs.

Every handler has two branches, and every behaviour has two tests. A change made in one branch and not the other is the most common defect in this codebase, and nothing but the tests catches it.

The two modes do not behave identically and cannot. Delete asks for confirmation only with the script on. The status announcement exists only with the script on: the plain path reloads and says nothing, which is the backlog row you wrote in Chapter 1. After a swap, focus is where the markup puts it; after a reload, the page scrolls to the top first.

The status codes are not the whole truth. A failed validation is 200 in one mode and 303 in the other, so anything that counts failures by status counts wrong.

State travels in URLs. A failed submission redirects with the typed title in the query string, which lands in the browser history and the server log. A title is the person's own text, and Appendix F is about why that matters.

The markup is longer. Every form carries hidden q and page fields, every link carries them in its query string, and every control carries both a plain attribute and an hx- one.

One URL with two answers needs Vary. A cache that ignores it serves a fragment as a page.

The plain path is slower per action. Every action is a whole page, not a few lines of it, and on a slow connection that is the difference between a pause and a wait.

The hx- attributes and the header check are a second vocabulary on top of HTML and HTTP; Appendix D exists because of it.

What the two paths buy is a page that works when the script does not load, is blocked or is off, and one piece of HTML for the browser and the screen reader alike. The GOV.UK service manual requires it for services the public has no choice but to use (Government Digital Service, no date a). We think the costs above are worth paying for an application like this one. For a drawing tool or a game they would not be, and saying so is part of the trade-off.
