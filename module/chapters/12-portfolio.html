12  Portfolio

By the end you have a README in which every claim links to the data, code or screenshot that supports it, a reflection of two paragraphs, and a tag that a stranger can clone, build and read.

Before you start, read crit/notes.md from Chapter 11 and have your module's assessment criteria open; this chapter builds towards them and restates none of them. You need about two hours and no new code, and this chapter has no session of its own.

12.1 What the portfolio is

The portfolio is the README of your repository and the files it points at. It is not a separate document, a slide deck or a folder of screenshots; it is the front page of the work, written for a reader who was not there and has little time. That reader opens the README at the tag you name, follows the links, and decides whether each claim is supported by what they find at the other end. A claim with no link is an assertion, and a marker treats it as one.

Every file the README points at already exists if you have followed the chapters in order: the consent form and its record, the notes, the stories and the backlog from Chapter 2; the audit record and fix from Chapter 4; the parity table from Chapter 6; the metrics file from Chapter 7; the pilot notes from Chapter 8; the analysis from Chapter 9; the regression checklist and re-pilot from Chapter 10; the screenshots named as Appendix J says; and the three crit files. This chapter adds the README and a tag. If a link you want to write has nothing to point at, the portfolio has found a gap, and the honest response is a sentence saying so, not a link to the nearest thing.

12.2 Activity 1: act on the crit

Open crit/notes.md. For each question, do what the note says: add the link, gather the evidence, or write the limitation. Where the evidence exists, the link is written in Activity 2. Where it can still be gathered, gather it now and commit it before you write a word of the README, because a link to an uncommitted file breaks at the tag. Where it cannot be gathered, write the sentence that states the limitation and keep it for the limitations section.

Re-running a pilot is not expected unless the crit found a flaw in the method, such as a participant who was told the answer. Polish the record; do not rerun the study.

12.3 Activity 2: write the README

Write the README in this order. Each section is a few sentences and the links that support them, and the whole file fits on two screens.

The first section says what the application is in two sentences and how to run it, by pointing at Appendix A rather than repeating its commands. It names the tag the portfolio describes, so the reader knows which commit the links resolve against.

The second section says how many participants took part in the pilots and in the re-pilot, in which modes, and that consent was recorded, with links to the consent log and the form's record; if the data was collected with another student, it says so without naming them. No names, no student numbers, no email addresses, nothing a participant could be recognised from; participants appear only by the codes Chapter 8 assigned.

The third section lists the findings, one sentence each, with a link after every sentence to the rows or lines that support it. A finding is a claim about what happened: "participants without JavaScript failed the edit task in two of four saves", followed by a link to those rows of the metrics file and to the line of the notes where a participant said why. The example data at the chapter-09 tag, read as Chapter 9 and Chapter 10 read it, shows the shape at paragraph length. A finding with an accessibility cause names its success criterion by number (W3C, 2023).

The fourth section lists the changes, one to three, each with the finding it addresses, the criterion it serves, and a link to the commit or the diff. A change that did not move its measurement is still a change; say what the measurement did and what you make of it.

The fifth section is the verification: a link to the completed regression checklist, a link to the re-pilot data, and the before and after figures side by side with their sources. A regression check that failed and was not fixed is said here, not left as a blank row.

The sixth section is limitations: what you did not do, what the sample size does not support, the questions from the crit you could not answer, and, where an AI tool helped with the code, the tool and the file it touched. One paragraph. A limitation stated here is professional practice; the same limitation discovered by the reader is a gap.

The seventh section is the reflection from Activity 3.

Links are relative paths within the repository, with a line or row where one applies, in the form the hosting service turns into a link to those lines (#L41-L46 after a file path works on GitHub and GitLab). A link that follows a paragraph rather than the sentence it supports is the miss a marker sees most often. A reader who has cloned the repository opens the same path. Links to your working copy, to a cloud drive or to a chat message resolve for nobody else.

12.4 Activity 3: the reflection

Write two paragraphs of prose at the end of the README, with no headings, bullets or template. The first paragraph is about the evidence: where the chain from finding to verification was strongest, where it was weakest, and which question from the crit you could not answer. The second is about what comes next: what you would measure that you did not, who you would recruit, and which backlog row you would take on, with the row named. A reader should be able to check each sentence against a file in the repository, the same as the rest of the README.

A set of headings with one sentence under each, "what went well" and "what was challenging", says nothing a reader can act on; write sentences that connect. Praise for your own work does not belong in it; the evidence is in the sections above, and the reflection is for what the evidence does not show.

12.5 Activity 4: check, tag, submit

Three checks, in order, before you tag.

No personal data anywhere. Search the working tree for email addresses with git grep -n -i -E '[a-z0-9._-]+@[a-z0-9.-]+\.[a-z]+'; the only hit should be your own address, if that. Search the history for each participant's real name with git log -p -S'<name>'; a name in an old commit is still in the repository even after the file was changed. Open every screenshot and look at the browser tabs, the bookmark bar and the window title. If a name is in the history, deleting the file does not remove it; tell your module team, or whoever owns the repository, before you tag, because the fix rewrites history and is not yours to do alone.

Every link resolves. Open the README on the hosting service's web view at the commit you are about to tag and click every link. A link that works in your editor and not on the web view points at a file that was never committed. The metrics file is the usual one: the reference repository ignores data/*.csv apart from the example files, so a link to the pilot data breaks at the tag unless the data was copied into a committed location when the pilots ended. If it was not, copy it now, commit the copy, and point the links at it.

The application runs from a clean clone at the tag. In a directory outside your working copy:

git clone <your repository address> check
cd check
git checkout <the commit you will tag>
./kotlin run

Open the page as Appendix A says, add a task, stop the server with Ctrl-C and delete the clone. If the clone fails to build and your working copy does not, a file the build depends on was never committed; git status in the working copy names it.

Then tag and push:

git tag -a <tag name> -m "Portfolio"
git push origin <tag name>

Write the tag name in the first section of the README and commit that change before you tag, or the README at the tag names a tag that does not yet exist. If you change anything afterwards, tag again with a new name and update the README; a moved tag is one the reader cannot trust.

Where and how the tag is submitted, and by when, is on Chapter 14.

12.6 What to record

The README and the tag. Nothing else is new this chapter; everything the README points at was recorded by the chapter that produced it. What you record here is the evidence for outcomes 4 and 16 in Appendix L.
