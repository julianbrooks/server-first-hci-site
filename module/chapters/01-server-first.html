1  Server-first

You clone a working task list, read how a request becomes a page, and fill the one gap left in it; by the end the list adds and deletes tasks with JavaScript off, and the same page works enhanced with HTMX.

Before you start, work through Appendix A until ./gradlew build passes on your machine, then check out the tag this chapter is written against: git checkout week-06-start. If you have not written Kotlin before, read Appendix B; this chapter assumes you can read a function and a map literal and nothing more. You have met HTML and CSS once, which is enough.

1.1 Why the server renders the page

The application in this book sends the browser finished HTML. The browser shows it without running a script, and every link and form on it works with JavaScript off. HTMX is then added as a layer on top: a small script that lets a form or link fetch a fragment of HTML and swap it into the page instead of reloading. If the script fails to load, is blocked, or is switched off, the page is still the page.

This is progressive enhancement, and the GOV.UK service manual requires it for government services (Government Digital Service, no date). Hypermedia Systems makes the longer argument for building this way (Gross, Stepinski and Akşimşek, 2023). The reason this book takes the position is narrower: the HTML the server sends is the HTML a screen reader reads, so there is one place to get the structure, the labels and the announcements right, and one place to check them.

Every interaction in the task list is therefore reached two ways: a plain form submission that ends in a redirect, and an HTMX request that ends in a fragment. The server tells them apart by one request header, and every handler answers both.

1.2 Activity 1: run it and follow a request

Run ./gradlew run and open http://localhost:8080/tasks. If the page is blank, a server from last time is still on the port; stop it with Ctrl-C in that terminal and run again. Add a task and watch the terminal print one line per request: method, path, status.

Four files turn that request into the page. Main.kt starts the server and installs everything.

src/main/kotlin/Main.kt
import io.ktor.http.ContentType
import io.ktor.http.HttpStatusCode
import io.ktor.server.application.Application
import io.ktor.server.application.install
import io.ktor.server.engine.embeddedServer
import io.ktor.server.http.content.staticResources
import io.ktor.server.netty.Netty
import io.ktor.server.plugins.calllogging.CallLogging
import io.ktor.server.plugins.statuspages.StatusPages
import io.ktor.server.request.httpMethod
import io.ktor.server.request.path
import io.ktor.server.response.respondText
import io.ktor.server.routing.routing
import routes.configureHealthCheck
import routes.configureTaskRoutes
import storage.TaskStore

/** Starts the server. The port comes from the PORT environment variable and defaults to 8080. */
fun main() {
    val port = System.getenv("PORT")?.toIntOrNull() ?: 8080
    embeddedServer(Netty, port = port, host = "0.0.0.0") { module() }.start(wait = true)
}

/**
 * Installs every plugin and route. The tests call this with their own [TaskStore],
 * so the application under test is the one that runs.
 */
fun Application.module(store: TaskStore = TaskStore()) {
    configureLogging()
    configureTemplating()
    configureStatusPages()
    routing {
        staticResources("/static", "static")
        configureHealthCheck()
        configureTaskRoutes(store)
    }
}

/** One console line per request: method, path and status. */
fun Application.configureLogging() {
    install(CallLogging) {
        format { call -> "${call.request.httpMethod.value} ${call.request.path()} - ${call.response.status()}" }
    }
}

/** Renders errors/404.peb for any response that ends as a 404 with no body of its own. */
fun Application.configureStatusPages() {
    install(StatusPages) {
        status(HttpStatusCode.NotFound) { call, status ->
            call.respondText(call.renderTemplate("errors/404.peb"), ContentType.Text.Html, status)
        }
    }
}

main reads the port and starts Netty with module(). module installs request logging, the template engine, a handler that renders the 404 page, and the routes. The tests call module with their own TaskStore, so the application under test is the one that runs.

Templating.kt builds the Pebble engine and holds the two functions every route uses.

src/main/kotlin/Templating.kt
import io.ktor.server.application.Application
import io.ktor.server.application.ApplicationCall
import io.ktor.util.AttributeKey
import io.pebbletemplates.pebble.PebbleEngine
import io.pebbletemplates.pebble.loader.ClasspathLoader
import java.io.StringWriter

val PebbleEngineKey = AttributeKey<PebbleEngine>("PebbleEngine")

/** Builds the engine the application uses. The template smoke test uses the same one. */
fun buildPebbleEngine(): PebbleEngine =
    PebbleEngine.Builder()
        .loader(ClasspathLoader().apply { prefix = "templates/" })
        // Every {{ value }} is HTML-escaped. This is what makes rendering through templates safe.
        .autoEscaping(true)
        // Templates are re-read on every request, so edits show without a restart.
        .cacheActive(false)
        .strictVariables(false)
        .build()

fun Application.configureTemplating() {
    attributes.put(PebbleEngineKey, buildPebbleEngine())
}

/**
 * Renders a template under resources/templates with [context], adding `isHtmx` so the
 * layout can use it without every route passing it.
 */
fun ApplicationCall.renderTemplate(name: String, context: Map<String, Any?> = emptyMap()): String {
    val engine = application.attributes[PebbleEngineKey]
    val enriched = context + mapOf("isHtmx" to isHtmxRequest())
    return StringWriter().also { engine.getTemplate(name).evaluate(it, enriched) }.toString()
}

/**
 * True when HTMX made the request and wants a fragment back. HTMX also sends HX-Request
 * when it restores a page from history, but then it expects the full page, so that case
 * returns false.
 */
fun ApplicationCall.isHtmxRequest(): Boolean =
    request.headers["HX-Request"] == "true" && request.headers["HX-History-Restore-Request"] != "true"

Three settings matter. autoEscaping(true) means every { value } in a template is HTML-escaped. cacheActive(false) means a template edit shows on the next request without a restart. isHtmxRequest() is the header check: HTMX sends HX-Request: true on every request it makes, so a route that sees it returns a fragment. HTMX also sends that header when it restores a page from history, and then it wants the whole page back, so that case returns false.

The stylesheet and the HTMX script are served by this application rather than a CDN, because lab networks block CDNs. The <div id="status"> is the one live region on the page: an element with role="status" that a screen reader announces when its content changes. It is empty on load, which is correct for a region that announces later changes. {% block content %} is where a page puts its body.

1.3 Activity 2: the add flow in both modes

The add form is its own template because the server sends it back after every submission.

src/main/resources/templates/tasks/_add_form.peb
{# Re-rendered out of band after every POST /tasks, so the form shows the result:
   empty after success, the typed title and the error after a failed validation. #}
<section id="add-section" aria-labelledby="add-heading"{% if oob %} hx-swap-oob="true"{% endif %}>
  <h2 id="add-heading">Add a task</h2>
  <form action="/tasks" method="post" hx-post="/tasks" hx-target="#task-list" hx-swap="afterbegin">
    <label for="task-title">Title</label>
    <input type="text" id="task-title" name="title" value="{{ addTitle }}"
           aria-describedby="title-hint{% if addError %} add-error{% endif %}"{% if addError %} aria-invalid="true"{% endif %}>
    <small id="title-hint">Between {{ minTitleLength }} and {{ maxTitleLength }} characters.</small>
    {% if addError %}<p id="add-error" class="error-message" role="alert">{{ addError }}</p>{% endif %}
    <button type="submit" id="add-button">Add task</button>
  </form>
</section>

The <form> carries two sets of attributes. action and method are what a browser uses; hx-post, hx-target and hx-swap are what HTMX uses when its script is running. The label is tied to the field by for, the hint by aria-describedby, and after a failed submission the field is marked aria-invalid and the error paragraph is added to its description.

TaskRoutes.kt holds every route in the application at this tag.

src/main/kotlin/routes/TaskRoutes.kt
package routes

import io.ktor.http.ContentType
import io.ktor.http.HttpHeaders
import io.ktor.http.HttpStatusCode
import io.ktor.http.encodeURLParameter
import io.ktor.server.application.ApplicationCall
import io.ktor.server.request.receiveParameters
import io.ktor.server.response.respond
import io.ktor.server.response.respondText
import io.ktor.server.routing.Route
import io.ktor.server.routing.get
import io.ktor.server.routing.post
import isHtmxRequest
import model.Task
import model.ValidationResult
import renderTemplate
import storage.TaskStore

/**
 * Every route answers in two modes. With the HX-Request header it returns the fragment
 * HTMX asked for, plus any out-of-band updates. Without it, it returns a full page or
 * redirects (POST, redirect, GET), so the same URLs work with JavaScript off.
 */
fun Route.configureTaskRoutes(store: TaskStore) {
    get("/") { call.seeOther("/tasks") }
    get("/tasks") { call.listTasks(store) }
    post("/tasks") { call.addTask(store) }
    // TODO Week 6 Lab 1: add delete. HTMX sends DELETE /tasks/{id}; a form without JavaScript
    // can only POST, so it needs POST /tasks/{id}/delete as well. Both call one handler.
}

/** The list page. After a failed submission the query string carries `error` and `title` so the form can show them. */
private suspend fun ApplicationCall.listTasks(store: TaskStore) {
    val error = request.queryParameters["error"]?.let(Task::messageFor)
    val title = request.queryParameters["title"]
    respondHtml(renderTemplate("tasks/index.peb", listContext(store) + mapOf("addError" to error, "addTitle" to title)))
}

private suspend fun ApplicationCall.addTask(store: TaskStore) {
    val title = receiveParameters()["title"]?.trim().orEmpty()
    when (val result = Task.validate(title)) {
        is ValidationResult.Error ->
            if (isHtmxRequest()) {
                // Nothing for the list. The form comes back out of band with the error, and the live region announces it.
                respondHtml(renderAddForm(title, result.message) + renderStatus(result.message, isError = true))
            } else {
                seeOther(tasksPath(error = result.code, title = title))
            }
        ValidationResult.Success -> {
            val task = Task(title = title)
            store.add(task)
            if (isHtmxRequest()) {
                respondHtml(
                    renderTemplate("tasks/_item.peb", itemContext(task)) +
                        renderAddForm() +
                        renderStatus("Added \"${task.title}\"."),
                )
            } else {
                seeOther(tasksPath())
            }
        }
    }
}

private val TITLE_LIMITS = mapOf("minTitleLength" to Task.MIN_TITLE_LENGTH, "maxTitleLength" to Task.MAX_TITLE_LENGTH)

/** Every task, newest first. */
private fun listContext(store: TaskStore): Map<String, Any?> =
    TITLE_LIMITS + mapOf("tasks" to store.getAll().asReversed().map { it.toPebbleContext() })

/** Builds /tasks with only the query parameters that carry information. */
private fun tasksPath(error: String? = null, title: String? = null): String {
    val params =
        buildList {
            if (error != null) add("error=${error.encodeURLParameter()}")
            if (title != null) add("title=${title.encodeURLParameter()}")
        }
    return if (params.isEmpty()) "/tasks" else "/tasks?" + params.joinToString("&")
}

private fun itemContext(task: Task): Map<String, Any?> = mapOf("task" to task.toPebbleContext())

private fun ApplicationCall.renderAddForm(title: String? = null, error: String? = null): String =
    renderTemplate("tasks/_add_form.peb", TITLE_LIMITS + mapOf("oob" to true, "addTitle" to title, "addError" to error))

/** The out-of-band update for the live region. The message is text; the template does the HTML. */
private fun ApplicationCall.renderStatus(message: String, isError: Boolean = false): String =
    renderTemplate("tasks/_status.peb", mapOf("message" to message, "error" to isError))

private suspend fun ApplicationCall.respondHtml(html: String) = respondText(html, ContentType.Text.Html)

/** 303 See Other: the status for "the POST worked, now GET this", so a refresh never re-submits. */
private suspend fun ApplicationCall.seeOther(path: String) {
    response.headers.append(HttpHeaders.Location, path)
    respond(HttpStatusCode.SeeOther)
}

With JavaScript off, the browser POSTs the form. addTask reads the title, validates it, saves it, and answers 303 See Other with Location: /tasks. The browser GETs the list and shows the new task. A refresh now repeats the GET, not the POST, so nothing is submitted twice; this is the POST, redirect, GET pattern, and seeOther is the only place the status code appears. A failed validation also redirects, to /tasks?error=min_length&title=ab: the URL carries the error code and the typed text, and listTasks turns the code back into a message with Task.messageFor. An unknown code renders nothing, so a crafted URL cannot put text on the page.

With HTMX, the same POST arrives with HX-Request: true, and the response is three fragments in one body. The first is _item.peb, which HTMX inserts at the start of #task-list as the form's hx-target and hx-swap say. The second is _add_form.peb rendered with oob set, so it carries hx-swap-oob="true"; HTMX takes it out of the response and replaces #add-section with it wherever that is, empty after a success and holding the typed title and the error after a failure. The third is _status.peb.

src/main/resources/templates/tasks/_status.peb
{# Swapped into the live region in the layout. innerHTML keeps the region itself in place,
   which is what makes screen readers announce the change. #}
<div hx-swap-oob="innerHTML:#status">{% if message %}<span{% if error %} class="error"{% endif %}>{{ message }}</span>{% endif %}</div>

hx-swap-oob="innerHTML:#status" puts the fragment's content inside the live region and leaves the region itself in place. Screen readers announce changes to a live region that already exists; a region inserted into the page with its message already inside is often not announced. The 2025 version of this code replaced the whole element. That the region stays in place has been checked by reading the HTMX source and by driving a browser against every tag: #status is the same DOM node before and after each swap. That the change is announced has not yet been checked with a screen reader on a lab machine; Activity 3 is where you find out.

Every fragment, including the one-line status, is a template, and renderStatus passes the message as text. Nothing in TaskRoutes.kt builds HTML with a title in it. That is what makes a title of <b>bold</b> & "quoted" arrive on the page as text; the test titles are escaped everywhere they appear posts exactly that and checks the output.

When one URL answers differently depending on a header, the response has to say so with Vary: HX-Request, or a cache can hand a fragment to a browser that asked for a page. At this tag no GET route varies, so none sends the header; Chapter 5 adds it when GET /tasks starts answering both ways.

Check the two modes from a second terminal while the server runs.

curl -i -d 'title=Buy milk' http://localhost:8080/tasks
curl -i -H 'HX-Request: true' -d 'title=Buy milk' http://localhost:8080/tasks
curl -i -d 'title=ab' http://localhost:8080/tasks

The first prints HTTP/1.1 303 See Other and Location: /tasks. The second prints 200 OK and a body that begins with a <li>, continues with the <section id="add-section" ... hx-swap-oob="true">, and ends with the <div hx-swap-oob="innerHTML:#status">. The third prints a 303 whose Location is /tasks?error=min_length&title=ab. The Network tab in the browser shows the same two shapes: the header and the fragments with the script running, the redirect and a second request without it. If the browser warns about resubmitting a form when you refresh after adding, a POST returned a page instead of a redirect.

1.4 Activity 3: implement delete in both modes

Two tests at the end of TaskRoutesTest.kt describe the behaviour and are switched off until it exists.

src/test/kotlin/routes/TaskRoutesTest.kt
    // Delete (Week 6 Lab 1). These two tests describe the behaviour to build; enable them when it exists.

    @Test
    @Disabled("Week 6 Lab 1: implement delete in both modes, then remove this annotation")
    fun `DELETE as HTMX removes the task and returns only the status`() =
        withApp { store, client ->
            val task = Task(title = "Remove me").also(store::add)
            val response = client.delete("/tasks/${task.id}") { header(HTMX_HEADER, "true") }
            assertEquals(HttpStatusCode.OK, response.status)
            val body = response.bodyAsText()
            assertFalse(body.contains("<li"))
            assertContains(body, "Deleted &quot;Remove me&quot;.")
            assertNull(store.getById(task.id))
        }

    @Test
    @Disabled("Week 6 Lab 1: implement delete in both modes, then remove this annotation")
    fun `POST delete without HTMX removes the task and redirects`() =
        withApp { store, client ->
            val task = Task(title = "Remove me").also(store::add)
            val response = client.postForm("/tasks/${task.id}/delete", false)
            assertEquals(HttpStatusCode.SeeOther, response.status)
            assertEquals("/tasks", response.headers[HttpHeaders.Location])
            assertNull(store.getById(task.id))
        }

Build it in the order the two TODO comments suggest. In _item.peb, add a form inside the <li> with a Delete button. For the browser it needs action="/tasks/{{ task.id }}/delete" and method="post", because a form without JavaScript can only GET or POST. For HTMX it needs hx-delete="/tasks/{{ task.id }}", hx-target="#task-{{ task.id }}" and hx-swap="outerHTML", so the response replaces the whole <li>. Give the button aria-describedby="task-title-{{ task.id }}" so a screen reader says which task the button deletes.

In TaskRoutes.kt, add delete("/tasks/{id}") and post("/tasks/{id}/delete") where the comment is, both calling one handler, so the two modes cannot drift apart. If delete is unresolved, add import io.ktor.server.routing.delete beside the imports for get and post. The handler looks the task up with store.getById(parameters["id"].orEmpty()) and answers HttpStatusCode.NotFound when there is none; the status page handler in Main.kt turns that into the 404 page. Otherwise it deletes the task and branches on isHtmxRequest(). In HTMX mode it responds with renderStatus and nothing else: there is no content for the target, so the outerHTML swap removes the <li>, and the live region announces the deletion. In the other mode it calls seeOther(tasksPath()).

Remove the two @Disabled lines and the import that goes with them, then run ./gradlew test. If the report says two tests were skipped, the annotations are still there. If the HTMX test fails because the body contains <li, the handler returned the item as well as the status. If the server log shows DELETE /tasks/... - 405 Method Not Allowed, only the POST route exists and HTMX is sending DELETE. In the browser, if the row stays on the page after Delete but is gone after a reload, hx-target names an id that is not on the <li>.

git diff week-06-start week-06 shows one implementation. Compare after your tests pass, not before.

1.5 What to record

Commit with a message that says what was added. Then write down, in a sentence each, what happened in the two modes when you added a task: with JavaScript off, the page reloaded and said nothing; with HTMX, the status box appeared and, if you had a screen reader running, was read out. That gap is the first row of the backlog you build in Chapter 2, and what you heard is its evidence.
