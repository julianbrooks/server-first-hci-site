7  Instrumentation

By the end you have an evaluation plan that names three to five tasks, each with a code, a success criterion and a definition of error, and you have watched the reference code write one metrics row per request in both modes and label those rows with a participant code.

Before you start, check out the week-09 tag and run ./gradlew build; if timed is unresolved anywhere, you are on an earlier tag. Have research/stories.md and backlog/backlog.csv from Chapter 2 open. Read the metric definitions in Appendix I once; this chapter uses them without restating them.

7.1 Measuring rather than asking

This chapter and the next find out what happens when people use the prototype, by measuring. The measurement comes from the server: every request the application handles writes one row to a metrics file. Nothing else is involved: no analytics script in the page, no third party, and nothing about the person beyond the pseudonym in the session column, which they can ask to have deleted. That log is a narrow instrument. It sees that a request arrived, what it was for, whether it succeeded, how long the server took, and when. It does not see the participant read the screen, hesitate, look for a button, or say "did that work?". Those come from the person sitting next to the participant with a notebook, which is Chapter 8; the two halves are put together in Chapter 9.

7.2 Activity 1: write the evaluation plan

Create research/plan.md. It has three parts: the tasks, the measures, and the design of the sessions.

A task is something a participant is asked to do with the task list, written as a scenario you can read aloud: "You have been asked to find every task about the quarterly report. Use the filter and tell me how many there are." Each task carries one of the codes in utils/TaskCodes.kt, because the metrics file records the code and nothing else about the task, so the plan has to be the place that says what T1_filter meant. Choose three to five of the five participant tasks: filter, edit, add, delete and mark done. T0_list is the page load and the redirects that follow a change without JavaScript, not a task anyone is asked to do.

src/main/kotlin/utils/TaskCodes.kt
package utils

/**
 * Codes for the tasks participants carry out in the Week 9 evaluation. They are the
 * task_code column of the metrics and are stated nowhere else.
 */
object TaskCodes {
    const val LIST = "T0_list"
    const val FILTER = "T1_filter"
    const val EDIT = "T2_edit"
    const val ADD = "T3_add"
    const val DELETE = "T4_delete"
    const val TOGGLE = "T5_toggle"

    val all = listOf(LIST, FILTER, EDIT, ADD, DELETE, TOGGLE)
}

For each task write the success criterion as something the facilitator can see or hear: the participant says "three", the new title is in the list, the task is gone. Then write what counts as an error. The log counts one kind of error on its own, a submission the server rejected, which it records as a validation_error row with the reason in the outcome column. Everything else, such as deleting the wrong task, succeeds as far as the server is concerned and is an error only if the note-taker writes it down. Say in the plan which errors you expect from the log and which from the notes, so that in Chapter 9 you are not tempted to add the two together.

Write the tasks against seed data you control. Decide the ten or so titles the list will hold at the start of every session, so that a scenario can name "Submit invoices" and the participant can find it; Activity 4 shows how to save them. Put delete last, because it is the destructive one, and give each task a time after which the facilitator moves on; two minutes is enough for any of these.

The measures section says which metrics you will report and names Appendix I as the definition of each. The design section is short: four participants, every participant does the tasks in both modes, two start with HTMX and two without JavaScript, and the comparison is within each participant. Chapter 8 explains why, and what that design can and cannot support; the plan only has to record it.

7.3 Activity 2: read the instrumentation

At the week-09 tag the instrumentation is already in the code. Start with utils/Logger.kt. The comment on LogEntry is the schema of the metrics file. It is the only place in the code or the book where the columns are listed, and every other page sends you here.

src/main/kotlin/utils/Logger.kt
package utils

import java.io.File
import java.time.Instant
import java.time.temporal.ChronoUnit

/**
 * One row of the metrics file, data/metrics.csv. This comment is the schema; nothing else
 * restates it. The columns, in order:
 *
 * - `ts_iso`: when the row was written, UTC, ISO 8601, for example `2026-11-18T14:03:21.512Z`.
 * - `session_id`: the value of the `sid` cookie. A facilitator sets it to a participant
 *   code before a session; otherwise it is six random hex characters.
 * - `request_id`: `r_` followed by eight hex characters, unique to one request.
 * - `task_code`: one of the [TaskCodes] constants.
 * - `step`: `success`, `validation_error`, `client_error` or `server_error`.
 * - `outcome`: `ok` for success; for a validation error the code from `Task.validate`
 *   (`blank_title`, `min_length`, `max_length`); for another error `http_` and the status,
 *   or the exception class name.
 * - `ms`: the server's time handling the request, in milliseconds. It is not time on task.
 *   Time on task is the gap between a participant's consecutive `ts_iso` values.
 * - `http_status`: the status code the server sent.
 * - `js_mode`: `htmx` when HTMX made the request, otherwise `nojs`.
 *
 * Every field is a controlled token or a number, so no field contains a comma.
 */
data class LogEntry(
    val sessionId: String,
    val requestId: String,
    val taskCode: String,
    val step: String,
    val outcome: String,
    val durationMs: Long,
    val statusCode: Int,
    val jsMode: String,
    val timestamp: Instant = Instant.now(),
) {
    fun toCsvLine(): String =
        listOf(
            timestamp.truncatedTo(ChronoUnit.MILLIS).toString(),
            sessionId,
            requestId,
            taskCode,
            step,
            outcome,
            durationMs,
            statusCode,
            jsMode,
        ).joinToString(",")

    companion object {
        const val HEADER = "ts_iso,session_id,request_id,task_code,step,outcome,ms,http_status,js_mode"
    }
}

/**
 * Appends [LogEntry] rows to the metrics file, writing the header first when the file is
 * new or empty. The path can be changed with the `metrics.file` system property, which
 * the tests do so they never touch data/metrics.csv.
 */
object Logger {
    val file: File = File(System.getProperty("metrics.file") ?: "data/metrics.csv")

    @Synchronized
    fun write(entry: LogEntry) {
        if (!file.exists() || file.length() == 0L) {
            file.parentFile?.mkdirs()
            file.writeText(LogEntry.HEADER + "\n")
        }
        file.appendText(entry.toCsvLine() + "\n")
    }

    fun success(sessionId: String, requestId: String, taskCode: String, durationMs: Long, statusCode: Int, jsMode: String) =
        write(LogEntry(sessionId, requestId, taskCode, "success", "ok", durationMs, statusCode, jsMode))

    fun validationError(
        sessionId: String,
        requestId: String,
        taskCode: String,
        outcome: String,
        durationMs: Long,
        statusCode: Int,
        jsMode: String,
    ) = write(LogEntry(sessionId, requestId, taskCode, "validation_error", outcome, durationMs, statusCode, jsMode))
}

Two things in that comment matter. The ms column is the time the server spent handling one request. It is not time on task, which is the gap between a participant's consecutive timestamps; the 2025 version of this material called ms "server-timed time-on-task", and that was wrong. And session_id is whatever the sid cookie holds, which is why Activity 3 sets that cookie to a participant code.

utils/Timing.kt is where rows are written. Every route handler runs inside timed(), which reads or sets the cookie, times the handler, and writes one row when it finishes: success, or validation_error when the handler reported one through recordValidationError, or client_error or server_error from the status. One request, one row, is what makes an error rate possible. The 2025 code logged a validation error and then a success for the same request and counted every failure twice.

src/main/kotlin/utils/Timing.kt
package utils

import io.ktor.http.Cookie
import io.ktor.server.application.ApplicationCall
import io.ktor.util.AttributeKey
import isHtmxRequest
import java.util.UUID

/** The name of the cookie that identifies a participant's session in the metrics. */
const val SESSION_COOKIE = "sid"

private val SessionCodeKey = AttributeKey<String>("sessionCode")
private val RequestIdKey = AttributeKey<String>("requestId")
private val ValidationOutcomeKey = AttributeKey<String>("validationOutcome")

/**
 * Runs [block] and writes one metrics row for the request: `success`, or
 * `validation_error` when the handler called [recordValidationError], or `client_error`
 * or `server_error` from the response status, or `server_error` when [block] throws.
 */
suspend fun <T> ApplicationCall.timed(taskCode: String, jsMode: String, block: suspend ApplicationCall.() -> T): T {
    val sessionCode = ensureSessionCode()
    val requestId = ensureRequestId()
    val started = System.nanoTime()
    try {
        val result = block()
        val ms = elapsedMs(started)
        val status = response.status()?.value ?: 200
        val validationOutcome = attributes.getOrNull(ValidationOutcomeKey)
        when {
            validationOutcome != null ->
                Logger.validationError(sessionCode, requestId, taskCode, validationOutcome, ms, status, jsMode)
            status >= 400 -> {
                val step = if (status >= 500) "server_error" else "client_error"
                Logger.write(LogEntry(sessionCode, requestId, taskCode, step, "http_$status", ms, status, jsMode))
            }
            else -> Logger.success(sessionCode, requestId, taskCode, ms, status, jsMode)
        }
        return result
    } catch (e: Exception) {
        val outcome = e::class.simpleName ?: "exception"
        Logger.write(LogEntry(sessionCode, requestId, taskCode, "server_error", outcome, elapsedMs(started), 500, jsMode))
        throw e
    }
}

/** Tells [timed] that this request failed validation with [outcome], one of the codes from `Task.validate`. */
fun ApplicationCall.recordValidationError(outcome: String) = attributes.put(ValidationOutcomeKey, outcome)

/** The js_mode value for this request. */
fun ApplicationCall.jsMode(): String = if (isHtmxRequest()) "htmx" else "nojs"

/** The session code for this request, if one has been set by [timed] or sent as a cookie. */
fun ApplicationCall.sessionCode(): String? = attributes.getOrNull(SessionCodeKey) ?: request.cookies[SESSION_COOKIE]

/**
 * Reads the `sid` cookie or sets a new one. The cookie is readable from JavaScript on
 * purpose: a facilitator sets it to a participant code in the browser console before a
 * session, for example `document.cookie = "sid=P3; path=/"`.
 */
private fun ApplicationCall.ensureSessionCode(): String {
    attributes.getOrNull(SessionCodeKey)?.let { return it }
    val code = request.cookies[SESSION_COOKIE] ?: newCode(6).also {
        response.cookies.append(Cookie(name = SESSION_COOKIE, value = it, path = "/", httpOnly = false))
    }
    attributes.put(SessionCodeKey, code)
    return code
}

private fun ApplicationCall.ensureRequestId(): String =
    attributes.getOrNull(RequestIdKey) ?: "r_${newCode(8)}".also { attributes.put(RequestIdKey, it) }

private fun newCode(length: Int) = UUID.randomUUID().toString().replace("-", "").take(length)

private fun elapsedMs(startedNanos: Long) = (System.nanoTime() - startedNanos) / 1_000_000

To see the two used together, read addTask in routes/TaskRoutes.kt. The validation branch records the code, then answers differently in each mode: a fragment with the error and the typed title for HTMX, a 303 redirect back to the list for a plain form. timed() writes the validation_error row either way, with the status the server sent.

src/main/kotlin/routes/TaskRoutes.kt
private suspend fun ApplicationCall.addTask(store: TaskStore) =
    timed(TaskCodes.ADD, jsMode()) {
        val form = receiveParameters()
        val title = form["title"]?.trim().orEmpty()
        val place = form.place()
        when (val result = Task.validate(title)) {
            is ValidationResult.Error -> {
                recordValidationError(result.code)
                if (isHtmxRequest()) {
                    val view = ListView.from(store, place.query, place.pageNumber)
                    respondHtml(
                        renderTaskArea(view) +
                            renderAddForm(view, title, result.message) +
                            renderStatus(result.message, isError = true),
                    )
                } else {
                    seeOther(tasksPath(place.query, place.pageNumber, error = result.code, title = title))
                }
            }
            ValidationResult.Success -> {
                val task = Task(title = title)
                store.add(task)
                if (isHtmxRequest()) {
                    // The new task is newest, so it is on page 1.
                    val view = ListView.from(store, place.query, 1)
                    respondHtml(renderTaskArea(view) + renderAddForm(view) + renderStatus("Added \"${task.title}\"."))
                } else {
                    seeOther(tasksPath(place.query, 1))
                }
            }
        }
    }

The status column is therefore truthful rather than tidy: a rejected submission is a 200 in HTMX mode and a 303 without JavaScript, and the step and outcome columns carry the meaning. Do not change the routes to send 400 on validation errors so that the column looks cleaner. HTMX 2 does not swap a 4xx response by default, and the participant would see nothing happen.

7.4 Activity 3: label a participant's session

The first time a browser visits the application the server sets a sid cookie to six random hex characters, and every row that browser produces carries them. Before a pilot session you replace that value with the participant's pseudonym, so that the rows can be told apart later and deleted on request. The cookie is readable from JavaScript on purpose. Open the browser console on a tab showing the application, type document.cookie = "sid=P1; path=/" with the participant's code in place of P1, and reload the page.

The check is the page footer, which shows the mode and the session code the next row will carry; the route tests at this tag assert both that the footer shows a sent code and that the row does. If the footer still shows six hex characters, the cookie was set in a console belonging to a different tab, or the page was not reloaded. A cookie set from /tasks without path=/ is still honoured, because the browser defaults the path to /, so that is not the cause. If the footer shows the previous participant's code, you have not changed it, and two people's rows will merge under one pseudonym, which cannot be undone afterwards.

7.5 Activity 4: dry run both modes

Start the server with ./gradlew run from the project root. The metrics file is written relative to the directory the server starts in, so starting it from elsewhere puts the file elsewhere. Add your seed tasks through the form and copy data/tasks.csv to research/seed-tasks.csv; before each real session you copy it back. Then delete data/metrics.csv, so that the seeding does not sit in your data; the next request writes a fresh file with the header.

Set the cookie to DRY1 as in Activity 3 and work through your tasks once with JavaScript on: add a task, submit a two-letter title, filter, edit, mark done, delete. Then turn JavaScript off and do it again. In Chrome, open DevTools, press F1 for its settings and tick "Disable JavaScript" under Debugger; the setting holds only while DevTools stays open, so leave it open. In Firefox set javascript.enabled to false in about:config. Reload after the change and look at the footer: it says "no JavaScript" when the script did not run and "HTMX" when it did.

Open data/metrics.csv. Expect one row for each thing you did, plus one T0_list row after each change without JavaScript, written about a second later by the GET the redirect caused. The excerpt below, from the example data in the week-10 tag, shows a rejected add followed by a successful one in that mode, each followed by its redirect; the header is the one in the comment on LogEntry. Filtering with JavaScript on writes a T1_filter row for each pause while you type.

Check three things. The js_mode column contains both htmx and nojs; if every row says nojs with JavaScript on, the HTMX script is not loading, and the footer will have told you so. The rejected title is one validation_error row with min_length in the outcome column and no other row for that request. The session_id column reads DRY1 throughout.

If the file does not exist, nothing has been requested since you deleted it, or the server is running from another directory. If a request is missing, look at the terminal, which prints one line per request; a line there with no row in the file means the handler is not inside timed(), which at this tag means the code has been edited. When the rows are right, delete the file again. The pilots start with an empty log.

7.6 What to record

Commit research/plan.md and research/seed-tasks.csv. Do not commit data/metrics.csv; the tag's .gitignore keeps it out, and Chapter 8 says what to keep once it holds participants' rows. In the plan, write one sentence under each task saying which row in the log will mark it as finished, since the gap from the previous row to that one is the time on task you will compute in Chapter 9. For a filter in HTMX mode it is the last T1_filter row before the participant answers; for an edit it is the T2_edit row from the save, not the one from opening the form.
